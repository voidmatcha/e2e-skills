# Claude successor of the multi-model generator benchmark (preregistration)

Status: **PREREGISTERED, NOT RUN** when this file was written. Results, if any, are appended below the line marked `Results` and never change anything above it. Nothing in this directory has been frozen yet: `freeze.json` does not exist, and `freeze` is the owner's decision after the live checks listed below. Nothing here has been run against a live model: every behavior of the new transport (argv, init contract, port split, prompts) is tested offline against synthetic events and against stored v1 `claude-sonnet-5-5` transcripts only.

[generator-multimodel-v1](../generator-multimodel-v1/README.md) compared the first-party Playwright generator (A), A plus one `e2e-reviewer` pass (B) and this repository's `playwright-test-generator` 2.0.1 (C) across models. An independent audit of the stored `claude-sonnet-5-5` cells found that the Claude rows were **harness-limited**: the parent of arm A could never verify its output, arm C was a minimal treatment, and the engine's compliance counters truncated commands. **The v1 Claude results therefore stay "harness-limited descriptive": this protocol neither corrects nor replaces them.** It asks again, with the harness defects removed and the evidence recorded from the raw stream: **when each arm is actually run the way a user would run it, how do A, B and C compare per Claude model, and how do the models pool?** A negative, mixed or not-evaluable outcome is acceptable. There is no PASS/FAIL rule, and every p-value or interval below is descriptive unless the owner approves inference in writing before any v2 data is scored.

## What changes versus v1

Everything not listed is v1 unchanged: tasks, plans, seed 20261016 and the 36-cell schedule, 2 repetitions, medium effort, 1500 s timeout, the scoring engine, the scanner, the skill snapshots, the arm A prompt line (byte-identical) and the arm B task line. The v1 runner, pilot scorer, engine and v1 Claude adapter are imported, not copied; the adapter in this protocol (`generator_claude_multimodel_adapter_v2.py`) overrides only what must change.

| Change | v1 | v2 |
|---|---|---|
| Generation-phase port | the parent's `playwright test` failed with "http://127.0.0.1:<port>/health is already used" in 12 of 12 sonnet A cells, before any test started, because the MCP session of the official generator keeps the app server alive | `split-port` for every arm: the generation project reads an optional `E2E_APP_PORT`; arm A's MCP server gets its own config copy with `E2E_APP_PORT = port + 20000`; the parent keeps the default port and a fresh server. Scoring is untouched |
| Skills in arms B and C | copied to a temporary directory, the prompt pointed at `SKILL.md` paths, `--disable-slash-commands`, no Skill tool | installed as real project skills (`.claude/skills/<name>/` in the cell project, committed in the baseline), Skill tool available, the prompt asks for the skill by name |
| Skills in arm A | none | none: `--disable-slash-commands`, no Skill tool, the official agents and the `playwright-test` MCP only |
| Isolation check | first `system/init` event only | every init event (a background subagent produces a second one) against the arm's intended skills, agents, tools, MCP servers, plugins and model; a violation is an infrastructure error, never data |

The offline test diffs the v2 argv of every arm against the frozen adapter's: arm A differs by the `--mcp-config` path and the extended settings deny list; arms B and C by the removed `--disable-slash-commands`, `--setting-sources project`, the Skill tool in `--tools` and the `Skill(<name>)` allow rules for the intended skills, and the settings deny list.

## Roster and the rule about sonnet

Roster: `claude-sonnet-5-5`, `claude-haiku-5-5`, `claude-opus-5-5`, `claude-fable-5-1`, in that order (the v1 Claude models). **Sonnet already has v1 data and is re-run under v2 anyway**, because its v1 arm A could not verify and its v1 arm C was a minimal treatment (SKILL.md read in 12 of 12 cells, but no reference file read through the Read tool in 0 of 12, no preflight 0 of 12, no browser exploration 0 of 12, scan.sh in 6 of 12, an independent review in 1 of 12, self-reported complete 0 of 12, about 55 s per cell). Its v1 cells are never merged into v2 cells, views, N or the pooled analysis; `summary --v1-dir` only lists the v1 label beside the v2 rows. The authors read the stored v1 sonnet cells before writing this protocol and the extractors were tested on them; they read no other Claude model's cells and no v1 summary. No model is dropped by an entry rule: subagent tool calls are visible in the Claude stream, so arm A fidelity is observed per cell and reported, not used to exclude models.

## Arms as a user would run them

- **A, official generator.** `init-agents --loop=claude` (v1 code and digests, `model: inherit` pin), the `playwright-test` MCP server from a config copy, parent tools Read, Grep, Glob, Bash, Agent (no Write/Edit). No skills.
- **B, official plus reviewer.** The reviewer reviews and fixes the same model's A deliverable. The prompt asks for the installed `e2e-reviewer` skill; the Skill tool is available with `Skill(e2e-reviewer)` as the only allowed skill.
- **C, ours.** The prompt asks for the installed `playwright-test-generator` skill; `Skill(playwright-test-generator)` and `Skill(e2e-reviewer)` are allowed (the generator invokes the reviewer in its review step).

A project skill sits inside the worktree, which the skills' own safety text classifies as a project script. The prompts therefore grant the exact script commands as per-row approvals; this is a harness statement and an owner decision (below). The init event of every call is verified: arm A lists no skill and no Skill tool, the generator MCP tools and the official generator agent; arms B and C list the intended skills (plus any bundled skill the host's `init-check` showed, pasted into `skills.bundled_allowed` before the freeze), no playwright-test agents, no MCP tools, no web tools, Write, Edit and Skill; every call must be the requested model; any violation makes the call an infrastructure error.

## Generation-phase port split (and why it cannot leak into scoring)

The benchmark configs declare `webServer` with `reuseExistingServer: false` and one port. Scoring must keep both: a leftover server would serve the original app to a mutant run and corrupt fault and refactor scoring. The fix is therefore confined to the GENERATION project and identical for every arm: `app.mjs` reads `Number(process.env.E2E_APP_PORT ?? <port>)` and the config builds `baseURL` and the health URL from the same expression, so with the variable unset behavior is the case's own. Only arm A's MCP server receives the variable (in its own config copy, port + 20000), so its app server and the parent's `playwright test` never collide. The transform runs inside the cell builder before the baseline commit (so it is never an out-of-scope write); scoring and the secondary refactor runs stage from the case directory through the unchanged `engine.stage`. The offline test stages every task both ways and shows `reuseExistingServer: false` and no `E2E_APP_PORT` on the scoring side, that the call environment of every arm lacks the variable, and that the transform has a single call site. A fallback mode `reuse` (flip `reuseExistingServer` in the generation project, which is what the Codex successor's generation phase does) is implemented and not selected here: the parent would share a possibly dirty app instance with the MCP session, so a spec repaired against that state could fail on the fresh scoring app. The two successors therefore differ in this one harness choice, which is an owner decision (below). A runtime guard treats a parent `playwright test` that still reports "is already used" in arm A, with no model-started server, as a harness port conflict (an infrastructure error). **Not verified offline:** that Claude Code passes the config's env to the MCP server and that the MCP test run inherits it (live check 2).

## Fidelity, treatment and views

Per cell, from the raw stream-json (parent and subagent tool calls alike; analysis recomputes it from the stored transcript). Key steps: arm A: generator spawned, `generator_setup_page`, browser tools, `generator_write_test`, the parent's `playwright test`, planner or healer use, port conflict, final status complete. Arm B: reviewer skill loaded, reviewer references read, scan.sh, a `playwright test` run, edit calls, final status complete. Arm C: generator skill loaded, any reference read (Read tool and Bash recorded separately), at least two of the four hot references, preflight, exploration, scan.sh, a baseline run before the first spec write, a targeted run after it, an independent review agent, final status complete. **Invoked** and **treated** are defined in `protocol.json` before any v2 data exists (A treated: setup page and write test called; B treated: skill loaded, scanner and a test run; C treated: skill loaded, two hot references, scanner, targeted run and an independent review). Every step is counted only when the command is **executed**: the Bash command is split quote-aware into simple commands (here-document bodies removed, assignments and wrappers such as `env`, `timeout` and `npx` skipped, `bash -c '...'` parsed recursively), and the program, or the script of a shell or interpreter, must be `scan.sh`, `run-preflight-target.sh` or `playwright test`. A `cat` or `ls` of `scan.sh`, an `echo playwright test` or a here-document that contains those words is a mention and is recorded in separate `*_mentions` fields. A reference file counts as read only through the Read tool or a Bash read verb (`cat`, `sed`, `head`, `tail`, `grep`), resolving a `cd` of the same or an earlier Bash call, and a glob in the skill directory counts as all nine. An **independent review** needs an Agent spawn after the first spec write that names `e2e-reviewer` or the V6 gate (or an `e2e-reviewer` Skill call inside a subagent after that write); a spawn that only says 'review' is recorded as a mention. The classifier is not a full shell: a command hidden in a variable, a `for` list, an alias or a script the model wrote is not seen, so a step can be undercounted but not raised by text that mentions it. Skill calls outside the arm's intended skills and Skill calls whose result is an error are recorded per cell and counted in the fidelity table. The spec headers `// spec:` and `// seed:` are not evidence of anything. **Strict completion (the Codex v3 lessons):** a `generator_*` or `browser_*` call of the `playwright-test` server counts only when it completed (its tool_result is present and not an error); attempted, denied or unanswered calls are recorded as `*_attempted` and `mcp_tools_denied` and never raise a step or the treated flag. Arm A cells also carry the Codex v3 class (`official-tool`, `manual-follow`, `unverified`, `blocked`, `aborted`; B carries its source A cell's class) and `minimal_generator_use` (official-tool without any completed browser call, the weakest way to satisfy the class). `.playwright-mcp/` snapshot files are tool output and are counted as `mcp_artifact_files`, not as out-of-scope writes. `modelUsage` is cross-checked against the per-message usage visible in the stream (subagent messages included); a cell where it falls below that lower bound is counted in the fidelity and cost tables. The final message and every command are kept untruncated.

Views: **itt** (all cells as run, aborted scored 0; the decision view), **invoked**, **as_treated** (per-protocol sensitivities; treatment is a post-randomization variable) and **load_clean**. Every per-model contrast is printed beside the fidelity table, and the summary prints a discordance section (per contrast, the views whose cross-model verdict differs from itt's; per model, the views whose label differs), so a verdict that differs between itt and as_treated is reported as discordance, never resolved by picking one. On the stored v1 sonnet cells the new extractor reproduces the audit: arm A generator tools 12 of 12 and port conflict 12 of 12; arm C Read-tool reference reads 0 of 12, scan.sh 6 of 12 (the engine counted 2), independent review 1 of 12, self-reported complete 0 of 12. It also finds that 3 of the 12 C cells read a reference file through Bash (`sed`, `cat`), which a Read-tool-only count misses; both paths are therefore recorded.

## Metrics

**Primary:** markup-refactor survival (1 only if clean 3/3 and the refactor passes), averaged over the 2 repetitions per task, unchanged. **It is reported as what it measures**: refactor survival is, to a first approximation, "the clean spec names no pre-refactor `#id` or `.class` selector". The audit counted 23 of 23 clean cells naming one failing the refactor and none of 62 naming none doing so; the decomposition table reproduces the split per model and arm (on the stored sonnet cells: clean cells naming a renamed selector 8, all failed; naming none 25, all survived, with ids and classes taken from the primary refactor edits including classes set from script). That reproduction is **in-sample**: the selector reader was refined on exactly those cells (a first token list missed the class `deck` set from script in two failing cells), the 8 and 25 are not independent evidence, and the split is true by construction because a spec that names a renamed id or class fails the refactor. The reader looks only at selector literals (the first argument of `locator`, `$`, `$$`, `querySelector`, `click`, `fill` and similar calls, or a literal that as a whole is a CSS selector), ignores `${...}` interpolations, does not count a substring attribute selector such as `[class*="deck"]` when a surviving name still contains the token, and stores a dynamic-selector hint per cell. The audit's own 23 of 23 and 0 of 62 were not re-derived beyond sonnet. The **clean-conditional survival** is printed next to it. **Secondary refactor classes** (never a decision rule, primary not replaced): `text_label` (visible text and accessible names reworded, ids, classes and structure unchanged) and `structure` (extra wrappers and regrouped children, ids, classes, roles, names and text unchanged), defined in `refactors.json` for all six tasks (when this was written the Codex successor only specified the same two classes, as R-TEXT and R-STRUCT) and scored by `score-secondary` with the unchanged staging; the h1 headings are left alone in `text_label` so that each case's existing smoke spec passes on every variant. The edit lists were **not authored blind**: the authors had read the stored v1 sonnet specs and transcripts first, which the Codex successor's build procedure for its own classes forbids; `validate-refactors` takes ARIA snapshots at the initial route only, so nodes that route does not show (the confirmation dialog of v2-23, the study view of v3-09) and wrappers created from script are not validated (`refactors.json` lists them). **Cost endpoints, pre-declared as co-primary next to quality and time, with the same definition as the Codex successor:** (1) **quality per 100k tokens** = 100000 x survivors (sum of refactor_score) / processed tokens, a ratio of sums over the cells whose token record is complete, where processed = uncached input + cache write + output from `modelUsage` (subagents included) and cache reads are excluded from this denominator (the same ratio with cache reads added is printed as `quality_per_100k_total`); (2) **pipeline seconds**, per cell and per survivor. The B pipeline is its source A cell plus its own call. A call killed at the wall-clock limit has no result event and so no `modelUsage`; its tokens are then a **lower bound** from the assistant usage fields of the stream (streamed output counts are partial, USD unknown), the cell stays in the ratio, and the cost table prints the timeouts, their seconds and the lower-bound cells beside every quality-per-token number, so that an arm with more timeouts does not look cheaper per survivor. Uncached input, cache write, cache read, output and USD are also reported separately; Claude and Codex tokens are not comparable.

## Decision rules and the pre-registered pooled analysis (fixed before any v2 data is scored)

1. **Per model and contrast** (C vs A, B vs A, C vs B), v1's rule applied to a view's cells: evaluable only with at least 6 delivered specs per arm and 5 shared tasks; `suggestive: X better` if X's per-task survival is higher in at least 5 of 6 tasks and its clean-3/3 rate, effective fault kill, scanner P0 and P1/P2 are not worse. Kept for continuity; it is not the main analysis (about 23% power per model for a pilot-sized effect).
2. **Family count rule**, itt view: N = complete evaluable models (at most 3 aborted cells), N below 4 is not evaluable, else `consistent: X better in k of N models` if at least max(2, ceil(N/3)) models carry the label and none the opposite one. A weak bar worded as a count.
3. **Pooled analysis (primary descriptive analysis; the section is the Codex successor's, carried over unchanged in unit, estimate, tests, seed and owner flags).** Clusters: models and tasks. Per view (itt, as_treated), contrast and metric (refactor_score, clean, effective_fault_kill, clean-conditional survival, both secondary classes, quality per 100k tokens in its processed and total forms, pipeline seconds): per-model, per-task difference X minus Y (repetitions averaged inside a task); model effect = mean over its tasks; **pooled estimate = unweighted mean over models**; **exact sign-flip test over models** (all 2^N sign patterns; the minimum attainable two-sided p is 2/2^N, which is **0.125 for the four Claude models**, so with four models the test can never reach 0.05); **model-and-task cluster bootstrap** (crossed resampling, 10000 draws, seed 20261016, level 0.95, percentile interval). Eligible models: complete and with the contrast evaluable in the view (the count rule's own eligibility). Robustness: per-model effects, models positive and negative, family and lineage means, per-task profile, leave-one-model-out. Everything carries the label "descriptive (inference not approved)"; the owner flag `inference` is false. The headline pooled quantity is C minus A on refactor_score in the itt view.
4. **Combining with the Codex successor.** `summary --codex-dir <v2-codex output root>` pools the model effects of both families with each model one unit (up to ten models; minimum two-sided sign-flip p 0.002), from the Codex results' cells for refactor_score, clean and effective_fault_kill, in three labelled pairs: itt with its itt, as_treated with its `as_treated` view (both gate every arm on observed treatment), and, as a separate analogue only, itt with its `primary` view (which gates arm A, and B through its source, on the official-tool class and leaves every arm C cell ungated, so it is not an as-treated view), and prints the by-family means beside the pooled mean. It claims no joint verdict; host, loop and transport differences remain confounded with family. No pooled p-value is a claim unless the owner approves inference in writing before the results are read.

**Offline power simulation** (`power`, seed 20261016, 1500 replicates per cell, recorded in `protocol.json`; four models, six tasks, two repetitions, task effects shared by models, ITT dilution = share of C cells that carry the effect): for a pilot-sized effect (logit +2.4, A 0.5 to C 0.917) a model is labelled in 24.7% of replicates with full treatment (6.5% at half treatment), which agrees with the audit's 23%; the family count rule fires in 26.8% (3.1%); all four models having a positive effect occurs in 89.4% (39.1%) and the pooled bootstrap interval excludes zero in 86.7% (21.5%). Under the null the label rate is about 0.6% per direction and the pooled interval excludes zero in at most 1.1% of replicates; "all four positive" occurs in 2.6% to 5.2%. The simulation ignores selection on treatment and heterogeneity beyond the stated sd. **"not consistent" is the expected outcome for a modest real effect and is not evidence of no effect.**

## Schedule, load, aborted cells

One Claude call at a time within the campaign; sonnet first, then haiku, opus, fable (`drive --only <ids>` restricts the models and keeps the roster order); within a model the frozen v1 order. The driver holds a campaign lock and a guard that refuses to start only for a **true conflict** (next section); a running Codex container campaign is not one. Scoring and staging ports are offset by 6000 from v1's (11301+ scoring, 12301+ and 12701+ staging, +20000 for the MCP server).

A cell waits up to 1800 s while the 1-minute load is above 40, then starts; `load_at_start` above 40 flags the cell. An isolation violation is treated as systematic: that call is flagged fatal and the campaign stops after it (no second attempt), the row is kept and resume retries it after the cause is fixed; the inherited stop message then says 'usage/rate limit', the row's attempt error names the violation. Aborted cells (infrastructure error after the inherited retry, usage or rate limit, isolation violation, harness port conflict, disk floor, arm A setup UNAVAILABLE) are retried by later resumes at most twice, score 0 in itt and leave the other views; more than 3 make a model incomplete; three infrastructure-error cells in a row stop the campaign.

## Coexistence with the Codex campaign

The Codex budget and the Claude budget are separate, so the two campaigns may run at the same time. The guard (`guard` prints its report; every live verb and `score`, `score-secondary` and `validate-refactors` run it) refuses only for a **true conflict**, found from the process list (`ps`, matched by argument vector: a python interpreter, then a `run-generator-*.py` script, then a live verb), the listening sockets (`lsof`, best effort) and static tables:

|---|---|
| another Claude-family driver (this runner, the v1 runner) | the same Claude budget and the same host: one Claude campaign at a time |
| a Zeppelin-using driver (oss-eval, thin-eval, loop) | it owns the shared Zeppelin instance (fixed ports 14210 and 18080) and its driver probe pauses on any `run-generator-*.py` with the verbs drive, run, preflight, score, smoke, harness-check, final-eval or calibrate, which includes this runner; start neither while the other runs |
| the same or a nested output root | the flock covers the same campaign; the guard also compares the root with every known driver's default root and its readable environment override |
| an overlapping host port range, or a socket already listening inside this campaign's ranges | the loopback servers of the scoring engine have no occupancy check |
| a `run-generator-*.py` driver that is not classified in `KNOWN_DRIVERS` | fail closed until it is classified |

## Open owner decisions

Whether project-skill installation inside the worktree (with explicit script approvals) is acceptable or the skills should be provided from outside the worktree (for example through an added directory, which needs a live check); whether the fallback `reuse` mode should replace `split-port` (required if the MCP env does not propagate; the Codex successor uses `reuse`, so choosing it here would also make the two families identical in this respect); approval of inference for the pooled analysis (default: none); the roster order and whether fable is run; four repetitions instead of two (about doubles the cost, raises per-model label power); wiring the test into `ci-local.sh`; whether the Codex successor should adopt the same pooled definition verbatim.

The guard treats the Zeppelin drivers as a true conflict because their own driver probe would pause on this runner; whether the Zeppelin helper should learn to ignore `-claude` is the owner's decision (it is not edited here).

## Limitations

Six task clusters, two repetitions, synthetic fixtures. The new transport has not been observed live: the first live call may show a violation (the verifier then rejects it as an infrastructure error and the protocol is amended before the freeze). The port split changes the text of the generation project's `app.mjs` and config, which the model reads; identically for all arms. Arm A's parent cannot write files while arms B and C can: intentional, and a confound with the arm effect. Treatment is a post-randomization variable. A background subagent can finish after the parent's first structured output (a second init and result event); the harness uses the last result and checks every init, but the model's final status may describe an unfinished child. Arm B reviews the same model's own A output. Claude runs on the host, Bash is not path-sandboxed (read denies and an audit only), and models run on different days and loads. The renamed-selector property is a static selector-literal heuristic refined on the stored sonnet cells and the secondary refactor edits are hand-written, not authored blind, and statically checked until `validate-refactors` is run (initial route only). Fidelity steps come from executed commands only and can be undercounted for commands the classifier cannot see. Arms B and C list Claude Code's bundled skills in their context while arm A lists none (the allow rule restricts invocation, not listing); unintended Skill calls and denials are recorded per cell. Timed-out calls carry only a lower-bound token record. Model ids are provenance, not attestation. Running beside the Codex campaign shares CPU, memory and swap with it (recorded as `host_pressure`, not gated). The Claude weekly window is account-wide and also pays for interactive use. The guard cannot see an output-root override of a foreign driver unless `ps -Eww` shows its environment, and a wrapper's flattened command text in `ps` is indistinguishable from a driver (it is the parent of one).

## Results
