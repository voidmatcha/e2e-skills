# Tool-enabled real-fix reviewer workflow v3

This is a same-window, selected-public-case development experiment, not a release evaluation. The [frozen protocol](protocol.json) paired three source-repaired BEFORE/AFTER clusters (Growi #16, Chronograf #2, OpenSearch #4a) under `gpt-6-sol` medium. Both arms had the same shell tool, source, output legend/schema, disposable-workspace sandbox, and time ceiling. `workflow` received the staged reviewer skill and was told to follow its scanner and semantic process; `legend-only` received no skill and chose its own review process. Each side/arm used a fresh model call; the balanced 12-call schedule had one repetition. The full prompt, skill, source, runner, and schema identities are pinned in the protocol. Neither arm executed project code or changed the third-party repositories.

The first attempt, [v1](../real-fix-tool-workflow-v1/protocol.json), stopped after 3/12 calls because its read-only sandbox denied the scanner's trusted temporary directory; the scanner had no complete Summary. [V2](../real-fix-tool-workflow-v2/protocol.json) changed to a disposable workspace-write sandbox, then stopped after 8/12 scored calls when its overly strict exact-one-scan gate rejected an extra JSON context scan despite a complete named-spec scan. Both remain **INCOMPLETE**. V3 changed only that gate to require a complete scan of the named E2E spec while recording extra scans. It ran all 12 calls afresh; no earlier answer was reused. V3 used the hash-pinned v1 runner with the [v3 wrapper](../../scripts/evals/run-real-fix-tool-workflow-v3.py). Raw reports and prompts remain in the local benchmark cache; [results.json](results.json) pins the completed raw report by digest.

| --- | ---: | ---: |
| Exact BEFORE repair targets | **3/3** | **1/3** |
| Same-pattern mapped AFTER alarms | 0/3 | 0/3 |
| Complete scanner Summaries | 7 | 0 |
| Other predictions: confirmed / false positive / invalid location / needs context | 90 / 6 / 1 / 0 | 0 / 14 / 11 / 2 |
| Reported input tokens (cached subset) | 3,339,348 (2,955,648) | 454,993 (370,816) |
| Output tokens / summed model-call seconds | 23,492 / 924.039 | 9,043 / 340.840 |

The workflow completed one scanner pass on each of the six named E2E specs and one additional OpenSearch AFTER JSON-context scan. The source-level [Growi](adjudication-growi.json), [Chronograf](adjudication-chronograf.json), and [OpenSearch](adjudication-opensearch.json) ledgers cover all 124 distinct off-target keys across both arms. The `90/6/1` and `0/14/11/2` counts are predictions, not independent defects or a population precision estimate. Target hits were scored separately. The six new OpenSearch judgments were checked against frozen Git blobs, including the fixed-index cleanup for #20 and wrong pattern/location claims for #4b, #4a, and #4g. No full test-runtime failure reproduction was performed.

The workflow used 7.34× the reported input tokens, 4.56× the noncached input tokens, and 2.71× the summed model-call time of the equal-tools legend baseline. Cached input is already included in input; these host-reported token counts are not a billing calculation. Repeated broad reference reads and the extra context scan contributed to the observed overhead. The workflow arm's extra target hits and cleaner off-target predictions support a narrow benefit of the **combined skill instructions and tool process** on these three cases. They do not isolate scanner causality: previous scanner packets contained exact target-line candidates for Growi, but not Chronograf or OpenSearch. Selected public cases, one model, one repetition, structured findings rather than the full prose report, and no sealed release isolation prevent a general accuracy or cost-effectiveness claim. No product rule was changed to optimize this benchmark.

The target metric checks pattern and line, not severity. The source-admitted Chronograf #2 instance is P1, but this workflow call labeled it P0. Therefore the workflow's correct-severity exact-target count is 2/3, not 3/3. A later [same-skill scanner ablation](../real-fix-scanner-ablation-v1/README.md) records this distinction explicitly; it does not retroactively change the frozen v3 score.

To reproduce the report summary after a fresh run, use `python3 scripts/evals/summarize-real-fix-tool-workflow-v3.py <raw-report.json>`; it rejects protocol, call-schedule, or adjudication-coverage drift and prints the fields in `results.json`. The runner's `--plan-only` preflight checks the frozen source and prompt identities without model calls.
