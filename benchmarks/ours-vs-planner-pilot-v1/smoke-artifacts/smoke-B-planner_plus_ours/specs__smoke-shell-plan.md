# Smoke: Application Shell Loads With Primary Navigation — Deltas

## Application Overview

This document is an AUXILIARY DELTA SET for a single, already-frozen scenario: "Application shell loads with primary navigation" at route `/` on http://localhost:5174. It does not introduce new scenarios or widen scope. It records acceptance-criteria deltas, the most robust readiness gate, live-resolved locator confirmations, an interceptable load-bearing dependency, and risk/flakiness notes, each labelled as `observed`, `inference`, `verification condition`, or `limitation` per the requester's labelling rule. All `observed` items were resolved live against http://localhost:5174/ in a 1280x720 Chromium viewport during this session (dev server running Vite with `/node_modules/.vite/deps/*` pre-bundled deps, `@react-refresh`, and `@vite/client` present, confirming this is a Vite dev-mode target, not a production build).

## Test Scenarios

### 1. Smoke Shell Deltas

**Seed:** `e2e/seed.spec.ts`

#### 1.1. Scenario 1 (frozen, verbatim): Application shell loads with primary navigation

**File:** `specs/smoke-shell-plan.md`

**Steps:**
  1. FROZEN SCENARIO TEXT (verbatim, unmodified, for reference only — not a new test): Given the application is served at http://localhost:5174; When a user opens `/`; Then the application shell loads and the primary navigation is visible.
    - expect: This is the only in-scope scenario. Everything below is a delta annotation set for hardening this single scenario, not additional scenarios.
  2. (a) ACCEPTANCE CRITERIA / ADDITIONAL FAILURE CONDITIONS — verification condition: assert exactly one `header` element is present on the page.
    - expect: `observed`: at 1280x720, `document.querySelectorAll('header').length === 1` on the live page after navigating to `/`.
  3. (a) verification condition: assert exactly one element matching `[role="navigation"][aria-label="Tool Switcher"]` exists, is inside the `header`, and is visible (not merely present in DOM).
    - expect: `observed`: `document.querySelectorAll('[role="navigation"]').length === 1` on the live page; the single match has `aria-label="Tool Switcher"`, computed `display: block`, `visibility: visible`.
  4. (a) verification condition: assert the primary navigation's tablist (`[role="tablist"][aria-label="Active tool"]`) is scoped inside the Tool Switcher nav and contains exactly 3 tabs: 'Layout', 'Bins', 'Baseplate', with 'Layout' having `aria-selected="true"` (or `[selected]` in accessibility-tree terms) as the default/initial state.
    - expect: `observed`: confirmed via live snapshot — `tablist "Active tool"` with `tab "Layout" [selected]`, `tab "Bins"`, `tab "Baseplate"`, nested under `navigation "Tool Switcher"` inside `banner` (header).
  5. (a) verification condition: do NOT scope the primary-nav tab assertion using an unqualified `getByRole('tab')` or `getByRole('tablist')` — a second, unrelated tablist exists elsewhere on the page.
    - expect: `observed`: a second `tablist` (unlabelled by aria-label in the accessibility tree, rendered as plain `tablist`) with tabs 'Inspector' (selected) and 'History' exists in the right-hand complementary panel (`tablist [ref=e503]` containing `tab "Inspector" [selected]` and `tab "History"`), confirming the requester's prior finding still holds this session. Locator must be scoped via the Tool Switcher nav ancestor, e.g. `page.getByRole('navigation', { name: 'Tool Switcher' }).getByRole('tablist', { name: 'Active tool' })`.
  6. (a) additional failure condition worth asserting: the grid/application landmark should also be present and singular, since the frozen scenario's 'application shell loads' implies more than just the nav — it implies the main content mounted too.
    - expect: `observed`: `document.querySelectorAll('[role="application"]').length === 1`; accessible name observed live as `application "Gridfinity drawer grid, 10 columns by 8 rows"`, nested inside `main`. Note the numeric name (10 columns × 8 rows) reflects default new-layout dimensions and could vary with app defaults, so assert presence/role, not the exact numeric name, unless the scenario intends to pin default grid size (out of scope here).
  7. (a) additional failure condition: assert no unhandled console errors/warnings are emitted during initial load.
    - expect: `observed`: this session's load produced 0 console errors and 0 console warnings (5 total info-level messages, none inspected in detail as they were not errors/warnings). A shell-load smoke test should still assert zero `pageerror`/`console.error` events as a cheap, high-signal failure condition, since a JS exception during mount would not necessarily prevent a stale/blank DOM from technically matching weaker selectors.
  8. (b) MOST ROBUST READINESS GATE — inference: the project's own helper is `waitForAppReady(page)` in `e2e/fixtures.ts`, which does `await page.waitForSelector('header', ...)` then `await page.waitForSelector('[role="application"]', ...)`. For THIS scenario (primary navigation specifically), the strictly more precise and still-robust gate is to wait for the scoped tablist to be visible with all 3 expected tab names, since the header/application selectors alone do not guarantee the nav's tabs have finished rendering.
    - expect: `inference` (from source: `e2e/fixtures.ts` lines 24-35): recommended gate = `await expect(page.getByRole('navigation', { name: 'Tool Switcher' }).getByRole('tab')).toHaveCount(3)` after `waitForAppReady(page)`, rather than a fixed `waitForTimeout`.
  9. (b) what settles last — inference: the visible URL itself is not a reliable settle signal for this scenario, because `/` performs a client-side rewrite to `/l/<random-id>/untitled-layout` (confirmed this session, see below), which is an async operation (id generation + `history.replaceState`) that is NOT required for the nav to be visible/interactive. Waiting on `page.url()` to match the final `/l/...` pattern before asserting nav visibility risks either a race (nav can render before the URL rewrite commits) or unnecessary coupling of an unrelated concern into this scenario.
    - expect: `observed`: after `page.goto('http://localhost:5174/')` and snapshot capture, the resolved URL was `http://localhost:5174/l/CIPWVRW4dFSJ/untitled-layout` (id shape: 12 mixed-case alphanumeric characters observed this run — treat the exact id as opaque/random per the requester's own note, do not assert its literal value).
  10. (b) verification condition: do not gate readiness on network idle broadly, since the app continues loading heavy, non-shell-critical chunks (e.g. three.js, @react-three/fiber, troika-three-text, brepjs, @liveblocks/client) well after the shell/nav is interactive.
    - expect: `observed`: network trace this session shows dozens of dependency chunk requests continuing past request #1135 (`https://va.vercel-scripts.com/v1/script.debug.js`) through request #2115 (`fit-curve.js`), i.e. large 3D/CAD/collab libraries are still being fetched long after the header/nav/application landmarks are already present in the DOM (which were confirmed via the very first `browser_snapshot` taken immediately after `goto`, before this trailing chunk activity was inspected). Using `networkidle` as a readiness gate for this scenario would be slow and flaky, and is not recommended.
  11. (c) LOCATOR CONFIRMATIONS / CORRECTIONS FOR PRIMARY NAVIGATION — resolved against the live page this session.
    - expect: `observed` role/name/state mapping (exact): `navigation` role, accessible name `"Tool Switcher"`, container `<div role="navigation" aria-label="Tool Switcher" class="flex-shrink-0">`, located inside `<header>` (which is itself inside a top-level `banner`-equivalent wrapper per the accessibility tree — the raw DOM shows a `<header>` element and the a11y tree groups it under an implicit generic region before `banner`). Bounding box at 1280x720: x=16, y=8.5, width=273.6796875, height=30 (pixel-for-pixel match to the previously-observed baseline of ~274x30 at (16, 8.5) — no drift this session).
    - expect: `observed`: nested `tablist` role, accessible name `"Active tool"`, containing exactly 3 `tab` elements with accessible names `"Layout"` (state: selected/`aria-selected=true`), `"Bins"` (not selected), `"Baseplate"` (not selected). Each tab additionally contains an `img` (icon) and a text label — do not rely on exact-text matching that excludes the icon `img`, prefer `getByRole('tab', { name: 'Layout' })` which matches on accessible name including icon alt text concatenation only if the icon has no separate accessible text (confirmed: icons render as bare `img` with no additional accessible name text visible in the tree, so name resolution is dominated by the visible text node).
    - expect: `observed`: computed styles on the nav container: `display: block`, `visibility: visible` — confirms genuinely visible, not just present-in-DOM/zero-size.
    - expect: `observed`: correction/precision on landmark counts — `header` count = 1, `[role="application"]` count = 1, `[role="navigation"]` count = 1 (all singular, matching the previously-observed baseline claims exactly; no corrections needed, baseline fully reconfirmed).
  12. (d) LOAD-BEARING, INTERCEPTABLE DEPENDENCY — name the exact request URL pattern observed on the wire whose fault would deterministically prevent the primary navigation from rendering.
    - expect: `observed`: the entry module script request is `GET http://localhost:5174/src/main.tsx` (HTTP 200 in this run), requested directly from the initial HTML document alongside `GET http://localhost:5174/@vite/client` and `GET http://localhost:5174/@react-refresh`. This is a Vite dev-server ES module entry point (this target is running in dev mode, not a built/production bundle — confirmed by the presence of `/node_modules/.vite/deps/*` pre-bundle requests and `@react-refresh`).
    - expect: `verification condition`: faulting this exact request via `page.route('**/src/main.tsx', route => route.abort())` (or `route.fulfill` with a 500/empty body) before navigation would deterministically prevent the entire React app — including the `header`, the Tool Switcher `navigation`, and the `[role="application"]` grid — from mounting at all, since no React root would attach. This is the single most upstream, narrowly-scoped interceptable dependency for this scenario; broader patterns like `**/node_modules/.vite/deps/*` would also break rendering but are far less precise (dozens of matching chunk requests, not one deterministic point of failure) and are NOT recommended as the fault-injection target.
    - expect: `limitation`: this finding is dev-server-specific (Vite dev mode, `src/main.tsx` served directly as an ES module). If this scenario is ever run against a production build of the app, the equivalent load-bearing request would instead be a hashed, built JS entry chunk (e.g. `/assets/index-*.js`) referenced from the built `index.html`'s `<script type="module">` tag — that pattern was NOT observed this session (only the dev server was exercised) and would need separate live confirmation before being relied upon in a prod-build variant of this test.
  13. (e) RISKS — race conditions.
    - expect: `inference`: because `/` triggers a client-side URL rewrite to `/l/<id>/untitled-layout` (see (b) above, `observed` this session), any test step that asserts on `page.url()` immediately after `goto('/')` (rather than asserting on DOM state) is a race-condition risk independent of nav visibility — the nav can and does render before or concurrently with the URL rewrite. This scenario's Then-clause only concerns shell/nav visibility, so URL-based assertions are out of scope and should be avoided as an implicit readiness proxy.
  14. (e) RISKS — viewport-dependence: does the Tool Switcher stay visible at 1280x720?
    - expect: `observed`: yes. At 1280x720 the Tool Switcher nav is fully visible with a stable, non-clipped bounding box (16, 8.5, 273.68 x 30), well within the 1280-wide viewport (occupies roughly the left ~23% of viewport width, nowhere near the right edge where other header controls like Export/Share/language/Help/Settings live). No evidence of overlap or wrapping at this viewport size.
    - expect: `limitation`: this session only exercised the default 1280x720 desktop viewport (the fixed size supplied by `planner_setup_page`). Narrower/mobile viewports were NOT tested this session; the codebase's `e2e/fixtures.ts` defines `MOBILE_VIEWPORT = { width: 375, height: 667 }` and a separate `waitForMobileAppReady`/`data-bottom-nav` pattern (inference, from source), implying the Tool Switcher's presence/visibility at mobile widths is NOT guaranteed to use the same `role=navigation`/`aria-label="Tool Switcher"` locator and was not verified live — do not assume this scenario's locator strategy generalizes below desktop width without separate live confirmation (that would be scope expansion beyond the frozen 1280x720-implicit scenario, so it is flagged only as a limitation, not added as a new scenario).
  15. (e) RISKS — i18n-dependence of the accessible name "Tool Switcher".
    - expect: `inference`: a `button "Change language"` control showing `"EN"` is present in the header (observed live this session), strongly implying the app supports locale switching and that `aria-label="Tool Switcher"` (and the tab names 'Layout'/'Bins'/'Baseplate') are very likely translated strings that would change under a non-English locale. This test was only executed in English (default/observed locale = EN this session); the exact `aria-label` string is therefore locale-coupled and should be treated as English-only unless the test explicitly pins/asserts the locale (e.g. via a language cookie/localStorage default, or by asserting the language button reads 'EN') before relying on the literal string 'Tool Switcher' in assertions.
    - expect: `limitation`: no other locale was exercised live this session, so the exact translated strings for other locales are unconfirmed and out of scope to fabricate.
  16. (e) RISKS — other flakiness sources observed or inferred.
    - expect: `observed`: the app loads a large number of third-party/heavy chunks after initial shell paint (three.js, @react-three/fiber/drei, troika-three-text, brepjs, @liveblocks/client, polygon-clipping, etc. — 2115+ network entries captured this session on a single fresh load), and also loads `https://va.vercel-scripts.com/v1/script.debug.js` (Vercel Analytics) from an off-origin host per the requester's own note. A shell/nav smoke test must not depend on these finishing, and should ideally block/ignore the analytics script (e.g. via `page.route('https://va.vercel-scripts.com/**', route => route.abort())`) to avoid nondeterministic timing or CI network-egress flakiness — this does not affect the frozen scenario's pass/fail (nav renders regardless) but is a stability recommendation for the harness.
    - expect: `verification condition`: assert the primary-nav check completes well before any expectation on 3D/canvas features, print/export, or collaboration (Liveblocks) features, since those subsystems load asynchronously and are unrelated to 'primary navigation is visible' — mixing their readiness into this scenario's gate would be scope creep and a flakiness source.
