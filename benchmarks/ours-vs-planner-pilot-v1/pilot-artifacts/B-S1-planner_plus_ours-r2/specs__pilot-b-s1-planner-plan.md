# Pilot B-S1 Planner Hardening Deltas

## Application Overview

Auxiliary plan-hardening pass for the single frozen Scenario B-S1 ("Adding a bin to a new layout places it on the baseplate grid and the layout summary reflects the added bin", entry route `/`, http://localhost:5174). This document does not introduce new scenarios or broaden scope. It records deltas (observed / inference / verification condition / limitation) found by live-driving the app and cross-referencing e2e/fixtures.ts, e2e/test-utils.ts, e2e/add-bins.spec.ts, playwright.config.ts, and the LayerPanel/GridAxisLabels source, intended to make the existing test plan for B-S1 more precise and less flake-prone without changing its scope.

## Test Scenarios

### 1. B-S1 Plan Hardening Deltas

**Seed:** `e2e/seed.spec.ts`

#### 1.1. Delta notes for Scenario B-S1 (no new scenario; annotations only)

**File:** `specs/pilot-b-s1-planner-plan.md`

**Steps:**
  1. [observed] Live viewport for chromium project is 1280x720 (dpr 1), matching playwright.config.ts `viewport: { width: 1280, height: 720 }` for the chromium/firefox/webkit projects. At this viewport, on a fresh 10x8 layout, the grid `role=application` (`aria-label="Gridfinity drawer grid, 10 columns by 8 rows"`) has a live bounding box of x=350,y=119,width=551,height=441, i.e. cell size ~55.1 x 55.125 px, and the toolbar reports zoom '170%' via 'Fit grid to screen' auto-fit.
    - expect: No expectation change; this is baseline calibration data for the drag geometry.
  2. [verification condition] The repo helper `drawBinOnGrid(page, startX, startY, endX, endY)` in e2e/fixtures.ts takes raw pixel offsets added to the live `getGridBounds()` origin, and does NOT derive them from bounds.width/height or column/row count. The existing spec e2e/add-bins.spec.ts:107 calls `drawBinOnGrid(page, 20, 20, 100, 100)` with literal magic-number pixels. Because zoom is auto-fit (see previous row) and therefore a function of viewport size, panel-open/collapsed state (left 'Tools' panel and right 'Inspector' panel can be collapsed, which changes available canvas width), and grid size, any generated test for B-S1 that hardcodes literal pixel deltas (instead of computing them at runtime as fractions of bounds.width/10 and bounds.height/8) risks silently drawing a bin of the wrong size (e.g. 2x3 or 4x4 instead of 3x3) on a differently-sized/zoomed grid. Because the frozen outcome's primary assertion is the exact string '11% filled · 1 bins', a wrong-sized bin would produce a different (but still plausible-looking) percentage and could either false-fail OR, worse, coincidentally still say '1 bins' while asserting the wrong coverage without anyone noticing why. The generated test MUST compute drag start/end as `bounds.x + (cellWidth * colFraction)` / `bounds.y + (cellHeight * rowFraction)` using `bounds.width/10` and `bounds.height/8` read at run time via getGridBounds(), never literal pixel constants copied from one exploration session.
    - expect: A red/failing signal this catches: bin ends up sized e.g. 2x2 or 4x3 instead of 3x3, which would make '11% filled · 1 bins' assertion fail loudly (not silently) IF the coverage math changes enough to alter the percentage — but for near-miss sizes (e.g. 3x2=6 cells vs 3x3=9 cells) the percentage changes from 11% to 8%, so this particular assertion IS discriminating; the hazard is purely about the test remaining stable/reproducible across environments, not about the assertion being weak.
  3. [observed] Manually replayed the scenario's drag recipe using live, runtime-computed coordinates: `cellW = box.width/10`, `cellH = box.height/8`; dragged from `(box.x + cellW*0.5, box.y + cellH*0.5)` to `(box.x + cellW*2.5, box.y + cellH*2.5)`. Result: exactly one `[data-bin-id]` element was created with computed accessible name 'Bin 3 by 3, category Coral', role=button, aria-pressed=true, and inline style `grid-area: 1 / 1 / span 3 / span 3`. The Layers region's stats span then read exactly 'Layers.stats' formatted text '11% filled · 1 bins' (verified via `Array.from(document.querySelectorAll('span')).filter(s => /filled/.test(s.textContent))`, which returned exactly one match with that exact text, matching the U+00B7 middle-dot separator character used in the frozen assertion).
    - expect: Confirms the frozen primary assertion `toHaveText('11% filled · 1 bins')` is achievable and exact-matches live DOM output, including the middle-dot character, when coordinates are computed at runtime rather than hardcoded.
  4. [observed] Confirmed via LayerPanel.tsx source (src/features/layers/components/LayerPanel/LayerPanel.tsx:44-63,137-141): coverage = Math.round((sum of bin.width*bin.depth) / (drawer.width*drawer.depth) * 100); for a 3x3 bin on a 10x8 grid this is Math.round(9/80*100) = Math.round(11.25) = 11. This is deterministic (not a rounding-boundary coincidence): a 3x3 bin is the only common near-miss size whose coverage rounds to 11% on this exact grid (a 3x2 bin gives 8%, a 4x3 gives 15%, a 3x4 gives 15%), so the '11%' figure is a reasonably strong (though indirect) proxy that the created bin's dimensions were exactly 3x3, not merely 'some bin exists'.
    - expect: Reinforces that the frozen assertion is load-bearing for bin *size* correctness, not just bin *presence* — a valuable property to preserve when writing the final assertion; do not weaken it to a substring/regex match that would also pass for wrong-sized bins that happen to also round to a similar-looking string.
  5. [verification condition] The Layers stats string is produced via i18n key `layers.stats` = '{coverage}% filled · {count} bins', and this key is translated across 20+ locale files (src/i18n/locales/*.json). If the test environment's browser locale/Accept-Language differs from 'en' (e.g. a differently configured Playwright `locale` context option, or future default-locale-detection changes), the exact English text assertion would fail for reasons unrelated to the feature under test. Recommend the generated test either (a) explicitly force `locale: 'en-US'` in the test/project context, matching what this repo's own playwright.config.ts projects already imply by using `devices['Desktop *']` without an override, or (b) assert via the `layers.stats` semantics (percentage + count as separate, locale-independent signals, e.g. reading the rendered digits with a loose regex `/^\d+% .* · \d+ .*/`) as a fallback/secondary check — but per the frozen scope's literal wording ('layout summary reflects the added bin'), the primary exact-text check should remain, this is a supplementary robustness note.
    - expect: A red/failing signal this would otherwise miss: test runs green on a contributor's or CI machine's default locale but silently breaks (unrelated to any real regression) if that locale ever changes from 'en', OR conversely passes for the wrong reason if the string happens to coincidentally match in another locale.
  6. [observed] The Layers region's stats `<span>` has no distinguishing id/data-attribute/aria-label of its own — it is a bare `<span>` sibling to an `aria-hidden="true"` middle-dot separator span and another bare `<span>` showing '3/12u' (used height total). Locating it via `page.getByRole('region', { name: 'Layers' })` then `.getByText(/filled/)` resolved to exactly one element both pre-bin ('0% filled · 0 bins') and post-bin ('11% filled · 1 bins') states; a broader `region.locator('span')` would match 3 spans (stats, separator, height-total) and risks an ambiguous/strict-mode-violation locator error if not scoped with a text filter.
    - expect: Recommend the generated test locate the summary as `getGrid Layers region`.getByText(/filled/) (or an equivalent `.filter({ hasText: '% filled' })`), not a generic `span` locator, to avoid Playwright strict-mode failures that would be a false negative unrelated to the feature.
  7. [verification condition] `page.getByRole('button', { name: 'Select bins in column 1' })` (without `exact: true`) resolves to 2 elements ('Select bins in column 1' AND 'Select bins in column 10') and throws a strict-mode violation. This is not part of the frozen scenario's primary assertion path, but if any generated helper or secondary check uses these row/column selector buttons by inexact name for grid-cell verification, it must pass `{ exact: true }` or it will error out (a real, reproducible failure mode, confirmed live).
    - expect: Deterministic Playwright strict-mode error if `exact: true` is omitted and a double-digit row/column index exists (columns run 1-10 here, so column 1 vs column 10 collide; rows only run 1-8 so no collision there).
  8. [observed] Discovered and confirmed live a stronger, non-implementation-coupled (not inline-CSS-style-based) way to prove a bin is placed 'ON the baseplate grid' at specific cells: the grid's row/column header buttons ('Select bins in row N' / 'Select bins in column N') toggle bin selection (aria-pressed + opacity/box-shadow visual change) based on which rows/columns the bin actually intersects. For the 3x3 bin drawn at CSS grid rows 1-3 / columns 1-3: clicking column buttons 1, 2, 3 each set the bin's `aria-pressed="true"` and `opacity: 1` (fully highlighted); column 4 left it `aria-pressed="false"`, `opacity: 0.6` (dimmed/unselected). Crucially, row labels are inverted vs. visual top-to-bottom order — the row-label buttons are rendered top-to-bottom as 8,7,6,5,4,3,2,1 (row '1' is the bottom-most/front row, row '8' is the top-most/back row). Clicking rows 6, 7, 8 (the three TOP rows) selected the bin; rows 1-5 did not. This confirms the bin occupies the top-left 3x3 region (columns 1-3, rows 6-8 in the UI's row numbering) using only user-visible selection-state toggles, not by reading the element's inline `grid-area` CSS.
    - expect: A stronger secondary assertion available if desired: after drawing the bin, click 'Select bins in column 1' (exact) AND 'Select bins in row 8' (exact, the top row) and assert the bin's `aria-pressed` becomes 'true'/opacity becomes 1; then click 'Select bins in row 1' (exact, the bottom row, or 'Select bins in column 4') and assert it does NOT select the bin. This is genuinely user-observable placement-at-a-cell proof, distinct from and more meaningful than reading `style="grid-area: ..."`, and is not currently part of the frozen scenario but is offered here as a design option for future scenario hardening, since the frozen scope explicitly forbids adding it now.
  9. [limitation] The row-label inversion (row 1 = bottom/front, row 8 = top/back) was found empirically via live interaction, not stated anywhere in visible UI copy/tooltip beyond 'Click to select row N. Shift-click for range...'; there is no on-screen text explaining the numbering direction. Any test author or future scenario writer using 'row N' terminology must not assume row N corresponds to the Nth row from the top — this must be verified per-instance rather than assumed, and the frozen scenario's own wording ('3rd row from top', not 'row 3') correctly avoids this trap by using visual/geometric description rather than the UI's row-number labels.
    - expect: No specific test failure to catch here since the frozen scenario doesn't use row-N terminology; this is a documentation/gotcha note to prevent a future author from writing a wrong assertion like clicking 'Select bins in row 3' expecting it to correspond to the visually-top 3rd row.
  10. [verification condition / limitation] `waitForAutoSave()` in e2e/test-utils.ts only checks that localStorage keys `gridfinity-library-v1` and `gridfinity-layout-<activeId>` are non-null; it does NOT inspect their JSON content for the actual bin data. Observed live: navigating to `/` on a cleared/fresh profile immediately creates a new layout at a URL like `/l/<id>/untitled-layout` and the header status region already shows 'Saved' before any bin is drawn (i.e., the empty layout is itself auto-persisted). Consequently, if a generated test calls `waitForAutoSave()` expecting it to confirm that the newly-drawn bin specifically was persisted, the helper could resolve immediately (both keys already existed from the initial empty-layout save) without ever having waited for the actual post-bin debounced save (1000ms debounce, confirmed via src/shared/hooks/useAutoSave.ts:12,131 `SAVE_DEBOUNCE_MS = 1000`). This is a real gap: the helper cannot distinguish 'a layout was saved' from 'THIS bin was saved'.
    - expect: Silent-pass risk this exposes: a test that (a) draws the bin, (b) calls waitForAutoSave(), (c) reloads the page and asserts the bin persisted, could flake if step (b) returns before the debounced save actually captured the bin (race), because waitForAutoSave's success criterion is satisfied by pre-existing keys from the initial empty-layout save, not by content matching the bin. If persistence-after-reload is ever added to this scenario (not in current frozen scope), the check must poll for the bin's JSON representation inside the localStorage layout value (e.g. `JSON.parse(localStorage.getItem(layoutKey)).bins.length === 1`), not just key existence.
  11. [verification condition] Confirmed via e2e/add-bins.spec.ts that this repo's own convention calls `clearAllStorage(page)` in `afterEach`, not `beforeEach`, relying on Playwright's per-test fresh browser context for isolation on the first test of a run rather than an explicit pre-navigation clear. The frozen scenario's Given clause ('fresh browser profile, empty client-side storage') is satisfied by Playwright's default context isolation, but if a generated test instead explicitly calls `clearAllStorage(page)` BEFORE navigating to `/` in the same test (a stronger, more explicit guarantee), note that `clearAllStorage` uses `page.evaluate` which requires a same-origin document already loaded — it must be called AFTER an initial `page.goto('/')` (or any same-origin navigation) and, if isolation is meant to affect the very state read on load, followed by a second `page.goto('/')`/`page.reload()` before the drag begins, otherwise the initial auto-created 'Saved' empty layout (see prior row) from the first load would already exist in storage at the time of the pre-state assertion — in practice harmless for a truly fresh context, but a hazard if this test ever runs in a shared/reused-context mode.
    - expect: No currently-observed failure (default Playwright context isolation makes this moot for CI), but flagged as a limitation/edge-case for anyone changing test isolation strategy (e.g. adopting `test.describe.serial` or a shared page fixture) later.
  12. [observed] Pre-state assertion values were directly confirmed live on initial load of a fresh layout (before any drag): Layers region stats span text = '0% filled · 0 bins' exactly, and `document.querySelectorAll('[data-bin-id]')` count = 0. Post-drag values were directly confirmed live: stats span text = '11% filled · 1 bins' exactly, `[data-bin-id]` count = 1, Inspector heading text pattern `/\d×\d Bin/i` would match '3x3 Bin' (heading itself not re-screenshotted here but consistent with the CONTEXT block and the confirmed grid-area/aria-label/coverage-math evidence above).
    - expect: This is the state-transition (empty layout -> one bin placed) pair the frozen scenario's Then clause depends on; both endpoints are now independently, live-verified in this session, not merely inferred from the provided CONTEXT block.
