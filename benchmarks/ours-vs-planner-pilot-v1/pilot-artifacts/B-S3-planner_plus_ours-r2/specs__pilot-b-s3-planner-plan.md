# Pilot B-S3 — Cloud Sync (Anonymous, Cross-Profile) Capability Investigation

## Application Overview

Gridfinity Layout Tool (http://localhost:5174) auto-creates a layout at `/` and redirects to `/l/<id>/<slug>`. Scenario B-S3 posits: "Without signing in, the layout is synced to a second browser profile through Cloud Sync and appears there automatically." This document reports live-browser findings only (plus source-code corroboration) and delivers plan deltas for this single scenario. No repository files were modified. Verdict: CAPABILITY_ABSENT — the application has no mechanism that automatically propagates a layout to a second, separately-stored browser profile without sign-in. The only cross-device mechanisms available anonymously are OAuth sign-in (which starts a real sync engine, but requires signing in — contradicting the scenario's premise) and the manual "Share layout" link (requires copying a URL out-of-band).

## Test Scenarios

### 1. B-S3 Investigation — Cloud Sync Without Sign-In

**Seed:** `e2e/seed.spec.ts`

#### 1.1. B-S3: Anonymous cross-profile Cloud Sync — findings and verdict

**File:** `specs/b-s3-cloud-sync-anonymous.spec.md`

**Steps:**
  1. ADMISSION GATE (observed): planner_setup_page and planner_save_plan tools are both available. Browser launched successfully via planner_setup_page, then browser_navigate to http://localhost:5174 loaded the app and redirected to /l/TiQxAc6thjBm/untitled-layout, confirming the app is live and reachable.
    - expect: Both required tools present.
    - expect: Live page loads and redirects to /l/<id>/<slug> as expected.
  2. observed: Opened header 'Open settings' button, clicked the 'Account' tab. Snapshot of tabpanel 'Account' shows: an 'Account' section heading followed by an EMPTY bordered box (no sign-in buttons, no text), and a 'Cloud sync' section showing two static strings side-by-side: 'All changes synced' (left) and 'Not synced yet' (right).
    - expect: This is the actual anonymous-state rendering of Settings > Account in this environment — not the expected 'local mode' panel with Sign in with Google/Github buttons.
  3. observed + inference: Read src/shell/Modals/SettingsModal/tabs/AccountTab/AccountTab.tsx. The empty box corresponds to the fallback branch `status !== 'authenticated' && status !== 'anonymous'` (i.e. status === 'unknown'), rendered as `<div ... aria-busy="true" />`. The expected anonymous branch (`status === 'anonymous'`) would render 'account.localMode.heading' text plus 'Sign in with Google' / 'Sign in with Github' buttons, which were NOT present live. Root cause traced to src/core/sync/session/useSession.ts: refreshFromServer() calls getMe() (fetches /api/auth/me expecting JSON) and on any throw returns null, leaving status stuck at 'unknown' forever.
    - expect: Verification condition: any test must NOT assert on the presence of Google/Github sign-in buttons or 'local mode' text without first confirming session status actually resolves to 'anonymous' in the target environment; in this dev fixture it does not.
  4. observed: browser_network_request on the /api/auth/me call (index 1147) shows response content-type `text/javascript` and a response body that is the raw TypeScript/ESM source of the API route handler (imports from /api/lib/*.ts, JSDoc comments, source map) — not executed JSON. Status was reported 200 in the network list despite the body being unexecuted source.
    - expect: limitation: in this local fixture, /api/* routes are served as raw source rather than executed as serverless functions, so genuine authenticated/anonymous JSON responses from the real backend could not be observed live. This is an environment limitation, not evidence about production behavior, and is called out separately from the source-code-level verdict below.
  5. observed: With the layout in its initial anonymous state, renamed the layout header (via the 'Click to edit layout name' textbox) to 'Cloud Sync Test Layout' and pressed Enter, then drew a 3x2 bin on the grid via mouse drag. Confirmed via Inspector snapshot that the bin was created ('3×2 Bin' panel, Bin List shows 1 entry) and the layout name updated in the header/tab title. Then called browser_network_requests (static:false) filtered on '/api/' and separately filtered on 'sync' (static:true).
    - expect: Result: only /api/auth/me (GET, 200) and /api/ml-telemetry (POST, 404) appeared under '/api/'. Filtering all traffic (including static/module requests) for the string 'sync' returned zero network REQUESTS matching an /api/sync/* endpoint — the only 'sync' hits were Vite serving the app's own /src/core/sync/*.ts and /src/features/*/sync/*.ts source modules (i.e. the sync feature's code being loaded, not any sync API traffic). No /api/sync/<kind>/<id> PUT/DELETE call was ever issued after renaming the layout or creating a bin while anonymous.
  6. inference (source code): Read src/shell/sync/SyncSessionMount.tsx. The sync engine's start(adapters) — which owns the outbox-drain logic that would eventually PUT to /api/sync/<kind>/<id> — is invoked only inside `useEffect(() => { if (status !== 'authenticated') return; ... start(adapters); }, [status, ...])`. Read src/core/sync/engine.ts: its own doc comment states 'Boot site (PR 4d) calls this on sign-in, stop() on sign-out.' There is no code path that starts the engine for an anonymous session.
    - expect: This corroborates the live observation: while anonymous, no local change (rename, bin creation) is ever enqueued to a running outbox/engine, so no /api/sync/* traffic can occur regardless of environment. This is the structural reason automatic cross-profile sync cannot happen without sign-in.
  7. observed: The 'Cloud sync' status line reading 'All changes synced' / 'Not synced yet' was traced via source search to i18n keys `dock.syncStatusIdle` = 'All changes synced' and `account.sync.lastSyncedNever` = 'Not synced yet'. In AccountTab.tsx these render from `useSyncStatusStore` fields `state` (default 'idle') and `lastSyncedAt` (default null/never-set) — i.e. this is the store's untouched initial/idle state, not a signal that any sync operation ran.
    - expect: Verification condition (explicitly required by task): a passing test MUST NOT assert on the static text 'All changes synced' as evidence of sync capability or activity — it renders identically whether or not a sync engine has ever run, because it is simply the idle default with pendingCount === 0.
  8. observed: Clicked header 'Share layout' button. A 'Share Layout' dialog opened showing the layout title, a permission dropdown ('Anyone with link can view' / '...can edit'), and a 'Create share link' button. No link was generated automatically; the flow requires the user to click 'Create share link' and then manually copy/transmit the resulting URL to another browser/person.
    - expect: This confirms the 'Share layout' feature is mechanism (b) from the task's taxonomy: a manual link-based flow, categorically different from and NOT satisfying automatic cloud sync (mechanism (a)).
  9. verdict synthesis
    - expect: CAPABILITY_ABSENT.
    - expect: Evidence (observed): anonymous Account tab shows no working sign-in-optional sync affordance in this environment (stuck-loading Account box); Cloud sync panel shows only static idle/never-synced default text; renaming a layout and creating a bin while anonymous produced zero /api/sync/* network requests; the only cross-browser transfer mechanism available anonymously is the manual 'Share layout' -> 'Create share link' flow (URL must be copied by the user).
    - expect: Evidence (inference from source): src/shell/sync/SyncSessionMount.tsx gates `start(adapters)` (the sync engine) behind `status === 'authenticated'`; src/core/sync/engine.ts documents it is started on sign-in and stopped on sign-out; there is no anonymous-mode sync path in the codebase.
    - expect: Therefore Scenario B-S3 as specified ('without signing in, the layout is synced ... automatically') describes behavior the application does not implement. No true positive test can be written for it as stated.
  10. plan delta: do not write or attempt to automate scenario B-S3 as a passing/positive test.
    - expect: If a regression-style (negative) test is desired instead, it should assert the ABSENCE of automatic propagation: create/rename a layout in profile A (fresh anonymous storage), open a second, separately-storaged browser context (profile B) at the same origin with no cookies/localStorage/IndexedDB shared and no sign-in performed, navigate to `/` there, and assert that profile B's library does NOT contain the layout created in profile A (e.g. via the 'Switch layout' library list), and that no /api/sync/* requests were issued by profile A while anonymous.
    - expect: Such a test must NOT: (a) assert on the static 'All changes synced' label as a positive signal, (b) inject localStorage/IndexedDB state itself and then assert on that injected state, (c) use the manual Share-link flow and call that 'automatic sync', or (d) fabricate a locator/selector not actually present in the live DOM.
    - expect: If product intent is that Cloud Sync should work anonymously (e.g. via an anonymous-device pairing key), that capability does not currently exist per both live observation and source; this should be filed as a product/spec gap, not silently downgraded to a passing test against Share-link or against self-authored storage writes.
    - expect: Separately-tracked environment limitation: /api/* endpoints in this local dev fixture return raw unexecuted source (content-type text/javascript) instead of JSON, which independently breaks session-status resolution (stuck at 'unknown') in this environment. Any future test suite targeting this app's auth/sync endpoints needs a properly running API backend (not just `vite` dev) to be meaningful; this pilot's negative-capability verdict does not depend on that bug, since it is corroborated by the sign-in-gated engine.start() code path, but it does mean the anonymous 'local mode' UI (Sign in buttons) could not be visually confirmed live in this session.
