# Scenario A-S1 Hardening Deltas (Offline/Funny-mode canned reply)

## Application Overview

This document is a set of plan DELTAS for a single FROZEN, already-approved scenario (A-S1). It does not add, split, reword, or expand the scenario. It only adds readiness gates, transient-state warnings, locator recommendations, and concrete verification conditions discovered by live exploration of http://localhost:5174 and by reading the app source (ChatWindow.tsx, funnyReply.ts, funnyReplies.ts, appAssistantReply.ts, ChatMessage.tsx, LoadingMessage.tsx). Each expectation item is prefixed with exactly one label: [observed] = confirmed live in this session, [inference] = confirmed only via source code, [verification condition] = a concrete failure condition the test must catch, [limitation] = something not observable or out of the app's capability. Frozen scenario text (verbatim, unchanged): Given: the application is served at http://localhost:5174, fresh browser profile, empty client-side storage. When: the user performs the actions the outcome below requires. Then: In offline mode, sending a message shows the user's message and the deterministic canned reply keyed by its first letter in the chat transcript. Context already established: "Offline mode" = the app's default-on "Funny mode" toggle (data-testid=funny-mode-toggle), which produces a canned reply keyed by the first letter of the message with no network call.

## Test Scenarios

### 1. A-S1 Hardening Deltas

**Seed:** `e2e/seed.spec.ts`

#### 1.1. Scenario A-S1: Offline mode sending a message shows user message + canned first-letter reply

**File:** `specs/a-s1-offline-canned-reply.spec.ts`

**Steps:**
  1. [readiness gate] Navigate to http://localhost:5174 with a fresh browser profile and empty client-side storage (per the frozen Given).
    - expect: [observed] Immediately after navigation, the UI is in an initial disabled/loading state: funny-mode-toggle (checkbox, data-testid=funny-mode-toggle) is checked but disabled; chat-input (data-testid=chat-input) is disabled; send-button (data-testid=send-button) is disabled; help-suggestion (data-testid=help-suggestion) is disabled; reset-button (data-testid=reset-button) is disabled; the message list shows a plain 'Loading…' paragraph (no data-testid).
    - expect: [inference: src/components/ChatWindow.tsx state historyReady, lines 30 and 41-63] This disabled/loading state is driven by a historyReady flag that is set true in the finally-block of the initial fetchMessages() bootstrap effect regardless of whether that fetch succeeds or fails — so the gate clearing is unrelated to backend/network availability and will clear even fully offline.
  2. [readiness gate] Wait for the readiness gate to clear before any interaction: wait for the 'Loading…' text to disappear (or equivalently for chat-input/send-button/funny-mode-toggle to become enabled). Do not use a fixed/arbitrary sleep for this.
    - expect: [observed] After the gate clears, the placeholder text changes to 'No messages yet.' and funny-mode-toggle, chat-input, help-suggestion, and reset-button all become enabled (confirmed via snapshot before/after using browser_wait_for on text 'Loading…' going hidden).
    - expect: [observed] Two GET requests to http://localhost:3001/api/messages fail with net::ERR_CONNECTION_REFUSED during this window (confirmed via network requests and console errors) yet the app still reaches the ready state — confirming the gate is a client-side readiness gate, not a real backend dependency.
    - expect: [verification condition] If the test types into chat-input or clicks send-button before this gate clears, the actions will act on disabled elements; the test must treat clearing of this gate as a hard prerequisite step, not something optional or skippable.
  3. [verification condition] Before sending anything, explicitly assert that funny-mode-toggle (role checkbox, accessible name 'Assistant mode Funny mode', data-testid=funny-mode-toggle) is checked, rather than merely assuming default state.
    - expect: [observed] The toggle is checked by default on a fresh load with no prior interaction (confirmed in the very first post-load snapshot and again after the readiness gate clears).
    - expect: [verification condition] If, at this point, the toggle is found unchecked, the scenario's own precondition ('offline/funny mode') is false; the test must fail immediately here rather than continue, because continuing could exercise the real POST /api/chat network path instead of the canned-reply path the scenario is about.
  4. [locator + message-choice verification condition] Type a plain-statement message into chat-input (textbox role, name 'Type a message…', data-testid=chat-input). The message must: (a) contain no '?' character, (b) not be exactly 'Help' (case-insensitive), and (c) not be exactly 'Hello there!' with the exclamation mark. Example proven live in this session: 'Hello there' (no trailing '!').
    - expect: [inference: src/lib/appAssistantReply.ts lines 102-114] Any message containing '?' is routed through getAppAssistantReply's keyword-topic lookup (reset/funny mode/history/search/playground/etc.) instead of the letter-keyed funny reply; a message exactly equal to 'Help' (case-insensitive) returns a hard-coded help menu instead. Using either form would make this test pass or fail for the wrong reason (wrong reply mechanism), defeating the scenario's intent.
    - expect: [inference: src/lib/funnyReply.ts lines 9-13, 26] A message whose trimmed value is exactly 'Hello there!' (with '!') is special-cased to the fixed reply 'GENERAL KENOBI!!' plus an attached image (data-testid=message-assistant-image), bypassing the first-letter lookup entirely — this exact string must be avoided when constructing the test message for this scenario.
    - expect: [observed] send-button (data-testid=send-button) is disabled while chat-input is empty and becomes enabled once non-empty text is present (confirmed via snapshot diff before/after typing 'Hello there').
  5. [locator] Click send-button (data-testid=send-button) to submit the message.
    - expect: [observed] A message-user element (data-testid=message-user) appears in the transcript containing the exact text that was typed (confirmed via DOM data-testid enumeration after send for both 'Hello there' and 'hello lowercase').
    - expect: [inference: src/components/ChatWindow.tsx line 14 (FUNNY_REPLY_DELAY_MS = 120) and lines 78-88] After the user message appears, there is an artificial ~120ms delay during which loading=true; controls (chat-input, send-button, funny-mode-toggle, help-suggestion, reset-button) become disabled again and a loading-indicator element (data-testid=loading-indicator, visible text 'Thinking...') is rendered as a temporary assistant-role bubble before being replaced by the real reply. This transient state was NOT directly captured live in this session (the window is short relative to manual tool round-trips) and is flagged as a limitation below.
    - expect: [verification condition] Any assertion on the assistant reply must use Playwright's auto-waiting/polling locator assertions (e.g. expect(locator).toHaveText(...)) rather than an immediate, non-retrying read of textContent taken right after the click — a non-polling check risks intermittently observing the pre-reply/loading state as a false negative, or coincidentally passing/failing depending on tool timing, i.e. flakiness in either direction.
    - expect: [verification condition] No new network request to /api/chat (POST) should appear after clicking Send while funny-mode-toggle is checked; use browser_network_requests (or route interception) to assert that the only requests seen are the already-known bootstrap /api/messages calls (and, if Reset was used earlier, /api/reset) and nothing new to /api/chat. Any /api/chat request here indicates the offline/no-network guarantee in the scenario's Then-clause was violated.
  6. [verification condition] Wait for and assert the exact text of the message-assistant element (data-testid=message-assistant) using an auto-waiting assertion.
    - expect: [observed] For 'Hello there' (first letter H), the reply is exactly: "Historians agree: the first bug was a literal beetle with opinions." — confirmed live via DOM data-testid enumeration immediately after send.
    - expect: [observed] Repeating with 'hello lowercase' (lowercase h) produced the identical reply text, confirming the key lookup is case-insensitive.
    - expect: [inference: src/lib/funnyReply.ts lines 14 and 18, and src/data/funnyReplies.ts FUNNY_REPLIES_BY_LETTER map] The key is derived from the FIRST character matching the regex [a-zA-Z] found anywhere in the trimmed message (not necessarily string index 0), upper-cased, then looked up in FUNNY_REPLIES_BY_LETTER; if no letter exists at all the reply falls back to FUNNY_NO_LETTER_FALLBACK. The test's expected-value computation must mirror this exact rule (first regex-matched letter, case-insensitive), not a naive 'message.charAt(0)' assumption, or the expected string could be wrong for messages starting with a digit/punctuation/emoji.
    - expect: [verification condition] The test must fail on: wrong-letter's canned text, any truncation/paraphrase/typo versus the exact string in FUNNY_REPLIES_BY_LETTER, the reply appearing under message-user instead of message-assistant, or the reply matching a different mechanism's output (help menu, topic-keyword reply, or the 'GENERAL KENOBI!!' special case) — assert exact string equality scoped to the message-assistant data-testid, not a loose substring/text-anywhere-on-page search.
  7. [limitation] Document known limitations of this hardened plan; no test action required for this step.
    - expect: [limitation] The ~120ms loading-indicator transient state (data-testid=loading-indicator, text 'Thinking...') is confirmed only via source (src/components/LoadingMessage.tsx); it was not visually captured live in this session because manual tool-driven interaction/snapshot round-trips are slower than the 120ms window. An automated Playwright test can capture it deterministically (e.g. via clock control or immediate polling); this exploration could not.
    - expect: [limitation] reset-button (data-testid=reset-button) also fires a best-effort POST to /api/reset that fails offline with ERR_CONNECTION_REFUSED without blocking the local/client-side reset (observed live: transcript still cleared to 'No messages yet.'). This is noted only for context on achieving a fresh state between runs; exercising Reset itself is not part of the frozen A-S1 outcome and is not asserted here.
  8. SCOPE-CHANGING (not applied) — the following adjacent behaviors were identified during exploration but are deliberately excluded as out of scope for this single frozen scenario:
    - expect: Toggling funny-mode-toggle off to exercise the real /api/chat network path — a different mode, not 'offline mode'.
    - expect: Sending the exact string 'Hello there!' to exercise the special-cased 'GENERAL KENOBI!!' + GIF reply — a different, non-letter-keyed reply mechanism.
    - expect: Sending 'Help' (exact) or any message containing '?' to exercise getAppAssistantReply's help-menu/topic-keyword replies — a different, non-letter-keyed reply mechanism.
    - expect: Sending a message with no alphabetic characters to exercise FUNNY_NO_LETTER_FALLBACK — a different keying rule (absence of a letter), not 'keyed by its first letter'.
    - expect: Asserting on Reset Chat's best-effort /api/reset network semantics as a standalone behavior.
    - expect: Asserting on the initial loading/readiness gate as an independent test outcome beyond 'the test must wait past it before acting'.
