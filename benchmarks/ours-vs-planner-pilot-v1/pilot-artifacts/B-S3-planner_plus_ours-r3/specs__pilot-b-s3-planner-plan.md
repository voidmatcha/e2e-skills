# Plan Deltas — Scenario B-S3 (Anonymous Cloud Sync Cross-Profile Propagation)

## Application Overview

Auxiliary plan-hardening pass for a single frozen scenario (B-S3) against the gridfinity-layout-tool dev server at http://localhost:5174. This document does NOT introduce new scenarios; it returns locator corrections, verification conditions, and limitations discovered by live exploration of the Settings > Account tab and by a genuine second-browser-context test, plus source-level inference from the auth-and-sync skill doc and AccountTab test suite. Bottom line: the central capability under test (anonymous, no-sign-in, automatic Cloud Sync propagation to a second browser profile) was NOT found in the app; Cloud Sync in this codebase is explicitly gated behind OAuth sign-in (Google/GitHub).

## Test Scenarios

### 1. B-S3 Plan Deltas

**Seed:** `e2e/seed.spec.ts`

#### 1.1. Scenario B-S3 — Deltas, Locators, and Verdict

**File:** `specs/pilot-b-s3-planner-plan.md`

**Steps:**
  1. DELTA 1 (observed): Locator correction for reaching the relevant panel. Header settings button's accessible name is exactly "Open settings" (role=button). Path: click role=button name="Open settings" -> dialog role=dialog name="Settings" opens -> click role=tab name="Account" (under tablist role=tablist name="Settings", section heading "Account & Data") -> tabpanel id="settings-tabpanel-account" becomes visible.
    - expect: Settings dialog opens with heading 'Settings' and a tablist containing sections 'Preferences', 'Defaults', 'Account & Data' (Account, Privacy, Storage), 'Advanced'.
    - expect: Account tabpanel contains two sections: heading 'Account' (an identity/sign-in box) and heading 'Cloud sync' (a status box).
  2. DELTA 2 (observed — LIVE APP BUG, not a test-authoring note): On this dev server, the 'Account' box under the Account tab never resolves. Its live DOM is `<div class="rounded-md border border-stroke-subtle p-4 h-[3.5rem]" aria-busy="true"></div>` — an empty, permanently-loading skeleton with no visible text, no sign-in buttons, and no accessible name/role content, even after a 3-second wait.
    - expect: If this were working per the app's own design (see Delta 4), the anonymous-state Account box should instead render text matching /working locally/i and /your layouts are saved on this device/i, plus two buttons: role=button name=/sign in with google/i and role=button name=/sign in with github/i.
    - expect: On this dev instance none of that renders; the box stays an empty aria-busy skeleton indefinitely.
  3. DELTA 3 (observed): Root cause of Delta 2 — the app's `/api/auth/me` call (which the client presumably awaits to resolve session status) returns HTTP 200 but with body content that is the raw, untranspiled TypeScript source of the API handler file (visible imports like `import { requireMethod } from "/api/lib/method.ts"`) rather than the expected JSON `{authenticated: false, user: null}`. This is consistent with the repository's own documented dev-mode limitation: 'pnpm run dev does not serve /api (no vite proxy) — runtime verification means a Vercel preview deploy' (.claude/skills/auth-and-sync/SKILL.md).
    - expect: This confirms the /api/* backend (auth, sync) is non-functional in this particular dev-server deployment; any assertions requiring real OAuth sign-in or real sync network calls cannot be exercised against this instance and must be treated as untestable here.
  4. DELTA 4 (inference, from src/shell/Modals/SettingsModal/tabs/AccountTab/AccountTab.test.tsx and .claude/skills/auth-and-sync/SKILL.md — NOT resolved live due to Delta 3): The application's Cloud Sync is explicitly and exclusively gated behind an authenticated session. Every `api/sync/*` handler starts with `requireSession()` and 401s without a valid session cookie (`__Host-gflt_session` / `gflt_session`). The client-side AccountTab test asserts that in the anonymous state the UI shows 'working locally' / 'your layouts are saved on this device' copy together with 'Sign in with Google' / 'Sign in with GitHub' buttons, and that sync status/pending-count/identity fields only render once `status: 'authenticated'`. There is no anonymous/no-sign-in code path in AccountTab or the sync engine (`src/core/sync/`) that pushes or pulls layout data.
    - expect: No toggle, opt-in switch, sync code, or device-pairing affordance exists anywhere in Settings, Storage tab, Labs, or header menus that would enable Cloud Sync without first completing Google or GitHub OAuth sign-in.
  5. DELTA 5 (observed — direct live cross-profile test): Created a genuine second, isolated browser context (separate cookies/localStorage/IndexedDB — the closest in-session equivalent of a 'second browser profile') via `browser.newContext()` and navigated it to http://localhost:5174/ fresh, with no sign-in and no manually shared link, while the original profile's layout remained open at `http://localhost:5174/l/9HlFmIItfMKt/untitled-layout`.
    - expect: The second, independent profile was redirected to a brand-new, distinct layout slug: http://localhost:5174/l/EuFaRVFQkefh/untitled-layout — a different randomly-generated ID, not the original layout.
    - expect: This is direct proof that, absent sign-in, the two profiles do NOT share layout state: the app creates an independent local (client-only) layout per browser profile rather than propagating any layout automatically.
  6. DELTA 6 (observed / scope clarification, per task's exclusions): The app does have two adjacent, DIFFERENT mechanisms that must not be confused with the scenario's claim: (a) 'Share layout' button in the header (role=button name='Share layout') — produces an explicit, manually-copied share link (cloud-share feature backed by `src/features/cloud-share/`), and (b) real-time Collaborative Editing via Liveblocks, joined explicitly by opening a shared room/link (see `src/shell/Collab/CollabProvider/CollabProvider.tsx` and `useCloudShareAutoSync.ts`, which auto-syncs only for the share *owner* to keep a share link's Blob copy fresh — this is share-link-scoped, not a general anonymous cross-profile sync). Neither of these matches the scenario's description of automatic, no-sign-in, no-manually-pasted-link propagation to an arbitrary second profile.
    - expect: A tester who lands on the Share button or on Collaborative Editing while investigating this scenario should recognize these as out-of-scope per the task brief and not credit them as satisfying B-S3.
  7. DELTA 7 (verification condition): Given the above, the given/when/then in Scenario B-S3 describes a capability this application does not provide. Recommend the scenario be marked as testing a NEGATIVE/absent capability. Any automated test written from this scenario must assert the ABSENCE of automatic anonymous propagation, e.g.: after creating content in profile A with no sign-in, a fresh profile B loaded at the bare root URL (no shared link) must NOT show profile A's bins/layout, and the Account tab (once its aria-busy skeleton bug in Delta 2 is fixed) must show 'Sign in with Google/GitHub' rather than any synced content, for an anonymous session.
    - expect: Test fails (correctly) if a future build ever makes profile B automatically inherit profile A's layout without sign-in and without a manually shared link, since that would be a serious anonymous cross-user data leak.
    - expect: Test should also fail loudly (rather than silently pass) if the Account tab's identity box is stuck in the aria-busy empty-skeleton state observed in Delta 2, since that indicates the local dev/test environment cannot exercise sign-in-gated behavior at all — such a run's results for any sign-in-dependent assertion should be treated as inconclusive, not as a pass for 'no sync happened'.
  8. DELTA 8 (limitation): The /api/* backend does not function under `pnpm run dev`/this dev-server invocation (Delta 3). Consequently OAuth sign-in, real `/api/sync/*` traffic, and the true authenticated Cloud Sync flow cannot be exercised or verified live in this environment at all — confirmed or denied only by source/tests (Delta 4), not by live interaction. Any test suite targeting authenticated Cloud Sync behavior needs a Vercel preview deployment or `npx vercel dev` (per .claude/skills/auth-and-sync/SKILL.md), not this dev server.
    - expect: Test infrastructure/CI notes should flag that this specific scenario's authenticated-path assertions are environment-dependent and will be inconclusive (not failing, not passing) against a plain `pnpm run dev` target.
  9. BOTTOM-LINE VERDICT for the central question
    - expect: NOT FOUND. There is no anonymous (no-sign-in) Cloud Sync opt-in toggle, no anonymous device-pairing/sync-code/link-this-device affordance, and no automatic cross-profile propagation of a layout without sign-in and without a manually pasted share link. Cloud Sync in this app is exclusively an authenticated (Google/GitHub OAuth sign-in) feature (Delta 4, inference) and a direct live two-context test confirms two anonymous profiles get independent, non-shared layouts (Delta 5, observed). The only anonymous cross-device mechanisms that exist are the explicit Share-link (cloud-share) and explicitly-joined real-time Collaborative Editing (Delta 6) — both are out of scope per the task brief and do not satisfy the scenario as written.
