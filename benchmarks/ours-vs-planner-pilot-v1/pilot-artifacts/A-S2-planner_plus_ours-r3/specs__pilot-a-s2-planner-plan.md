# Scenario A-S2 Hardening Deltas

## Application Overview

This document contains PLAN DELTAS ONLY for the single already-approved Scenario A-S2 (client-side chat history persistence and deletion) of the Playwright Chat Lab app served at http://localhost:5174. No new scenarios have been added, and no existing scenario has been split, reworded, or removed. Each expectation below is labelled [observed], [inference], [verification condition], or [limitation] per the requesting agent's instructions. "[observed]" items were confirmed live against the running dev server in this session (snapshots/DOM/localStorage/dialog inspection). "[inference]" items come from reading src/components/ChatWindow.tsx, src/components/ChatInput.tsx, src/components/ChatHistoryProvider.tsx, src/lib/chatHistoryStorage.ts, and src/pages/HistoryPage.tsx, but were not independently re-verified in the browser. "[verification condition]" items are failure conditions a robust test must be able to detect. "[limitation]" items could not be observed or verified in this session. The app's pre-existing failing requests to http://localhost:3001 and Google Fonts were left untouched, as instructed, and were not stubbed or repaired.

## Test Scenarios

### 1. Scenario A-S2 — Chat message persists in history across reload and can be cleared

**Seed:** `e2e/seed.spec.ts`

#### 1.1. A-S2: Send a chat message, verify it survives a reload on /history, then delete history

**File:** `e2e/history-persistence.spec.ts`

**Steps:**
  1. Start with a fresh browser profile / empty client-side storage and navigate to http://localhost:5174/.
    - expect: [observed] Page loads with title 'Playwright Chat Lab'; nav bar exposes links Chat (/), Search (/search), Message history (/history), Playground (/playground), Help (/help).
    - expect: [observed] Immediately after `page.goto()` resolves, the composer textarea (data-testid=chat-input) is NOT disabled and the placeholder text 'No messages yet.' is already shown (i.e. historyReady has already flipped true) — confirmed via `isDisabled()` returning false and `.chat-window__placeholder` textContent right after goto, with no explicit wait added.
    - expect: [inference] Per ChatWindow.tsx, the textarea and Send button share `disabled={loading || !historyReady}`; `historyReady` starts false and only becomes true inside the `finally` block after the background `fetchMessages()` call (to the intentionally-down http://localhost:3001) settles, at which point the placeholder also switches from 'Loading…' to 'No messages yet.'. So there IS a real, code-level disabled window before boot completes.
    - expect: [limitation] Could not directly capture the transient 'Loading…' / disabled composer state in this session — the ERR_CONNECTION_REFUSED failure to :3001 resolves faster than any observation point reachable via normal navigation waits (goto/waitForLoadState) without adding artificial network delay, which was avoided since the task says not to stub or repair the app's pre-existing failing requests. Do not assume this window is literally zero-length; it is only unobserved here.
    - expect: [verification condition] A test must not assume the composer is instantly interactive without checking. It should explicitly wait for the textarea to be enabled (e.g. `expect(chatInput).toBeEnabled()`) and/or for the placeholder text 'No messages yet.' before typing, rather than firing keystrokes unconditionally right after navigation.
  2. Click into the chat-input textarea and type a non-empty message (e.g. 'Hello world'). Observe the Send button's disabled state before and after typing.
    - expect: [observed] Before typing, Send button (data-testid=send-button) has the `disabled` attribute (confirmed via snapshot: `button "Send" [disabled]`).
    - expect: [observed] After filling the textarea with 'Hello world', the `disabled` attribute is removed from the Send button (confirmed via snapshot with no `[disabled]` marker).
    - expect: [inference] Per ChatInput.tsx, Send is disabled via `disabled={disabled || !value.trim()}`, so any whitespace-only input keeps Send disabled even though the boot-disabled window has passed.
    - expect: [verification condition] Test must assert Send is enabled (not just present/visible) immediately before clicking it, and must not attempt to click while it still carries the disabled attribute — clicking a disabled native button is a no-op in real browsers but some drivers silently succeed on stale disabled elements, so an explicit enabled-state assertion is required to catch regressions.
  3. Click Send and wait for the assistant reply to appear in the chat window before doing anything else (do not reload yet).
    - expect: [observed] With the default 'Funny mode' toggle checked, the assistant reply text appears in the chat window within roughly 120ms of clicking Send (both the user text and a generated funny reply were visible in the very next snapshot after the click).
    - expect: [observed] The instant the assistant reply text is visible in the DOM, `localStorage.getItem('ai-assistant-chat-history-v1')` already contains a JSON array with an entry whose userContent/assistantContent match the sent exchange — verified directly via `browser_evaluate` reading localStorage right after the reply rendered, with no artificial delay added.
    - expect: [inference] In ChatWindow.tsx's `handleSend`, `recordSuccessfulExchange(...)` (which synchronously calls `upsertExchanges` → `localStorage.setItem`) executes synchronously, before the `finally { setLoading(false) }` block, on every success/fallback code path (Funny mode, Assistant-mode success, and Assistant-mode local fallback). There is no `await` between recording the exchange and the point where `loading` flips back to false, so there is no test-observable window (via clicks/snapshots) where the UI shows the reply/loading=false but localStorage is not yet written.
    - expect: [verification condition] The test must not reload the page immediately on clicking Send. It must first wait for a positive signal that the exchange was recorded — e.g. wait for the assistant reply message element to become visible, or wait for the Send button/textarea to return to a non-disabled 'ready' state — before navigating away or reloading. Reloading while `loading` is still true (before the reply appears) is a genuine race that could result in the exchange being missing from history after reload.
    - expect: [limitation] Only the Funny-mode timing path (an artificial 120ms `setTimeout`) was directly observed. The Assistant-mode real-network path calls `sendChatMessage` against the intentionally-down localhost:3001 backend and falls back locally on failure; its exact timing/disabled-window was not separately measured in this session, though the same synchronous-recording argument above applies to it per source inspection.
  4. Navigate to /history (via the 'Message history' nav link or direct URL).
    - expect: [observed] Heading role 'heading' at level 2 named 'Message history' is present (confirmed in snapshot), followed by paragraph text 'Conversations are saved in this browser (your messages and assistant replies), grouped by day.'.
    - expect: [observed] The sent exchange appears grouped under a level-3 heading with the formatted date (e.g. 'Saturday, September 12, 2026'), inside a `list` containing one `listitem` per exchange. Each listitem's content is composed of plain, unnamed `generic` (div) nodes: a timestamp span, then the literal text 'You', the user message text, the literal text 'Assistant', and the assistant reply text — none of these carry an ARIA role beyond generic, and none carry a distinguishing accessible name.
    - expect: [observed] With 2 exchanges present (verified by sending two separate messages), there are 2 sibling `listitem` elements, and the literal strings 'You' / 'Assistant' and even timestamps (e.g. '2:45 AM' for both, since sent in quick succession) are duplicated verbatim across listitems.
    - expect: [observed] Direct DOM inspection confirms no `data-testid` (or any other unique attribute) exists on `.history-day__item` (`<li>`), `.history-exchange__role`, or `.history-exchange__text` elements — the only class hooks are shared across all items.
    - expect: [verification condition] Because 'You'/'Assistant' labels and the day heading text are NOT unique once more than one exchange exists, a locator such as `page.getByText('You')` or a role-based locator matching the literal name 'You' WILL violate Playwright strict mode with 2+ exchanges in history. Tests must scope locators using the unique message content itself (e.g. `page.getByText('Hello world', { exact: true })`) or filter `.history-day__item` via `.filter({ hasText: <unique user or assistant text> })` rather than relying on the 'You'/'Assistant' role labels or timestamps alone.
    - expect: [inference] The day-grouping heading text is derived from `userTimestamp` via a local `Intl.DateTimeFormat`, so a message sent right at local midnight could in principle be grouped under a different calendar-day heading than a test author expects; this boundary condition was not exercised (would require clock manipulation) and is flagged as a [limitation] rather than verified.
  5. Perform a full page reload on /history (not an in-app SPA navigation) after the exchange is confirmed present.
    - expect: [observed] After `page.reload()`, the same `listitem`(s) with identical content (user text, assistant text, timestamp) are still present — confirmed by counting `.history-day__item`/testid elements before and after reload and by re-inspecting the snapshot, with values unchanged.
    - expect: [inference] Persistence works because `ChatHistoryProvider` initializes React state via `useState(() => loadExchanges())`, which synchronously reads `localStorage` on every fresh mount; `readRaw()` in chatHistoryStorage.ts wraps `JSON.parse` in try/catch and filters entries with `isExchange()`, silently returning `[]` on any parse error or malformed entries rather than throwing.
    - expect: [verification condition] A test asserting persistence must trigger an actual full navigation/reload (e.g. Playwright's `page.reload()` or a fresh `page.goto()` to the same URL), not merely re-render via client-side router, to genuinely exercise the read-from-localStorage-on-mount path.
    - expect: [limitation] Did not attempt to inject corrupted/malformed JSON into the `ai-assistant-chat-history-v1` localStorage key to verify the try/catch fallback live; that resilience claim is [inference] from source only, not observed in this session.
  6. With at least one exchange present, click the 'Delete history' button (data-testid=delete-history-button).
    - expect: [observed] Clicking the button triggers a native browser `confirm()` dialog (not a custom in-page modal), with the exact message: "Delete all message history stored in this browser? This cannot be undone." — confirmed via the automation tool's modal-state capture showing `["confirm" dialog with message "Delete all message history stored in this browser? This cannot be undone."]`.
    - expect: [verification condition] Because this is a real blocking native dialog, a Playwright test MUST attach its dialog handler (`page.on('dialog', ...)` or equivalent) before or in the same synchronous turn as the click that opens it; without a handler registered in time, Playwright will hang/timeout on the triggering click. The handler must call `dialog.accept()` to proceed with deletion or `dialog.dismiss()` to cancel — relying on default OS/browser auto-dismiss behavior is not safe to assume.
    - expect: [observed] Accepting the dialog (`accept: true`) with at least one exchange present clears the list: after acceptance, the page shows the paragraph 'No history yet. Send a message in Chat to build your archive.' and the Delete history button gains the `disabled` attribute.
    - expect: [observed] Dismissing the dialog (`accept: false`) instead leaves history unchanged: after dismissal (tested with 2 exchanges present), both listitems remained, with identical content to before the click — confirmed via snapshot comparison immediately after `browser_handle_dialog` with `accept:false`.
    - expect: [observed] When `exchanges.length === 0` (fresh/empty history), the Delete history button already renders with the `disabled` attribute, so it cannot be clicked at all and no dialog is ever triggered — confirmed both on initial fresh navigation to /history with no data, and immediately after an accepted deletion.
    - expect: [verification condition] A test verifying the 'clearing history removes it' half of Scenario A-S2 must (a) confirm the exchange is visible on /history before deleting, (b) register the dialog handler, (c) accept the dialog, and (d) then assert BOTH that the specific message content is gone from the DOM AND that the Delete history button is disabled again / the empty-state message ('No history yet. Send a message in Chat to build your archive.') is shown — checking only one of these could pass on a partial-failure regression (e.g. UI clears visually but localStorage key is not actually removed, or vice versa).
