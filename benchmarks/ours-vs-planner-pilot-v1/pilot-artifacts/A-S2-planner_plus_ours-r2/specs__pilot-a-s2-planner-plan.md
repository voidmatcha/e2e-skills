# A-S2 Plan Hardening Deltas

## Application Overview

This is an AUXILIARY PLAN-HARDENING addendum for the single frozen scenario A-S2 (client-side chat history persistence and clearing) on the Playwright Chat Lab app at http://localhost:5174. It does not introduce new scenarios; it hardens the one existing scenario with additional acceptance criteria, guards, and locator evidence gathered by live exploration.

## Test Scenarios

### 1. A-S2 Hardening Deltas

**Seed:** `e2e/seed.spec.ts`

#### 1.1. A-S2: Send a message, reload, verify persistence in history, then clear history

**File:** `e2e/a-s2-chat-history-persistence.spec.ts`

**Steps:**
  1. [observed] Navigate to http://localhost:5174/ on a fresh profile with empty localStorage. Precondition guard: assert chat screen shows paragraph 'No messages yet.' (role: paragraph, exact text, observed live) and the Send button (testid 'send-button', accessible name 'Send') is in the disabled state before any text is typed.
    - expect: Chat screen is in its documented empty state before the test begins; if this guard fails, the storage was not actually empty and the test must abort rather than silently reusing stale data.
  2. [observed] Click the chat textbox (role: textbox, accessible name 'Type a message…', testid 'chat-input') and type a unique message string that embeds a run-specific token (e.g. timestamp or UUID) rather than a static literal, to avoid collisions with any residual data across retries.
    - expect: [verification condition] The Send button (testid 'send-button') transitions from disabled to enabled only once the textbox has non-empty content — observed live: it was disabled with empty input and became enabled ([ref=e29] had no 'disabled' state) immediately after `fill()`. If Send remains disabled/clickable-but-inert after typing, that is a failure condition distinct from persistence failure and should be asserted separately before proceeding.
  3. [observed] Click Send (testid 'send-button').
    - expect: [observed] The user message and an assistant reply both render in the chat transcript synchronously (no network round trip observed via browser_network_requests — only pre-existing failing GET calls to http://localhost:3001/api/messages occurred at initial page load, not on send). [verification condition] The test must NOT assert the exact assistant reply text as a hardcoded literal: two separate sends in this session produced two different assistant strings ('Historians agree: the first bug was a literal beetle with opinions.' and 'Socks in the dryer are off-chain NFTs with zero provenance.') for the same 'Funny mode' toggle state, confirming assistant replies are drawn from a randomized pool. Only assert that an assistant reply container is present and non-empty, keyed off the fixed 'Assistant' label, not its content.
  4. [observed] Inspect localStorage key 'ai-assistant-chat-history-v1' via page.evaluate immediately after send.
    - expect: [observed] The key contains a JSON array with one object: {id, userContent, assistantContent, userTimestamp, assistantTimestamp}. userContent exactly equals the typed message. [verification condition] This low-level storage check is an optional extra guard layered on top of the UI assertion (per instructions the caller may choose UI-only checks) but if used, must key off userContent equality, not id (id is a freshly generated UUID composite and not stable/predictable), and must NOT assert assistantContent verbatim (randomized, see above).
  5. [observed] Navigate to http://localhost:5174/history (link role, accessible name 'Message history', href '/history').
    - expect: [observed] Page shows heading level 2 'Message history', a 'Delete history' button (testid 'delete-history-button', accessible name 'Delete history', observed enabled/not-disabled when at least one entry exists), a day-group heading (role heading level 3, text pattern 'Weekday, Month D, YYYY' e.g. observed 'Friday, September 11, 2026'), and a list (role list) containing one listitem with: a time label (role generic, text pattern like '10:00 PM' — [verification condition] do not assert the exact clock string since it is derived from wall-clock time and will differ per run/timezone; assert only that a time-like string is present, or better, assert this via testid/structure only, not a hardcoded value), a 'You' label followed by the exact user message text, and an 'Assistant' label followed by non-empty text.
  6. [observed] Call page.reload() (true reload, verified distinct from a same-URL goto) while still on /history.
    - expect: [observed] After reload, localStorage key 'ai-assistant-chat-history-v1' is unchanged (verified byte-identical JSON before/after reload in this session) and the UI re-renders the same single listitem with the same userContent and assistantContent as before reload. This is the core persistence assertion for the scenario's 'Then' clause. [verification condition] The test must wait for the history list/listitem to be visible after reload before asserting (settled-state gate) rather than asserting immediately post-navigation, since this is a client-rendered SPA route (React) and content is not present in initial HTML.
  7. [observed][limitation] Separately, and only as a documented pitfall (not part of the required assertion path): reloading the Chat screen itself (route '/') resets its live transcript to 'No messages yet.' even though the corresponding entry remains present under /history. This was observed live: after sending 'Second persistence check' and navigating away and back to '/', the transcript pane showed 'No messages yet.' while /history still listed the exchange.
    - expect: [verification condition] The test MUST perform its reload-and-check-persistence assertion on the /history route (or via localStorage), not on the Chat route, or it will produce a false failure. This is a hardening guard against a plausible but incorrect test design, not a product bug to fix.
  8. [observed] Click 'Delete history' (testid 'delete-history-button'). A native browser confirm() dialog appears with message exactly: 'Delete all message history stored in this browser? This cannot be undone.'
    - expect: [verification condition] The test MUST register a dialog handler (Playwright page.on('dialog') / browser_handle_dialog equivalent) BEFORE or synchronously with the click, or the test will hang waiting on the native dialog. This is a required read/write guard, confirmed live (the click paused the page and reported 'Modal state: confirm dialog ... can be handled by browser_handle_dialog').
  9. [observed] Negative guard: dismiss (cancel) the confirm dialog instead of accepting it, on a session that has one history entry.
    - expect: [observed] Dismissing the dialog leaves localStorage 'ai-assistant-chat-history-v1' and the rendered listitem completely unchanged (verified live: JSON string identical before and after dismiss, listitem still rendered). [verification condition] The plan should include this as an explicit negative-path check: clearing must be gated on dialog acceptance, and a naive click-only test (without dialog acceptance) must NOT be mistaken for a passing 'clear' assertion.
  10. [observed] Accept the confirm dialog.
    - expect: [observed] After acceptance: localStorage key 'ai-assistant-chat-history-v1' becomes null (evaluated live, returned null), the day-group heading and list disappear entirely, a paragraph with exact text 'No history yet. Send a message in Chat to build your archive.' appears, and the 'Delete history' button itself becomes disabled (observed live: [disabled] state on testid 'delete-history-button' with no remaining history). [verification condition] The test's 'clearing removes it' assertion should check for the disappearance of the specific listitem/text (or the empty-state paragraph appearing) rather than merely the absence of the day heading, since an app defect could theoretically leave stale text elsewhere; check both the positive empty-state message and the absence of the previously-asserted user message text.
  11. [observed] Isolation guard: before and after the accepted delete, enumerate all localStorage keys.
    - expect: [observed] Only two keys exist in this app's storage: 'ai-assistant-chat-history-v1' and 'chat-lab:theme'. Deleting history removes only the former; 'chat-lab:theme' persists unchanged across the delete. [verification condition] If the caller adds any storage-level assertions, they should confirm the delete action is scoped to the chat-history key only and does not clear unrelated app state (e.g. theme preference), guarding against an overly broad 'clear all storage' implementation regression.
  12. [observed] General settled-state / timing gate applicable to every step above.
    - expect: [verification condition] Because this is a client-rendered SPA (React, Vite dev server) with route changes handled client-side, every navigation (goto '/', goto '/history', reload) must be followed by waiting for the expected role/text-based locator to be visible rather than a fixed sleep, before making assertions. This is inferred from the app's behavior (client-side routing, empty-state text swapping) observed across the session, not from reading source code.
  13. [limitation] Pre-existing unrelated failing network calls.
    - expect: [observed] Two GET requests to http://localhost:3001/api/messages fail with ERR_CONNECTION_REFUSED on every initial load of '/' (observed via browser_network_requests and console events on two separate navigations to '/'). [verification condition] The test must NOT assert 'no console errors' or 'no failed network requests' as a blanket check, since this failure is pre-existing, off-origin, and explicitly out of scope per task instructions; any error-monitoring assertion must be scoped to exclude requests whose origin is not http://localhost:5174.
