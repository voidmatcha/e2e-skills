# Thin rules, a scanner gate and a CLI-first workflow over the official generator: generator-thin-eval-v1

Status: PREREGISTERED, NOT RUN, NOT FROZEN. This is an offline-built successor of [Codex v3](../generator-multimodel-v3-codex/README.md). The binding [protocol](protocol.json) and runner specify the experiment before new results. Development observations motivate the treatments and proposed practical margins; no successor campaign outcomes exist or were used to tune them. No freeze has been created. Existing campaign inputs remain untouched.

The owner’s 2026-10-15 direction is to test whether the official Playwright generator plus compact rules and a scanner-only gate captures most of the full reviewer’s benefit at a small fraction of its cost. Supplied independent development analysis attributes about 56% of an example reviewer pass to loading reviewer skill/reference text, with roughly 25–28k newly loaded text tokens per pass; reviewer calls account for about 58–59% of generation-plus-review dollars in the analyzed Claude runs. The deterministic scanner itself uses no model tokens; its command and returned output still consume model context. These are reported attribution estimates from finished development runs, not causal proof or expected effects for this experiment. Earlier observations suggested robust strong-model official outputs, higher full-skill cost, and differences in selectors and readability. [Provenance](../generator-thin-layer-v1/PROVENANCE.md) distinguishes these observations from checked source instructions.

**Revision r3 of 2026-10-16 (protocol id `generator-thin-eval-v1-r3`, replaces the r2 freeze).** The r2 freeze (workers 2) was run through harness-check and preflight for both roster models and its first canary CRASHED after one completed gpt-6-sol cell with `AttributeError: module 'generator_codex_auth_helpers' has no attribute 'clean_env'`. No scored cell was run and the canary produced no verdict. The campaign was archived whole (`~/Documents/e2e-skills-bench/evidence-2026-10-15/archived-invalid/thin-eval-v1-r2-canary-import-race`: output directory, freeze, pipeline script and log; never edited or resumed). Diagnosis: a lazy-import race that only two cells in flight can hit. The frozen shared adapter's `helpers()` registers the auth-helper module in `sys.modules` before executing it, so the second cell received the half-initialised module; a two-thread offline reproduction against a slow stub shows the same failure, and serial runs and the r1 canary (cells ran apart) never hit it. It is not a model, judge or scoring defect. Fix: `warm_lazy_modules` loads that module once on the main thread before the dispatch shims and the pool exist, and refuses to start the queue unless every attribute the cells read is present; the frozen shared and v3 files are not edited and serial behaviour is unchanged. An audit of every module the runner imports found no other lazy initialisation on the cell path (the rest load once at import, are per-thread through the dispatch shims, or are thread-safe). The change was made after observing the crash, so it is disclosed as a post-observation infrastructure repair; it changes no score, metric, threshold, arm, schedule, pin or the r2 judge repair. Restart: a new freeze (the r2 `freeze.json` was moved to the archive; the output directory is the new `~/.cache/e2e-skills-bench/thin-eval-v1-r3`), then harness-check, preflight and a NEW canary for every roster model. It was written after observing the canary 1 rollouts, so it is disclosed as a post-observation judge repair, checked against all twelve archived rollouts (all judge complete with the guard verified) and by mutation. ## Outcome-blind roster

The roster has one to three models; stage 1 recommends two. The default rule, **first-finished**, walks the frozen v3 declared model order and takes the first K models (K=2 recommended, K=1 minimum) whose v3 campaign has a freeze-bound admission and all 24 arm-C cells with process observations. An excluded model is skipped and recorded; an undecided or unfinished model ends the walk, so no later model is taken ahead of it. Only declared order and completion enter the choice. No clean, survival, fault, selector, scanner, cost, arm-C count or thin-arm value is used, and the roster is fixed at freeze. The expected outcome is `gpt-6-sol` and `gpt-6-astra` if both finish and are admitted in v3; that is an expectation, not a selection.

The stricter v3 ranking rule is retained for a later three-model stage: it ranks the six v3 Codex candidates by arm-C delivered count, then treated-core count, then total C_STEPS hits (denominators 24 cells and 168 step opportunities), with the v3 order breaking ties, and requires every candidate to have a final admission or exclusion, so it needs the whole v3 campaign. Only delivery/process fields enter; clean/refactor/fault results, findings and cost never do. Parent-stream C process observations miss actions performed only by children, an inherited limitation.

Both automatic rules refuse a partial campaign: every selected model needs complete report/results with all 24 C cells and available process observations. They record raw source digests and the chosen order in the new freeze. This build does not open the running v3 output directory or choose a roster.

The owner may supply `--models MODEL1 [MODEL2 [MODEL3]] --override-reason REASON` before freeze. The models must be unique v3 catalog members. Override selection is explicitly labeled; it is never described as the algorithm’s outcome. The frozen roster cannot be changed or replenished after outcomes are seen. A third model, optional arms or the full ranked roster belong to a separate later freeze.

One model has no between-model variation and the minimum exact sign-flip p is 1; two models give 0.5; three give 0.25. Stage 1 is therefore a go/no-go screen for spending a later stage, not a roster-level result.

It is not scheduled, not part of scheduled-cell spend, not randomized with this campaign’s arms, was run at another time under the v3 harness, and carries the label cross-campaign descriptive in every report. It is allowed only when all of these hold, and a failure refuses the freeze (or the summary attachment) rather than substituting anything:

## Metrics and analysis

Predeclared descriptive comparisons are D−A (thin layer helps) and E−D (scanner gate helps), both within the campaign; F−A (the CLI-first workflow against the official agent as it is); F−D (the surface effect with the thin rules held constant: does the CLI surface match the MCP surface in quality, and at what token cost; not a pure surface effect, see the comparability caveat below); F−E (indirect: E differs from F in both surface and scanner gate, so the contrast is confounded and reported without a threshold); and G−F (the scanner effect on the CLI surface), G−E (**G vs E**: the product paths, CLI against official agents, at an equal scanner gate) and G−A (**G vs A**: the CLI plus scanner product path against the official agent as it is); E−B (cheap gate versus full reviewer), only when B is scheduled; and C−E (full skill beyond the cheap stack), cross-campaign descriptive by default. Report the original v3 selector/refactor 2×2 table on clean cells, unknown selector status, dynamic hints, clean-conditional survival and unconditional refactor_score. This headline measures largely whether specs depend on changed id/class tokens. It is not a broad proof of maintainability. The original removed-token scan can match literals that are not selectors and can miss dynamic construction; the independent static counts are diagnostics alongside it.

Reuse v3’s task-within-model averaging, equal model weighting, pooled report, exact model sign flips, crossed model/task bootstrap, lineage profiles and leave-one-model-out (degenerate with one or two models; reported, not interpreted). Run primary, ITT, upper, load-clean and as-treated views. Complete models need at least six deliveries in each compared arm and five common tasks to enter a contrast. Every exclusion is reported. Missing metric observations are omitted and their task/model coverage remains visible.

A, D and E share the same successor official-tool classifier; F and G have none (see below). It preserves v3’s disclosed secondary-evidence fallback when primary rollout evidence is missing, but rejects explicit transcript/root identity conflicts before any parent MCP, artifact or message fallback. Only descendants linked to a verified root supply rollout tool activity or child costs; conflicting or unrelated identities make accounting incomplete. Hard evidence is still required for entry. D/E’s additional parent layer-read indicators and E’s scanner-command indicator are shown separately and gate their as-treated views; E commands may come from completed parent shell calls or identity-verified descendant rollouts with returned outputs. Messages, unreturned requests, unrelated descendants and identity conflicts cannot supply the scanner indicator; a command mentioning the path is not proof that its output was consumed, that scanning succeeded or that findings were fixed. Child-only thin-rule reads and missing scanner rollouts can be missed. B retains the v3 reviewed-official-output, reviewer-read and scanner-run definition. C’s as-treated definition remains the v3 skill/reference/scanner core. Every model’s raw untruncated compliance, fidelity details and tokens are retained in results and summary. Treatment-selected views are descriptive, not randomized causal estimates.

**Exploration depth beside the fidelity class.** The official-tool class proves the generator surface was touched, not that the exploration loop ran: in the v3 mid-run check one arm-A cell made 7 setup and 7 write calls with no click, type, navigate or snapshot and still counted as official-tool. Each A, D and E cell therefore also reports its completed `browser_*` calls on the playwright-test server from the root rollout and verified descendants, split into acting tools (click, drag, evaluate, file upload, dialog, hover, navigate, press key, select, type) and observing tools (snapshot, wait, verify), plus the `generator_setup_page`, `generator_read_log` and `generator_write_test` counts. Without a root rollout the parent stream gives only a lower bound, and a zero is then reported as unknown, never as no exploration. The summary counts cells with zero browser interactions per arm and keeps incomplete cells separate. The class and its thresholds are unchanged and no gate uses the counts.

**Fidelity of F and G: CLI exploration observed.** There is no official-tool class for F or G. The class is `cli-observed` when the untruncated root command stream shows, in one named session and in command order, a verified `open`, a verified guard probe (an `eval` fetch of `http://127.0.0.1:9/`) followed by a verified `requests` whose output shows `net::ERR_BLOCKED_BY_CLIENT` for that origin, a verified `goto` of an exploration origin (a loopback http origin other than the refused port 9; the model picks its own free port, so the origin cannot be pinned) and then a verified `snapshot`; `unverified` when specs were delivered without that proof; `blocked` when nothing was delivered; `aborted` for infrastructure outcomes. The shell command is tokenized (including `bash -c` wrappers): a call counts only when `playwright cli` or `playwright-cli` is the executable at a command position, so a command that only mentions the CLI (a quoted `echo`, `grep` or `printf` argument, a `cat` of the guide, a path such as `.playwright-cli/`) is not an invocation, and `--help`, `-h` and `help` are not either. A verified call has exit code 0 (an unknown code is unverified), is not masked (`|| true`, `|| :`, `; echo ...`, a pipe or `&` after it hide the CLI's exit code; a last call or one followed solely by `&&` keeps it) and returned no CLI error banner. The guard is checked, not assumed: the browser containment is enforced by the model following the guide, so the per-cell `guard_verified` flag (probe eval then `requests` in the same session showing the blocked origin) is required for `cli-observed` and counted in `summary.fidelity.F.guard_verified`; it shows the probe was blocked, not that every later request stayed inside the allowlist. Commands are read untruncated, so long compound commands are not cut. The class never encodes exploration depth: per cell the record also holds counts of CLI verbs split into acting (goto, click, fill, type, press, select, check, hover, drag, upload, reload, eval, ...), observing (snapshot, console, ...) and session commands (open, close, requests), the number of failed commands, the number of guard-probe evals and a zero-exploration flag (a session that only opened, probed the guard and closed explored nothing); a missing stream is unavailable, never a zero. F and G as-treated additionally require the parent read indicator for the thin rules (G also the scanner-command indicator); a CLI-guide read indicator and the guide’s integrity are reported and gate the F decision. The verb vocabulary was read from the 24 stored arm-C cells, and the offline tests run the extractor on those stored transcripts when they are on the machine. The rollout-derived child-agent count of every generation-arm cell is recorded; F and G declare none, and a cell with a child agent or an unknown child count is reported and blocks the F decision rather than being hidden.

Static secondaries count literal id/class selectors including attribute equivalents, positional locator calls, toHaveClass calls, complete generic numbered titles, tests per file and vacuous assertions from delivered specs. Counts include justified positional uses; no rule is suppressed to improve a score. The lexical helper ignores comments and quoted/regex bodies, reports unresolved selector calls and preserves missing files as unavailable. It cannot resolve arbitrary helpers, aliases or dynamic code. Summary reports per-file/per-cell records and per-arm/view totals with observed-file denominators and tests-per-file distributions. Pooled conditional metrics retain model/task/arm observed-repetition counts. Count tables and distributions are not an AST or semantic verdict, and one-test files can be reasonable for unrelated screens. There is no post-hoc composite hygiene score.

Cost reports tokens per arm using successor-validated parent plus persisted descendant usage read from rollouts, every attempt once, cached/uncached/output components, quality per 100k tokens and time per cell/survivor. Every token and cost number, including planning and desk estimates, comes from root plus verified child rollouts; the parent-only usage in `final.json` is never an input, and a cell without rollouts is incomplete rather than parent-only. Report quality metrics beside processed-token denominators and the predeclared survivors per 100k processed tokens; ratios are descriptive and do not combine metrics into a post-hoc quality score. Each scheduled A/C/D/E pipeline contains only itself. When B is scheduled, its pipeline includes the matched A generation plus its reviewer pass, including both calls’ descendants and attempts; show reviewer-only cost separately. A appears as its own treatment and in B’s pipeline for comparison, but is not charged twice in the scheduled-cell spend total (`scheduled_cell_spend`); harness and admission calls and the arm C reference are excluded. A durable per-model attempt journal preserves spent infrastructure calls when the inherited runner drops retryable rows on resume. Proven never-launched B skips are rechecked on resume without adding a spent attempt; if A recovers, the replacement reviewer call and every actual attempt are retained once. An interrupted call with no returned usage adds an unknown attempt, making cost/time incomplete rather than free. Incomplete tokens are counted and excluded from ratios. Elapsed reporting includes observed and unknown cell counts and a completeness flag. Any missing required time leaves the all-cell mean and seconds per survivor unavailable; observed sums and means have separately labeled denominators. The rules occupy 1,883 bytes, approximately 471 tokens; the prompt line adds 95 bytes, approximately 24 tokens. The 495-token budget uses `ceil(bytes/4)` separately and is an estimate. Actual reads, repeated context and child copies are already in measured input; **never add this estimate again**. No price lookup or dollar-cost estimate is performed.

## Predeclared decisions and power

“Cheap stack sufficient (development point rule)” requires a three-model roster that finishes, arm B scheduled, arm C re-run or a valid v3 reference, and E at most 0.10 below both B and C on selector hygiene, clean-conditional survival, unconditional survival, clean pass and effective fault kill in both primary and ITT pooled point estimates. Mean model E/B and E/C processed-token ratios must each be at most 0.80, and both cached-inclusive ratios below 1. All B/C/E pipeline costs must be complete, including A’s contribution to B. Require observations for every decision metric in all six tasks per arm/model, at least 18/24 official-tool A/D/E cells, 18/24 treated B cells (when scheduled), 18/24 treated-core C, 18/24 D/E read indicators, 18/24 E scanner-run indicators, at least 18/24 jointly qualifying D cells (official-tool plus layer-read) and E cells (official-tool plus layer-read plus scanner-run), intact staged rules/scanner bytes and known selector status on clean cells. Missing evidence gives “inconclusive”; adequate data missing a threshold gives “cheap stack not demonstrated sufficient.” Neither implies the full skill or reviewer is necessary.

**Stage-1 screen.** With one or two models, or without B, the same thresholds are applied to each available comparator and reported as comparator screens. A comparator that misses a threshold with adequate evidence gives “cheap stack not demonstrated sufficient.” If every available comparator passes, the statement is “inconclusive: stage-1 screen met” and names what was not run; the sufficiency sentence is never issued from a partial design. An E-versus-C screen against the v3 reference is labeled cross-campaign descriptive.

**CLI-first decision (pre-declared, development point rule).** The decision statement is fixed before any result: *the CLI-first thin workflow is adopted as the default path when, against MCP delegation, its quality is the same or better and its tokens are fewer or equal.* Operationally (`decision.cli_first` in the protocol, `cli_first_decision` in the runner): (1) the pooled F−A and F−D point differences are at least −0.10 on selector hygiene, clean-conditional survival, unconditional refactor survival, clean pass and effective fault kill, in both the primary and the ITT view; (2) the mean model F/A and F/D processed-token ratios are at most **1.10** and the cached-inclusive ratios at most **1.10** (see the token rule below; not the 0.80 saving required of the cheap stack against B and C); (3) the setup-failure hard gate holds (below) and at least 18 of 24 F cells per model are `cli-observed`, jointly treated, carry the rules-read and CLI-guide-read indicators and intact rules and guide integrity; (4) F cells show no child agent and have complete pipeline tokens; (5) the A and D comparators have at least 18 of 24 official-tool cells each; (6) selector status is known on every clean cell and delivered specs are available; (7) three models finish. G (a default arm since the pre-freeze revision, so always scheduled) is screened against E and against A the same way (G−E and G−A), met only when both pass; that screen is computed separately with its own reasons and reported as the independent `g_screen` field: only the evidence of F, A and D gates the F sentence, and G or E problems or a failed G screen never change it. **Token rule.** The bound is 1.10 (a stated 10% margin, replacing the earlier 1.00 “fewer or equal”) and applies to two ratios separately, both of which must hold: the **processed** ratio (uncached input plus output; **cached input is not counted**) and the **cached-inclusive** ratio (input plus output as the CLI reports it; **cached input is counted**). Tokens are root plus verified descendants. The stricter 0.80 saving of E against B and C is unchanged.

**Setup-failure hard gate.** For F and G, per model, user-visible setup failures (the stop clause `partial_or_blocked` fired, or `open` was attempted and never verified) must be at most 10% of the arm's cells (at most 2 of 24). A cell that never attempted `open` is a fidelity failure, not a launch failure; an aborted cell or a missing stream is unknown and makes the gate unknown (inconclusive), never a pass.

**Non-ceiling endpoints (first class).** The five quality metrics were at or near ceiling in development runs, so the summary also reports, per arm and derived offline from transcripts and rollouts: CLI launch failure rate, setup failure rate, stop-clause cells, zero-snapshot cells, mean wall time, root tool rounds (a parent-stream count; `codex exec` reports one turn, so a turn count would carry nothing) and tokens by role (root and child, processed and cached). The fraction of delivered-spec locators present in an observed snapshot is **pending**: derivable in principle by matching spec locators to the CLI snapshot text, but the extractor is not built, and the field is null.

**Shipping mapping (pre-registered, decoupled from the adoption sentence).** The adoption sentence above still requires three models. The shipping decision of the router (3.0.0) is separate and may use stage 1 (two models). If (a) the F and G setup failure rate is at most 10% per model and the CLI fidelity gates pass, and (b) no pooled point deficit of at least 0.20 on any of the five metrics, in the primary or ITT view, of either product path (E, G) against the comparators A, D, E and G with adequate evidence, then 3.0.0 ships thin with the routing **official agents if present, else CLI** and **no quality claim**. If (a) fails, 3.0.0 ships detection routing with the **ask for CLI or snapshots** default. If (a) holds and (b) fails the mapping says `hold` (owner decision; detection routing is the conservative default); missing evidence is `inconclusive`. Limitation: every arm receives an approved plan and a seed, so planning from a raw request is **not measured**, and auth-gated and page-object-model repositories are **not measured**; remote targets, interactive questions and official-agent presence detection are not measured either.

**F canary (before the full stage, per roster model).** Six F cells per roster model (the first two tasks of repetition 1's seeded order, three repetitions) run first. Any anomaly (an aborted cell, a non-`cli-observed` class, an unverified guard, a setup failure, zero snapshots, a fired stop clause, a child agent, unread rules or guide, no deliverable, incomplete tokens, retries, changed integrity, or a grid that is not exactly the six cells) stops it: archive the canary as invalid, fix the cause, and restart as a new protocol version. A frozen campaign is never patched. Canary cells are **extra spend** (6 F cells per model; the plan reports it under `canary` and `with_canary`), are archived as non-data, and the same six cells are **re-run inside the full grid**, which keeps 24 cells per arm per model. `canary_plan` and `canary_verdict` are the offline definition and verdict; the live wiring is `canary --output OUT --allow-live`, run after freeze, harness-check and preflight and before drive: it takes the machine lock and the disk floor, runs the six F cells of each admitted model through the same `run_model` path into its own archived non-data directory `OUT/_canary/<model>/`, evaluates `canary_verdict`, and prints PROCEED (exit 0) or STOP (exit 3, with `INVALID.json` and the archive / fix / new-version instruction). A canary is never resumed, `canary` refuses when any `OUT/<model>/final.json` exists, and **`drive` fails closed** unless `OUT/_canary/verdict.json` says proceed for the same freeze, covers exactly the admitted models and no `INVALID.json` exists. It is unit-tested with stubs only and has not run live; the inherited harness has no free-memory floor (the container is capped at 4g), and none is added.

**F−D comparability caveat.** F minus D bundles more than the exploration surface. D delegates to the official generator child, which writes through `generator_write_test`; F writes the specs itself with ordinary file edits. D's prompt is the shared frame, A's delegation line and the rules line; F replaces both with its own line, which also tells the model to stop with status `partial_or_blocked` when the CLI session cannot be opened, a clause D's prompt does not have (D is not rewritten). Cells that stopped under that clause are reported separately (`summary.fidelity.F.blocked_by_stop_clause`, per-cell `stop_clause_blocked`) apart from the fidelity classes. A small F−D difference cannot be attributed to the CLI surface alone; the protocol records the same caveat in `decision.cli_first.comparability_caveat`. **Margin and minimum detectable effect.** The quality margin is 0.10. The descriptive 80% grid MDE of a pairwise contrast is 0.20 for two or three models at baselines .5 and .7 (0.25 for one model, .20 at baseline .7 with full fidelity; unattainable at .9), and there is no inferential MDE. So “better” is said only at a pooled gain of at least +0.20 on all five metrics in both views; between −0.10 and +0.20 the wording is “same within the screen”, which is not evidence of equivalence, and the 0.10 margin is smaller than the 0.20 MDE. Statements: “CLI-first thin workflow adopted as default path (development point rule)” (all of the above, three models); “CLI-first thin workflow not demonstrated at least as good as MCP delegation” (adequate evidence, a threshold missed against A or D); “inconclusive: CLI-first stage-1 screen met against the evaluated comparators” (one or two models, thresholds met; the adoption sentence is never issued from fewer than three models); “inconclusive” (missing coverage, process, integrity, child-count or cost evidence). The cheap-stack statement above is unchanged and independent; both are reported side by side in `summary`.

Report D−A and E−D gains and whether they reach 0.10 without a superiority verdict. Report E−B (when run) and C−E with all metric denominators and token ratios. If C−E exceeds 0.10 on selector hygiene or clean-conditional survival in both primary and ITT, the owner may describe a development signal for the full skill after checking delivery and fidelity. If A already matches E, an E tie with B/C is not evidence that the thin layer or scanner helped. The full necessity statement remains an interpretation of published effects, not an automatic label.

The 0.10 quality margin and 20% token saving are proposed practical screening thresholds for owner review before freeze. They are not validated product-risk limits. With one to three model clusters the minimum exact two-sided sign-flip p is 1, 0.5 or 0.25: **no finite effect is detectable at α=.05 with this test**. The bootstrap spread under-covers with so few clusters; no equivalence or statistical noninferiority claim is supported.

The deterministic [offline simulation](power-simulation.json) records one-, two- and three-model designs with six tasks and four repetitions (default arms A, D, E, F, G, 120 cells per model). Its pairwise marginal simulation uses shared task/model logit variation, baselines .5/.7/.9 and fidelity 1/.75; it applies separately to D−A, E−D, E−B, C−E, F−A, F−D, F−E, G−F and G−E, rather than jointly simulating all arms. The scenario numerics are unchanged by the arm additions (they are pairwise and arm-agnostic; the regenerated artifact reproduces the earlier numerics exactly) and only the descriptive arm, cell-count and comparison metadata changed. For a 0.10 descriptive point-gain trigger at baseline .7 and full fidelity, the chance-trigger rate under no true gain is .0715, .139 and .2165 for three, two and one model, and the trigger probability at a true .10 gain is .4705, .522 and .4935. The 80% grid MDE is .20 for two and three models at baselines .5/.7 and unattainable on the feasible .9 grid; for one model it is .25 except .20 at baseline .7 with full fidelity. The same draws estimate the descriptive probability that a rival-minus-E deficit is at most .10: .9285 (three), .861 (two) and .7835 (one) when equal, and .5295, .478 and .5065 when the true deficit is .10. These are point-rule sensitivities, not inferential power or noninferiority evidence. They omit B’s reuse of A, shared-arm contrast dependence, the time gap and harness difference of the cross-campaign C reference, joint multi-metric primary/ITT sufficiency, outcome-dependent dropout and unknown token-cost variability. A small observed tie remains unresolved.

## Generation-phase repairs (arms A, D, E, F and G)

Both repairs live in the successor-owned runner and staging; no frozen v1 or v3 file changes. Arms F and G use the same staged generation config; there is no MCP server process to receive the exploration-port variable, and the shipped-text guide has no port instruction: the model starts `webServer.command` as written on the configured baseURL (the default port) and stops it in step 6. For F and G, exploration and the test run are therefore sequential on the same default port P (not on separate ports as for the MCP arms, whose exploration port is P+10000): fresh state depends on the model stopping the app in step 6, and a leftover app makes the test run (`reuseExistingServer` false) fail loudly rather than silently reuse state. For F and G the CLI’s `.playwright-cli/` directory (session state and snapshots under the project directory) takes the place of `.playwright-mcp/`: it is git-excluded before the baseline commit and listed from disk into `cli_artifact_writes`, never an out-of-scope write (sibling `cli_*` functions; the MCP-arm functions are untouched). B and C keep the v3 call path byte for byte (which keeps the C reference comparable), and the entry-rule calls keep the v3 generation config because admission depends on tool evidence, not on a passing test run.

**Shared-server state (finding F3).** In v3 the generation config sets `reuseExistingServer` true so the parent’s single test run can start while the MCP session holds the app server. The child’s browser exploration had mutated that server, so the run reused polluted state and 4 of 9 mid-run arm-A cells (all three v2-23 and one v2-06) self-reported a failing generation-time run (account already deleted, tags already existed). The repair splits ports by role. The staged generation config reads one environment variable, `GEN_EXPLORE_PORT`, which only the MCP server process receives through one extra `-c mcp_servers.playwright-test.env` entry. The MCP session explores on port P+10000 and may reuse its own server across setup calls. Every shell command, including the parent’s single run and any child test run, has no such variable: it uses the default port P with `reuseExistingServer` false, starts a fresh app process and cannot attach to the explored one. The app source gets the same variable for its listen port. A server the model starts itself on P makes the test run fail loudly rather than silently reuse state. Scoring is unchanged: it stages through the unmodified engine stage with the frozen configs (`reuseExistingServer` false, no variable), `scoring_guard` runs before and after scoring, and the deliverable is only `tests/`. Each cell records its isolation mode, both roles’ reuse values and port-normalized config and app digests; analysis refuses mixed or mislabeled isolation.

Offline proof: for every scheduled task the staged files resolve, under the explore environment and under no environment, to internally consistent but different ports, with reuse false in the test-run role; the argv carries exactly one extra MCP-only entry and none in the shell environment; the scoring files and case configs are byte-identical before and after; and seven in-memory mutations of the repair (shared reuse, no env entry, one app port, and others) each fail at least one test. The generated config evaluated under Node with the Playwright import stubbed gave port 9301 with reuse false unset and port 19301 with reuse true set, and every generated app parsed. These do not prove the live behavior: whether the MCP server process honors the per-server environment entry, whether repeated `generator_setup_page` calls reuse the explored server and whether the app listens on the explore port need a live smoke.

**Scoped writes (finding F5).** `.playwright-mcp/page-*.yml` snapshots were recorded as out-of-scope writes in 6 of 9 mid-run arm-A cells, and the `node_modules` link swapped inside the container showed as a modified tracked file that cost the agent investigation commands. `.git/info/exclude`, written before the baseline commit, lists `node_modules` and `.playwright-mcp/`, so neither is tracked nor listed by `git status` (checked once by hand with real git: a link swap and snapshot files left `git status` empty). The collector lists `.playwright-mcp/` files from disk into `mcp_artifact_writes` and keeps them out of `out_of_scope_writes`; they still count as secondary fidelity evidence exactly as before, without double counting. The link restore after the call is unchanged. Side effect: a model command such as `git clean -x` would also remove ignored paths, which the v3 tracked link did not expose; this is rare and visible in transcripts.

## Token ratio definition (pre-freeze revision)

The CLI-first token screen (`decision.cli_first`, bound 1.10 on the processed and the cached-inclusive ratio) uses the ratio of **task-standardized per-cell means** (usable = token-complete cells, equal task weights), the same definition as the improvement report, instead of a ratio of arm sums that is biased when two arms have different numbers of usable cells. It equals the old value on a balanced complete grid, the bound and every completeness gate are unchanged, a task with no usable cell leaves the ratio undefined, and the old sum ratio and a geometric mean of per-task ratios are reported as sensitivities only. See `CHANGES.md` (Token-ratio definition) for the reproduced distortion, the sources and the before/after definitions.

## Token completeness gate (pre-freeze revision)

A comparison needs at least 18 of an arm's 24 cells per model with a complete token record (the `decision.cli_first`, G screen and shipping gates). Fewer than 18 usable cells stays inconclusive and says "usable n of 24". Incomplete cells above the floor are excluded from the token ratios (never zero-filled or imputed) and their counts are printed beside the result (`token_completeness`, `statement_with_disclosure`, and every improvement sentence). The 1.10 bound, the quality margins and the undefined ratio for a task with no usable cell are unchanged. See `CHANGES.md` for the reason and the before and after rules.

## Improvement report (descriptive, pre-registered before the freeze)

`decision.improvement_report` fixes in advance when the report may print a sentence about a **cost** improvement of the CLI product paths. It is descriptive: it never feeds `decision.cli_first` or `decision.shipping`, and it is not a statistical test. The 1.10 token bound of `cli_first` only requires that a CLI arm is not more expensive; only this report may say it was lower.

- **Pairs and kinds.** F against A and D, and G against A, D and E. For each pair and model: the processed-token ratio, the cached-inclusive token ratio, the wall-seconds ratio, and the ratio of refactor survivors per 100k processed tokens (x over y, each arm's mean per usable cell so unequal usable-cell counts stay comparable; cells without a complete token record or an observed elapsed time are counted and left out, never zero-filled). Valid-cell counts per arm and model, and the setup success rate (CLI arms: one minus the user-visible setup failure rate; official arms: the share of cells whose official tools were observed), are printed beside every ratio.
- **Interval.** The pooled value is the unweighted mean of the per-model ratios. Its 95% interval is a task-clustered percentile bootstrap (tasks resampled with replacement, models too when there are several; the protocol seed and replicate count, standard library only). With one model it resamples the six tasks only and is a rough description.
- **When an improvement sentence is allowed.** Only if all hold: quality is not shown worse than the existing -0.10 margin on all five thin metrics in the primary and ITT views; at least 18 cells with the needed record per arm and model; the setup gate passed for the pair's CLI arm; and the interval upper bound is below 1.0 (tokens, seconds) or the lower bound is above 1.0 (survivors per 100k tokens). The sentence is then "lower measured cost". Otherwise the only sentence is "cost improvement not demonstrated" (Korean: 비용 개선은 입증되지 않았다) with the point estimate and the interval.
- **Wording limits.** Every sentence ends with the stage tag (development stage, N models, 6 synthetic tasks). No sentence says or implies better quality; a phrase guard refuses the report if one appears. "No MCP setup is needed" is stated from the design and the canary observation, not as an evaluation result.
- **Queue priority: none.** Putting the comparison arms (A, F, G) ahead of D and E in the cell queue was considered and rejected: arms are interleaved per task in catalog order precisely so that no contrast is confounded with time of day, load or rate-limit drift, and a priority order would do that to every contrast that includes D or E (F-D, G-D, G-E, E-D). The cell counts and the repetition structure are unchanged.

## Cell concurrency (optional, pre-registered at freeze)

`workers` is 1 (serial, the default and the baseline) or 2. It is chosen when the campaign is frozen (`freeze --workers 2`), written into `freeze.json` and carried by every report; a report whose `workers` differs from the freeze is rejected. Models still run one after the other and the machine-wide lock still refuses a second driver; only the cells of one model overlap. `canary` uses the same value, so a canary run with `workers = 2` is the check that two concurrent cells behave like serial ones before `drive` starts.

- **Serial path unchanged.** With `workers = 1` the frozen v1 loop runs exactly as before. The new code only runs for `workers = 2`.
- **Queue.** Cells are taken in the frozen schedule order, so two workers always run neighbouring schedule cells; the pre-registered arm and time-of-day interleaving is unchanged. After the first failure (an exception, the usage-limit stop, the three-in-a-row infrastructure stop, a disk or swap stop) no new cell starts; the cell already running finishes and is recorded, then the failure is raised. Optional arm B waits for its arm A cell.
- **Why shims.** The frozen v1 runner and the successor integration patch module globals per cell (`engine.call_model`, `engine.stage`, `compat.command`, the prompt line, the generation-staging log). Those cannot be made thread-safe in place, so for `workers = 2` the globals are replaced once by dispatch shims that read a per-thread hook set; a thread without hooks reaches the original function. A test runs every arm through the serial patch stack and through the shims and requires identical staged files, argv, prompt and record.
- **Swap guard.** Before each cell starts, the host swap (`sysctl -n vm.swapusage`) must be under 9 GiB (or under 85% when the swap file is at least 16 GiB). Otherwise the cell waits, polling every 30 seconds for at most two hours, and the wait is written to the report (`concurrency.swap_guard_events`). An unavailable probe is recorded once and does not block.
- **Known limits.** Two cells share the colima VM (4 CPUs, 6 GiB; each container is capped at 2 CPUs and 4 GiB), the Codex account (two sessions refresh the same ChatGPT token) and the host load that `wait_for_load` watches (pause threshold 12). Scoring stays serial after the generation phase. Interrupting the driver lets the running cells finish. The canary and the first cells are where these limits would show: a rise in infrastructure errors or timeouts against the serial baseline is an anomaly and stops the campaign like any other.
