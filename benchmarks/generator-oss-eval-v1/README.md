# Zeppelin OSS generator comparison: generator-oss-eval-v1

Status: PREREGISTERED, NOT RUN, NOT FROZEN; EXPOSED DESIGN, NOT A SEALED EVALUATION. This is a separate protocol from the [Codex successor](../generator-multimodel-v4-codex/README.md). This build creates an offline harness and synthetic tests; it makes no model call, starts no server or container, and creates no campaign freeze. The binding [protocol.json](protocol.json) specifies the design. Results may be appended below `## Results`; text above that heading is freeze-bound.

The six synthetic generator tasks reached a ceiling in a finished strong-model campaign: every arm scored 1.00 on every metric. This protocol therefore compares the same treatments on real Zeppelin screens. Ceiling motivation is not evidence that any arm will win on OSS tasks. The two development tasks are `zep-sidebar` and `zep-note-rename`, both from the same upstream PR. They cover sidebar state transitions and notebook-title editing/persistence. Neither is a random sample of projects or behaviors.

## Zeppelin ownership and cleanup

Exactly one campaign may use the shared instance at `127.0.0.1:18080`. A machine-global, nonblocking lock covers every live entry, drive, score and final-eval path, independent of output directory. A second driver or another matching benchmark process causes refusal. Different output roots do not authorize simultaneous campaigns.

Generation uses a dedicated instance of the loop proxy harness at `127.0.0.1:14210`, forwarding API/websocket traffic to 18080 and rewriting Origin to `http://127.0.0.1:14200`. Scoring reuses proxy port 14210 serially after the previous phase exits, serving one variant at a time. Container generation reaches `http://host.docker.internal:14210`; host scoring reaches `http://127.0.0.1:14210`. The scorer replaces only that exact URL literal in its scratch copy of delivered files, uniformly across the three clean runs, five defects and R1. Original artifacts are preserved, and this normalization changes no selector, assertion or test logic. Scoring refuses while any generation call is active. The OSS helper wraps the loop's unchanged serving harness with a private readiness endpoint. Before spawning, a bind probe refuses an occupied port without signalling its occupant. Readiness requires the owned child to remain alive and return its fresh token, requested variant and resolved distribution identity. A generic HTML response or a failed child cannot establish readiness. Shutdown targets only the owned child. This offline repair exercises these checks with mocks; it checks no listening port or process and touches no Zeppelin state.

Every cell receives a campaign/cell note namespace. Cleanup in `finally` deletes surviving notes in that namespace and its `~Trash` descendants after generation and each variant, including exceptions. It also deletes newly observed escaped note IDs belonging to that cell under exclusive ownership; it never deletes a preexisting foreign ID. Cleanup failure stops progress and remains in the record. Before/after snapshots record surviving escapes as cell violations, clean them by ID and continue; a scoring escape fails that run. Removal or path changes of preexisting foreign notes stop the campaign and preserve those foreign IDs. This is observation rather than prevention: transient escapes and edits to foreign note contents at the same path are unobservable. Generated specs must use the supplied namespace. The owner must decide whether strict prevention requires a stronger enforcing proxy before relying on that claim.

A new scoring attempt persists `STARTED` before runtime work and invalidates `scores.json`. A completed attempt with matching report/freeze digests is reused; an incomplete matching attempt resumes only its unscored cells, preserving saved adjudications. `scoring-attempts/<attempt-id>.json` retains completed or partial rows, the active cell and chained failure details, including cleanup/isolation failures. `scoring-attempt.json` identifies the latest attempt. An interruption or error leaves it `STARTED` or `INCOMPLETE`; analysis, attribution and summary require matching `COMPLETED` scores from that latest attempt. Retained successful `results.json` or scores from an older attempt cannot bypass this check. Legacy scores without an attempt record require a new authorized scoring attempt. `drive --model` limits work to that model. Completed model results with current report, scores and freeze digests are skipped.

## Metrics and cost

The primary metric stays refactor survival: a delivered suite must pass clean 3/3 and the behavior-preserving R1. Missing delivery, zero tests and any clean failure score zero. The summary labels it selector hygiene and also prints clean-conditional survival and the clean-cell selector/refactor 2x2. These Zeppelin refactors include tag/markup changes, so the metric covers more than renamed ids/classes. Static selector evidence has dynamic-selector blind spots and does not establish general robustness.

Other endpoints are clean 3/3, effective fault kill over D1-D5, scanner P0 and P1/P2 per cell, fidelity, and cost. A mutant failure is a valid kill only when it corresponds to that defect's declared behavioral criterion and the identical frozen suite passed clean. Infrastructure/setup failures and unrelated selector failures are not valid kills. Supply behavioral attribution through `score --adjudications <JSON-file>` or offline `analyze --adjudications <JSON-file>`: the map is `call_id -> defect_id -> boolean`. Preserve minimal failing-test title chains and attribution. Error messages are used transiently only for reference calibration and are not persisted in per-defect results. Automatic mutant failures without infrastructure errors yield candidate kill rate only. Each candidate needs true/false attribution; a noncandidate is a known miss. Any unadjudicated candidate makes effective fault kill null. Offline attribution uses saved scores and never reruns browser scoring.

Co-primary cost endpoints follow the imported Codex plan: refactor survivors per 100k processed tokens and pipeline seconds, read next to quality. Processed tokens are uncached input plus output, parent and children together; cached input is separate and included in a sensitivity ratio. Parent usage comes from its own root rollout with stream cross-check; descendant usage comes from persisted rollouts. B includes its A source and reviewer call. Every retry is included once. Missing source or per-attempt records make the denominator incomplete; count excluded cells explicitly. Ratios use sums of survivors and complete token totals, not the mean of individual ratios. Parent/child additivity remains a live check.

## Analysis and detectable differences

The contrasts are C minus A, B minus A and C minus B. Reuse the approved Codex pooled estimator: average repetitions within each model/task, take each model's unweighted task mean, then average models equally. Print exact model sign-flips, the 10,000-replicate crossed model/task bootstrap with seed 20261016, model/task profiles, lineage means and leave-one-model-out results. Primary, ITT and as-treated views report the primary metric; clean and effective fault kill also appear in the primary pooled view. Every pooled result says `development evidence`. DEV and heldout outputs remain separate; no Claude, historical fixture or DEV/EVAL pooling occurs.

The old five-of-six-task per-model directional rule cannot be satisfied on this two-task pool and is not inherited. No superiority, replication, release PASS/FAIL or cross-model directional verdict is issued. Report effect sizes and counts. Pooled eligibility requires both tasks represented in both arms, and every exclusion is visible. Exact model sign-flips require joint coordinate-wise sign invariance conditional on magnitudes; shared tasks and lineages can violate it. With six models the smallest attainable two-sided p is 0.03125; with four it is 0.125. These p-values and bootstrap intervals are descriptive, not calibrated inference about a task population.

Before observing data, a normal independent-Bernoulli approximation at two-sided alpha 0.05, power 0.80 and baseline 0.5 gives a difference scale of 0.5719 for 12 cells per arm/model and 0.2335 for 72 cells per arm across six models. The formula is `(1.959964 + 0.841621) * sqrt(0.5 / n)`. These optimistic scale markers are not certified minimum detectable effects: repetitions share tasks, lineages share models, fidelity selects cells, and ceiling probabilities change variance. The per-model scale is too large to interpret as a local detectable improvement from a 0.5 baseline. With only two DEV task clusters, both from one PR, a defensible population-task MDE is unavailable. Six repetitions improve within-task precision and do not add task clusters. A small, tied or null result cannot establish equivalence, general quality or transfer to other OSS work.
