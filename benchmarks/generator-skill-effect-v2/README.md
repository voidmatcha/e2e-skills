# Generator skill-effect v2: headroom-screened tasks (2026-10-06)

Status: **`INCONCLUSIVE` (thin pool): the headroom screen kept 3 of 24 tasks against a pre-stated minimum of 12, so under the frozen rule the final full / lean / no-skill comparison was not run.** The no-skill arm (`claude-sonnet-5-5`, tools, 48/48 calls, $3.34) delivered specs that were green on the correct app in 44 of 48 calls and killed **216 of the 220** seeded faults those 44 deliverables faced (98.2%); 20 tasks sat at a mean primary of 0.90 or above, one at 0.00 because of a fixture defect the screen itself exposed, and the three in-band tasks were there mostly because one of two deliverables failed on the correct app, not because faults went undetected. Twenty-four fresh, harder, brief-style tasks did not create fault-detection headroom for this model either; what varied was refactor survival (24 of 44 clean deliverables) and clean-run reliability (4 of 48 failed), which this protocol had preregistered only as secondaries.

## Why this experiment exists

[v1](../generator-skill-effect-v1/README.md) was `INCONCLUSIVE`: on ten criteria-listed single-page apps, `claude-sonnet-5-5` without the skill already killed 0.927 of the seeded faults, above the preregistered 0.90 ceiling, so no fault-detection lift could be seen. v2 keeps v1's staging, deterministic scoring and decision structure and changes what v1 got wrong: the tasks are user briefs on apps with multi-step flows, server persistence, ordering and error-recovery behavior rather than numbered checklists; headroom is measured on the model itself, by a no-skill-only screen, instead of being assumed from an author-written naive spec; the freeze happens after the model-free validation has completed, not before; and what each arm actually did (which skill files it read, whether it ran the tests, the scanner, a browser-exploration command, a repeat run or a subagent) is read deterministically from the Claude Code stream-json transcript instead of from the model's self-report.

## Design

**Pool.** Twenty-four new apps ([`cases/`](cases/)): a three-step checkout, a debounced catalog search, a comment thread with replies and a confirm dialog, tabbed settings with an unsaved-changes guard, slot booking with conflicts, a tag editor with a limit, an inbox with unread counts, a multi-page storefront with a wishlist, passwordless sign-in with lockout, a sortable table with URL state, bulk select and delete with undo, an expense tracker with blur validation, a kanban board with drag and drop and a WIP limit, checkout coupons, an address book with dependent selects, a quiz, notes with a trash, toast notifications, a profile with live initials, a reading list with load-more, a language switcher, an orders page with URL-synced filters, an account-deletion dialog, and an editor with server-side autosave. None reuses a v1 app, the archived counter fixture, the writescope-demo todo app, or any case of the skills' own evals or the debugger benchmarks. Each task is a brief of three to five sentences; each of its five seeded faults ([`truth/`](truth/)) carries a `brief_phrase` that `validate` checks appears verbatim in the brief, so every fault breaks something the brief states. Fault classes: one `surface` fault per task and four drawn from `persistence`, `ordering`, `recovery`, `precision`, `interaction`, `a11y` and `boundary`. Each task also has a behavior-preserving markup refactor and author strong/naive specs; `validate` requires the strong spec to be green twice, kill 5/5 and survive the refactor, and the naive spec to miss at least two faults (a sanity floor, not the headroom claim).

**Headroom screen.** Only the no-skill arm runs on the whole pool: two repetitions per task, shuffled with the screen seed. The pre-stated keep band is a mean no-skill primary in [0.40, 0.80]; at least 12 tasks are kept, with a pre-stated fallback (nearest to the band first, never a task at 0 or at or above 0.90). The kept set, the screen report digests and the spend are frozen into `protocol.json` before any skill-arm call. Screening repetitions are never reused as comparison data.

**Final comparison.** Kept tasks only, three arms, three fresh repetitions, a different seed, two workers, the same model (`claude-sonnet-5-5`, Claude Code 2.1.289), tools (`Read,Grep,Glob,Bash,Write,Edit,Agent`), prompt frame, pre-granted approvals and project staging as v1. The `full` arm is told to read and follow the working-tree `playwright-test-generator` skill, staged outside the project with the working-tree `e2e-reviewer` skill; the `no-skill` arm gets nothing else.

**Lean arm (added before the freeze).** v1's full-skill calls ended `PARTIAL/BLOCKED` 27 times out of 30, mostly because V2/V3 probes were skipped, the V6 separate-reviewer gate was unmet or exploration was replaced by reading the source, at 6.05 times the no-skill cost and with no measured fault-kill benefit. At the user's request a third arm, `lean`, runs [`arms/lean/SKILL.md`](arms/lean/SKILL.md): a benchmark-only text derived from the real skill by removing layers, never by adding advice. It keeps the project profile, the scenario minimum with one primary outcome and the error-cause signal, the three default secondary outcomes and the failed-write re-read rule, the selector priority and forbidden-pattern table, the await/web-first/one-hard-expect rules, per-test independence, a run-and-fix loop bounded at three mechanics-only attempts, and one `scan.sh` pass with P0/P1 fixes. It drops live exploration and its guards, the write-set snapshot, the approval ceremony and its tables, scenario admission bookkeeping and the Locator Mapping Table, the tracer protocol, V2 to V6 and the completion matrix (the `--repeat-each` run stays), the full e2e-reviewer Phase 2 review, Step 5b, the YAGNI audit, the POM template, network determinism, SSR, auth and branch-seeding sections, the safety preamble, Test Agents interop and imported cases. `protocol.json` lists the kept and removed layers; the real skill under `skills/` is untouched. The lean arm never runs on the screening pool.

**Scoring** is v1's: three clean runs on the correct app, one run per fault variant, one on the refactor, and the bundled scanner on the delivered files. **Primary metric: effective fault-kill rate** (faults killed / 5, counted 0 unless green 3/3); `full` versus `no-skill` on this metric alone decides the verdict. **Preregistered secondaries:** `lean` versus `no-skill` on the primary (same rule, its own PASS/FAIL); `lean` non-inferiority to `full` (lean's mean primary and mean refactor score each within 0.10 of full's, the paired bootstrap 95% CI lower bound of lean minus full on the primary above -0.10, clean-pass drop at most 0.05), with cost and time multiples reported plainly; and the **refactor survival score** (1 when green 3/3 and green on the refactor) for full versus no-skill and lean versus no-skill, each with its own paired lift, CI and PASS/FAIL. Process compliance per call, for all three arms: skill files read, app source read, `playwright test` runs, `--repeat-each` runs, `scan.sh` runs, browser-exploration commands, `git status` calls, Agent spawns, writes outside `tests/`.

**Decision rule** (frozen in [`protocol.json`](protocol.json)): `PASS` needs full minus no-skill paired lift >= +0.10, a case-cluster bootstrap 95% CI lower bound > 0, a full clean-pass rate not more than 0.05 below no-skill, and a kept-set no-skill primary below 0.90; `INCONCLUSIVE` on any unscored call, drift, spend-cap stop, incomplete schedule, or a kept-set baseline at or above the ceiling; otherwise `FAIL`. Spend cap $150 across both stages, $4 per call, 1500 s per call. Power: with 12 kept tasks and an assumed paired-difference SD of 0.30, each paired comparison has a minimum detectable lift of about 0.24 at 80% power; a true lift of 0.10 would usually go undetected, so `FAIL` means "no large effect shown", and the 0.10 non-inferiority margin sits inside the noise, so a non-inferiority `PASS` means "no large deficit shown", not "equivalent".

**Selection effect, stated in advance.** Keeping the tasks on which the no-skill arm scored low means its fresh repetitions regress upward toward the pool mean, which works against finding a lift and can push the kept-set baseline back over the ceiling; the kept set is also enriched for tasks whose behavior is ambiguous or flaky for this model. Both are reported, not corrected.

## Screen

The screen ran 2026-10-06T03:49Z to 07:16Z (UTC): 24 tasks, no-skill arm only, two repetitions, seed 20261006, two workers, Claude Code 2.1.290 (the CLI auto-updated from 2.1.289 between v1 and this freeze; the version is recorded in `protocol.json`), 48/48 calls, $3.34, no infrastructure error, no timeout, six load pauses honored (the runner waits while the 1-minute load average is above 12). Raw calls: [`reports/screen.json`](reports/screen.json); scores: [`reports/screen-scores.json`](reports/screen-scores.json); selection: [`reports/screening.json`](reports/screening.json) and `protocol.json` `screening` (frozen 07:16:56Z, before any full or lean call; none was ever made).

| Band | Tasks | Mean no-skill primary |
| --- | ---: | --- |
| Kept (0.40 to 0.80) | 3 | v2-03 comments 0.50, v2-07 inbox 0.80, v2-08 storefront 0.50 |
| Dropped, ceiling (>= 0.90) | 20 | 1.00 for 18 tasks; 0.90 for v2-17 trash and v2-18 toasts |
| Dropped, floor (0.00) | 1 | v2-02 debounced search |

The pre-stated fallback (nearest to the band, never a task at 0 or at or above 0.90) could add nothing, so 3 < 12 and the protocol stops here.

What the 48 no-skill deliverables did: 44 were green 3/3 on the correct app. Those 44 faced 220 seeded faults and killed 216: the four misses were `v2-07 f5` twice (the server also marks the neighbouring message read; visible only after a reload and only on another message's marker), `v2-17 f1` once and `v2-18 f3` once. By class, every `recovery`, `interaction`, `boundary`, `a11y` and `ordering` fault was killed; `persistence` 46/48, `precision` 62/63, `surface` 43/44. The two in-band tasks other than v2-07 scored 0.50 because one repetition was not green on the correct app, with a kill rate of 1.00 in the other. Refactor survival among the 44 clean deliverables was 24 (0.545), with every failure an `#id` or CSS locator on a renamed element. Process indicators from the transcripts: 33 of 48 calls ran `playwright test`, 23 ran `--repeat-each`, 31 read `app.mjs`, none used a browser-exploration command or spawned a subagent.

The four non-green deliverables are instructive and two of them are the author's fault, not the model's:

- `v2-02` (both repetitions): the model's test typed a short query, cleared the box and expected an empty list; a slow response for the short query then arrived and repopulated the list. The app's clear path does not advance the request serial, so the brief's own promise ("never leave results from an earlier, shorter query on screen") is violated by the fixture on that path. The strong author spec never hit it because it clears only after a fast six-letter query. This is a fixture defect found by the baseline; it is why the task sits at the floor.
- `v2-03` r1: the model posted a reply and immediately posted a sibling; the fixture's `form.reset()` after the awaited request cleared the sibling text mid-fill, so the post was rejected and the counter read `2 comments`. The same race was fixed in v1's guestbook by disabling inputs while a request is in flight; this app did not get that fix. Fixture defect.
- `v2-08` r1: a second browser context navigated to a hard-coded `http://127.0.0.1:<staging port>/wishlist`, so the spec fails on every other port. Test defect (the same shape as v1's `gen-06`).
- `v2-02` r2: as r1.

Neither fixture was changed after the freeze; the frozen bytes and scores stand, and the two defects are recorded here instead.

## Results

Not run. The frozen rule required at least 12 kept tasks before any full or lean call; 3 qualified, the pre-stated fallback added none, and the band was not relaxed after seeing the data. No `full` or `lean` call was made, so there is no lift, no non-inferiority result and no compliance table for those arms; the lean-versus-full question remains unanswered. Machine-readable verdict: [`reports/results.json`](reports/results.json).

Interpretation: author-written small apps with fault-kill rate as the primary metric give no headroom for `claude-sonnet-5-5` without the skill. Two protocols have now reached that ceiling, with checklists (v1) and with briefs on harder apps (v2): a tool-enabled model that reads the app source and runs its own tests verifies almost every stated behavior, including server persistence, ordering, recovery and accessibility details. The headroom-first redesign therefore did not produce a usable pool. No skill effect is claimed in either direction.

### Post-hoc descriptive (not decision data)

Computed after the screen outcome was known, from the 48 no-skill screen calls only, with v1's definitions (clean = green 3/3 on the correct app; kill rate given clean = faults killed / 5 averaged over clean deliverables; refactor survival given clean = share of clean deliverables green on the markup refactor; refactor score over all calls = 1 when clean and green on the refactor, else 0). It is not part of the frozen rule and no skill arm ran, so it cannot show a skill effect.

| Measure (no-skill, 48 calls) | Value |
| --- | --- |
| Clean 3/3 pass rate | 44/48 = 0.917 (0 flaky; the 4 failures are described above) |
| Mean effective kill (the primary) | 0.900 |
| Kill rate given clean | 0.982 (216/220) |
| Refactor survival given clean | 24/44 = 0.545 |
| Refactor score, all calls | 0.500 |
| Scanner hits on the 48 deliverables | 0 P0; 8 P1/P2 heuristic; 618 LLM-triage hints (not findings) |
| Process indicators | 33/48 ran `playwright test`, 23/48 ran `--repeat-each`, 31/48 read `app.mjs`, 5/48 ran `git status`, 0 ran the scanner, 0 used a browser-exploration command, 0 spawned a subagent, 0 wrote outside `tests/`; mean 5.0 tool calls |
| Cost and time | $3.34 total, $0.07 per call, 1662 s summed |

Markup-refactor survival is the one scored dimension where the no-skill arm shows room: 0.545 here, consistent with v1's 12/28 (0.429), against v1's 23/30 (0.767) with the skill, a descriptive difference that v1 could not test because it was not its primary. That motivates a v3 whose preregistered primary is refactor survival (with process compliance as a preregistered secondary), screened for headroom on that metric before any skill-arm call, on fixtures free of the two defects found here. It is a direction for a new protocol, not a result of this one.

## Limits

- **The `full` arm is a snapshot, not the live skill.** `arms/full/playwright-test-generator/` is a byte copy of `skills/playwright-test-generator` as released in 2.0.0 (taken 2026-10-06T03:00:38Z at commit 0c37f08, when that directory had no uncommitted edits), and `arms/shared/e2e-reviewer/` is the e2e-reviewer directory at the same moment including the user's then-uncommitted scanner and reference edits. All three arms and the scorer read only these snapshots; `selftest` proves it ([`reports/selftest.json`](reports/selftest.json)). The repository skill was scheduled to change after this freeze (fixes folded into 2.0.0 without a version bump), so a result here is about the snapshot bytes, not about whatever `skills/playwright-test-generator` contains when you read this.
- **The lean arm is a measurement variant, not a shippable skill.** It drops the safety preamble, the approval ceremony and the untrusted-content rules on purpose, because the benchmark projects are local and disposable by construction; nothing about it should be read as a proposal to ship a reduced skill.
- **How to read lean.** The lean text is the real skill's written rules without its process layers. If lean lands near full and both beat no-skill, the value measured here sits in the written rules; if full beats lean, the process layers (exploration, V2 to V6, independent review) add something the rules alone do not; if neither beats no-skill, this harness and task set cannot see the skill's value. The most informative outcome is lean well above no-skill and lean near full. Lean's compliance indicators (`--repeat-each` and `scan.sh` runs) are recorded like the other arms'.
- One host and model family; author-written apps with in-memory state. The screen selects on a single model's no-skill behavior, so the kept set says nothing about other models.
- Two fixtures (v2-02, v2-03) carry defects that the screen exposed after the freeze; they are documented above and were not repaired, because a frozen protocol is superseded, not edited. A successor must fix them before reuse.
- Faults are seeded one per brief phrase; this measures whether the delivered tests verify what the brief says, not fault prevalence in production suites.
- The skill is built for an interactive approval gate; the harness pre-grants approvals in the shared prompt, so headless skill behavior (skipped exploration, probes or scanner) is part of what is measured and is reported through the compliance indicators.
- A null result on these screened tasks does not show the skill is useless: it shows no measurable lift of this size on tasks this baseline already finds hard, under this harness.

## Reproduce

```bash
npm ci --prefix scripts/evals/fixtures
python3 scripts/evals/run-generator-skill-effect-v2.py validate --output /abs/validation.json
python3 scripts/evals/run-generator-skill-effect-v2.py freeze --stage pool --validation /abs/validation.json
python3 scripts/evals/run-generator-skill-effect-v2.py screen --output benchmarks/generator-skill-effect-v2/reports/screen.json --allow-live
python3 scripts/evals/run-generator-skill-effect-v2.py score benchmarks/generator-skill-effect-v2/reports/screen.json --output benchmarks/generator-skill-effect-v2/reports/screen-scores.json
python3 scripts/evals/run-generator-skill-effect-v2.py select --scores benchmarks/generator-skill-effect-v2/reports/screen-scores.json
python3 scripts/evals/run-generator-skill-effect-v2.py run --output benchmarks/generator-skill-effect-v2/reports/final.json --allow-live
python3 scripts/evals/run-generator-skill-effect-v2.py score benchmarks/generator-skill-effect-v2/reports/final.json --output benchmarks/generator-skill-effect-v2/reports/final-scores.json
python3 scripts/evals/run-generator-skill-effect-v2.py analyze benchmarks/generator-skill-effect-v2/reports/final-scores.json --output benchmarks/generator-skill-effect-v2/reports/final-results.json
```

`screen` and `run` refuse to start when any frozen digest has drifted or when the stage before them is not frozen; `select` refuses scores that did not come from a no-skill screen and exits non-zero when fewer than `min_kept` tasks qualify, which is where this protocol ended. The `run`, final `score` and `analyze` lines above are the preregistered procedure that was not reached. The delivered test files of every call are archived under `reports/*-artifacts/`, so `score` can be rerun without model calls. This protocol is spent; a rerun is a new version with new cases.
