# Reviewer release v1

**Status: `NOT_RUN` / `INCONCLUSIVE`. No accuracy, lift, or user-helpfulness result is claimed.**

**Decision: `PROCEED_WITH_INFRASTRUCTURE_ONLY`.** Build and validate the runner, scorer, custody schema, and attestation verifier, but do not begin a release run until the external custodian, sealed corpus commitment, preregistered signing key and verifier digest, clean committed evaluated tree, and isolated runner are all in place.

The protocol, bundle preflight, reference pre/post-run Ed25519 signature-and-file verifier, one-shot witness socket client and single-receipt verifier, operator-side witness-service reference code, development-only read/scan tool broker, Codex MCP bridge and offline transcript reconciler, one-call capture adapter and artifact assembler, response normalizer, post-run utility-ledger validator, and finding-level one-cell and full-matrix scorers are implemented. A candidate 1,080-call coordinator now connects the one-call adapter to the frozen schedule and online witness callbacks, but it has only offline synthetic schedule/refusal tests and cannot pass the current `FROZEN` admission gate. A candidate post-run bridge calls the trusted signature-and-file verifier and then reconciles all 1,080 raw transcripts; its Python wiring test uses a fake verifier result and is not signature evidence. The older opaque-token matrix scorer remains for regression diagnostics, but only the new finding-level matrix scorer counts extra false findings and computes finding precision, recall, and F1. Every local scorer remains `INCONCLUSIVE` for the frozen release decision. A verified isolated release executor, independently deployed witness and key custody, release-grade completeness and provenance verifier, external corpus, and independent human adjudication operation are not implemented or available. A successful preflight or development score cannot produce or imply a release benchmark result.

Reviewer release v1 is a from-scratch, preregistered benchmark for deciding whether `e2e-reviewer` has release-grade value beyond an otherwise identical model invocation. It does not reuse the public reviewer holdouts or any independent-product-review packet from v1-v10.

The machine-readable contract is [`scripts/evals/reviewer-release-v1-protocol.json`](../../scripts/evals/reviewer-release-v1-protocol.json). If this README and that file differ, the JSON protocol controls.

The [independent operator handoff](OPERATOR_HANDOFF.md) names the separate custodial, adjudication, witness, and executor work still required before a release run. It is explicitly marked not ready for corpus transfer or model dispatch.

### Pre-execution schema amendment

On 2026-09-23, before any release-v1 model call or external corpus admission, the protocol was amended from SHA-256 `bf1d89e7d1050c897997e41886bb110ef6776adf22a0e7393bf527d34f0fdbf4`. The original bundle could record only a pattern and severity, while the advertised gates require an adjudicated source location and a way to count extra false findings. The amendment adds a fixed response/normalization contract and requires positive labels and both pre-run human votes to name accepted source-line locations. It also requires the independent pre-run reviewers to certify that no unlisted scoring-valid finding remains in a case; otherwise the scorer could misclassify a legitimate second finding as a false positive. The validator binds the final label to the frozen case and resolved votes. A further pre-execution design pass specified the agent-workflow treatment and replaced the incompatible single-file corpus row with a bounded, hashed multi-file case root. The single attestation contract was also split: a pre-run isolation attestation cannot bind future raw outputs, judge ledgers, or scores, so a separate post-run attestation must bind those artifacts and the pre-run attestation. The signed corpus commitment was then bound to the actual bundle corpus, labels, pre-run adjudications, and custody ledger bytes; post-run input/output inventories were specified to cover all 1,080 call keys and their declared artifact bytes. No release calls occurred between these changes. The 120-case allocation, three arms, repetition schedule, statistical tests, and decision thresholds did not change; the validator checks the exact statistics and decision values against the pre-amendment contract. This is a disclosed pre-execution contract repair, not a measured result or permission to run before the remaining prerequisites are met.

The same pre-execution repair now binds `response_manifest` in the post-run signature and specifies the per-call `transcript_report` format and offline byte reconciliation. It also requires each staged case manifest and MCP session header to agree with the signed corpus case. These additions close gaps between a signed file inventory, the case actually exposed through the tool broker, and the response rows used for scoring; they do not attest that a trusted isolated executor produced the bytes.

Before any release call, the post-run contract was also made explicit about the signed score: resolve the signed adjudication ledger against the signed response manifest, recompute the finding-level matrix result from the signed corpus and labels, and reject a `scorer_output` whose JSON differs. This binds the arithmetic to the signed evidence; it cannot prove that judges were independent or that the online witness actually observed the model run.

Before any release call, the previously underspecified “SHA-256 seeded per-case arm order” was fixed to `sha256_v1_per_case_repetition_order`. Sort the 120 committed, UTF-8-encodable case IDs in ascending UTF-8 byte order; for each case run repetitions 1, 2, 3; within each repetition sort the three arms by ascending SHA-256 of the compact UTF-8 JSON array `["reviewer-release-v1", case_id, repetition, arm]` (no spaces, no ASCII escaping), breaking an equal digest by arm ID. This fixes call order before the sealed corpus is revealed. It changes no case allocation, arm, threshold, or statistical unit. The local planner computes these keys but still does not execute models or attest external isolation.

The Go reference attestation verifier now uses the protocol's exact compact UTF-8 JSON bytes for this rank. Go's default JSON encoder escapes `U+2028` and `U+2029` even when HTML escaping is disabled, whereas the Python planner's `ensure_ascii=False` leaves them as UTF-8; the old Go implementation therefore ordered at least one legal case ID differently. A Python-vs-Go vector test first reproduced the mismatch, and both sides now pin those characters, literal backslash escapes, controls, and HTML punctuation. This is a pre-execution verifier repair, not a change to the frozen ordering rule or any release result.

The same verifier now has a single-receipt mode that checks an Ed25519 signature against a supplied public key and the SHA-256 of the exact expected event payload before a coordinator continues. It rejects mismatched payloads, keys, signatures, non-events, and symlinked receipt files. The release coordinator must use an independently preregistered key and pinned verifier binary; neither exists here yet. A reference operator-side witness service is implemented in the same Go source tree: it verifies the signed pre-run commitment, independently hashes the fixed per-call artifacts, enforces the frozen 2,160-event schedule, and syncs its private create-only journal before acknowledging each receipt. Offline tests use disposable keys. No independently operated signer, key-custody evidence, or online timing proof has been connected to the one-call adapter, so this remains infrastructure rather than release evidence.

The one-call development adapter now sends the already frozen prompt bytes directly through nonblocking stdin instead of reopening its `prompt.txt` artifact at launch. Offline tests cover a prompt larger than a pipe buffer, a child that writes a full output pipe before reading stdin, and a child that closes stdin early. Preparation, launch, and finalization are separate callable boundaries: an optional begin acknowledgement runs after input freezing and before `Popen`, and an optional end acknowledgement runs after all five output artifacts are written. The adapter rechecks the four signed-input candidates and the runner's case, protocol, and prompt source files around those boundaries, and writes a create-only attempt marker before launch. Offline negative tests reject a refused acknowledgement, changed bytes, and a second launch within the same artifact directory. A fresh one-call Codex development smoke on a public synthetic two-file case returned `CAPTURED_UNATTESTED` with a reconciled `complete_development_trace_only` report. No independent witness is connected, the marker does not prevent a retry under a different artifact directory, and the adapter remains unusable as a release executor.

Before any release call, each scheduled invocation also has one attempt and a 600-second wall timeout. A timeout or interruption makes the release run `INCONCLUSIVE`; it cannot be replaced by a fresh call under the same case/arm/repetition key. These limits prevent post-observation retries from selecting favorable output. They are execution rules, not an observed model-performance result, and do not alter the 1,080-call schedule or numeric outcome thresholds.

The same pre-execution amendment changed the effective unstable-cell decision rule. The former “any invalid or unstable result fails the arm” wording contradicted the registered `0.10` unstable-case ceiling and left no scoring treatment for those cells. A malformed but completely captured model response now cannot vote toward a majority; if two other valid responses agree, their lowest-numbered matching repetition is selected. Otherwise the case-arm cell stays in the 120-case denominator as incorrect and unhelpful, with no invented finding (and one false negative for a positive case). Two blinded judges must inspect all three raw repetitions for an unstable cell, record separate harmful/fabricated flags against each raw hash, and use the same tie-break rule on the derived any-harmful/any-fabricated cell flags. The numeric gates are unchanged, but the effective decision rule changed before any release call; the protocol declares `outcome_thresholds_changed: true` rather than hiding that relaxation.

Before any release call, the shared strict-JSON adapter was specified as an exact common prompt. It gives every arm the same minimal 24-entry ID/title/severity index, pinned by its SHA-256 in the protocol, because the scorer requires those output codes; withholding their meaning from `no-skill` would confound defect detection with code-name guessing. `no-skill` is therefore a schema-only control with no pattern contracts, skill workflow, or scanner. `catalog-only` adds detailed pattern contracts, and `full` adds the skill workflow and bundled scanner. This is a conservative test of the added skill behavior, not a claim that the control saw no taxonomy information.

Before any release call, the common index was changed to bare IDs, its digest was re-pinned, and the shared prompt now states the exact output form. The first full-arm attempt also showed that `SKILL.md` names references as `references/...` while the broker accepted only fully qualified paths; the broker now maps only allowlisted relative reference names to their declared staged files. The successful full-arm development call satisfied the required case read and scanner checks and reconciled seven MCP calls. These transient local smoke outputs are not a retained or independently adjudicated benchmark corpus; no correctness, specificity, or skill-lift conclusion follows from them.

The development smoke now optionally retains owner-only raw traces under ignored `testbed/` with `--artifact-dir <new-absolute-testbed-path>`. It writes a file-hash manifest only after a successful reconciled call; `--replay-artifact-dir <path>` rehashes every file and reconciles the saved prompt, Codex JSONL, MCP journal, final response, and normalized output without a model call. On 2026-09-24, one synthetic `test.only` case was run and replayed in all three arms at `testbed/reviewer-release-exact-smoke-20260924/`: `no-skill` and `catalog-only` each had one MCP call; `full` had eight, including the required source read and scanner call. This private, locally mutable development record helps reproduce executor behavior but is neither signed nor independently held. It must not enter the release corpus, the scored 1,080-call matrix, or any skill-effectiveness claim.

The signed `evaluated_skill` artifact is a strict JSON snapshot of the exact skill and scanner file SHA-256 maps. The pre-run verifier rejects missing, extra, or malformed entries and rehashes the matching bundle files. The post-run call inventory must also carry a strict staged-skill manifest: exact arm-specific skill and scanner file hashes, plus base64 of the initial reference bytes. The offline reconciler checks those hashes against the signed evaluated-skill snapshot and MCP session header, then recomputes each complete prompt from the signed common template, signed case, and decoded initial material. Merely sharing a common prefix, or signing an arbitrary treatment suffix, is insufficient. This is a byte-consistency check; the separate release executor and custody attestation remain necessary to establish who staged and used those bytes. The pre-run signer must independently confirm that the bundle files came from the clean committed evaluated tree before signing; matching bundle hashes alone do not prove that origin.

Each signed-inventory `runner_config` is strict JSON identifying the frozen primary host/model, a runner version at or above the protocol floor, and `runner_default_no_overrides` decoding. The offline matrix reconciler requires one exact runner version across all 1,080 calls. These declarations check paired comparability of recorded inputs; only independent executor provenance can prove that the declared binary and settings were actually used.

For every call, the reconciled model-visible tool trace must include a successful read of **every** source file in the signed case, not merely one read from a multi-file root. The `full` arm must additionally invoke the frozen bundled scanner. Otherwise the call is incomplete and cannot enter the accuracy matrix. This checks observable coverage, not whether the model reasoned correctly about what it read.

## What is being measured

### Treatment surface is designed, not executable yet

The shipped reviewer starts from `SKILL.md`, reads references at their phase boundaries, and runs the bundled scanner. The public v7 holdout instead embedded seven skill files into each `full` prompt and disabled every model tool, so it measured a useful instruction-material ablation, not the installed workflow or scanner. The reviewer entrypoint has already been trimmed from about 67 KB to about 15 KB; the archived exploratory trim rerun and the counted v7 run are both public-development evidence, not a controlled release comparison of a further compact variant.

Release v1 now specifies a read-only agent review workflow. Every arm gets the same case bytes, task, minimal output-code index, and strict-JSON response adapter, with read-only staged-case access. `full` additionally sees `SKILL.md` in its initial prompt, may read its named references on demand, and may run only the frozen bundled scanner. Its scanner uses deterministic Tier 3 only, with project ESLint, external AST tools and downloads disabled; an incomplete scan invalidates the call. `catalog-only` additionally sees the detailed pattern reference; `no-skill` receives no treatment-specific reference. Skill-file reads and scanner access are the treatment, not hidden common assistance. Only declared hashed files are staged; target-controlled code, project configs and package scripts cannot execute. Network, browser, writes and subagents are off. Each call must bind the initial prompt, every model-visible file read, ordered tool arguments/results, and raw final response to its attestation. The JSON adapter makes native Markdown reporting fidelity explicitly out of scope.

The development-only broker now copies exactly the declared case files into a private workspace, rechecks their hashes on reads and scanner calls, stages only the arm's allowed skill material, and permits the bundled scanner only for `full` with Tier 3 and fixed flags. Adversarial tests exercise path traversal, undeclared files, mutation, symlinks, and cross-arm tool denial. A small MCP bridge exposes the broker's arm-specific tools and rejects undeclared methods or tool names; an offline end-to-end test exercises real staged source reads and a Playwright scanner hit through that bridge. The bridge writes a create-only, hash-chained local journal of its session header, MCP wire requests/responses, and broker tool results; offline checks reject truncation, mutation, and model-visible tool errors. A separate offline reconciler compares that journal with supplied raw `codex exec --json` events, initial-prompt bytes, and the final-message file. It rejects missing terminal events, unexpected tool types, arm/tool mismatches, and MCP responses that differ from recorded broker bytes. Codex may terminate a STDIO server without closing its input; in that case the reconciler accepts an otherwise complete journal ending after a delivered reply only when a successful terminal Codex turn and every exact tool call/result match it. On 2026-09-23, the opt-in `python3 scripts/evals/smoke-reviewer-release-codex-mcp-v1.py --arm <arm>` development smoke exercised real Codex CLI `gpt-5.6-sol` calls for all three arms: `full` completed a staged-file read and bundled scanner call, while `catalog-only` and `no-skill` each completed a staged-file read. Every call matched its local journal and final-message file. These are arm-specific plumbing prompts, not identical task prompts or a paired accuracy experiment. Neither component authenticates where those bytes came from: the journal's self-hash can be recomputed by anyone with write access, and the smoke is not an isolated release executor. MCP tool filtering alone does not restrict a model process's other built-in tools, sign a complete per-call transcript, or establish external custody. The protocol therefore remains `DESIGNED_NOT_IMPLEMENTED`, and the validator still rejects a premature `FROZEN` state. No extra dieting or prompt-only result can substitute for that work or for external custody and adjudication.

Each case now declares a unique source root and 1–64 hashed source files beneath it, with at most 1 MiB per file and 4 MiB per case. Pre-run accepted locations must name a line in one of those files; the release preflight checks the actual hashes and line counts. This replaces the earlier single-file case shape, which could not represent the scope or scanner input needed by the specified workflow. The development-only matrix scorer accepts the same multi-file shape but does not itself rehash source bytes or establish release evidence.

The benchmark measures three distinct outcomes on the same 120 unique cases:

1. **Finding accuracy:** whether the response identifies the adjudicated E2E defect without inventing findings in clean code.
2. **Skill lift:** whether the full skill improves case-level correctness over a same-host, same-model, same-case no-skill invocation. Catalog-only is a diagnostic middle arm, not the primary baseline.
3. **User helpfulness:** whether a blinded maintainer could safely act on the response: the finding is correctly located and explained, the proposed repair addresses the cause, and the validation advice would distinguish the repair from the original failure mode.

It does not estimate defect prevalence, developer time saved, production incident reduction, generator quality, or performance on frameworks other than Playwright and Cypress.

## Frozen corpus design

An external custodian supplies 120 previously undisclosed, unique cases after the evaluated skill and protocol are frozen. The cells are exactly balanced:

| Framework | Positive | Clean | Total |
| --- | ---: | ---: | ---: |
| Playwright | 30 | 30 | 60 |
| Cypress | 30 | 30 | 60 |
| **Total** | **60** | **60** | **120** |

A positive case contains one primary adjudicated finding. A clean case contains no in-scope finding. Near-duplicate source, shared defect lineage, paired mutants, or multiple excerpts from one upstream test count as one cluster and cannot cross train/evaluation or positive/clean boundaries. Repository, author, and project identifiers are blinded before model execution.

Coverage is also frozen: each of the 24 stable reviewer patterns must have at least two positive opportunities and at least two distinct clean or near-miss guard opportunities. No source repository may contribute more than two of the 120 cases, and each P0/P1/P2 severity stratum must contain at least ten positive cases. One case may expose only its single primary positive label for scoring; coverage opportunities do not create extra labels or enlarge the denominator.

Every case is run in three arms:

- `full`: the frozen complete `e2e-reviewer` skill;
- `catalog-only`: only the frozen 24-pattern catalog and severity definitions, without workflow, verification, or response instructions;
- `no-skill`: the same task prompt and minimal output-code index, without detailed pattern contracts, skill workflow, or scanner.

All three arms use the same runner family, model, decoding settings, case bytes, and common task prompt; the treatment-only initial reference bytes differ by design. Arm order is deterministically hash-ordered for each case and repetition as specified above. There are three fresh-workspace repetitions per case and arm. Repetitions measure stability; they are never counted as 360 independent cases.

The amended response format is one strict JSON object with a `findings` array. Each finding carries a pattern ID, severity, source-relative file and line, causal explanation, repair, and discriminating validation advice. Normalization sorts and deduplicates finding identities without erasing the original prose; a response with the correct primary finding plus an invented second finding must contribute one true positive and one false positive. A majority-stable identity set selects the lowest-numbered matching repetition for blinded helpfulness review. The pre-run oracle supplies accepted file-line locations within the hashed case source. The implemented response normalizer preserves raw prose and separately canonicalizes finding identities. The post-run validator checks the 1,080-response manifest and binds 360 blinded utility ledger cells either to a majority-selected raw hash or to all three raw hashes of an unstable cell. The finding-level matrix scorer includes those unstable cells in the fixed case denominators, aggregates exact finding counts and paired statistics, and rejects disagreement with the resolved utility decisions. Its gate arithmetic is diagnostic only. None of these outputs prove judge identity, custody, or isolation; a release-grade verifier and independent adjudication still remain.

The primary release matrix has one frozen cell:

| Host | Model | Minimum runner version |
| --- | --- | --- |
| Codex | `gpt-5.6-sol` | `codex-cli 0.152.0` |

The schedule is exactly `120 cases x 3 arms x 3 repetitions = 1,080 model calls`. The primary cell must pass every absolute and paired gate. Host, model, or minimum version cannot be supplied as an untrusted runtime override. A Claude Opus or Fable run may be registered later as an optional replication, but cannot contribute to, replace, or rescue the primary gate. Any result claim is specific to Codex + `gpt-5.6-sol`; it is not a cross-model or cross-host accuracy claim.

## Blinded adjudication

Adjudication has two separate passes. Before any model call, two independent humans create the reference oracle without seeing a model output, the case author's candidate label, or each other's decision. After model execution, responses are anonymized and order-randomized; two humans score correctness and helpfulness with the resolved oracle visible but without knowing the arm or model identity. Disagreements in either pass go to a third tie-breaker. Adjudicators must disclose project and benchmark conflicts; anyone who authored a case, skill change, or evaluated response is excluded from that case.

The final oracle, adjudication ledger, exclusions, and tie-break decisions are published after the run. Inter-rater agreement is reported but is not used to replace resolved labels.

## Preregistered release gates

Each case contributes one case-arm decision. A 2-of-3 agreement among valid normalized predictions is stable, even if the third response is invalid; three different valid predictions or fewer than two matching valid predictions is unstable. Unstable cells count as incorrect and unhelpful rather than disappearing from the denominator. Their rate is separately capped at `0.10`.

The `full` arm must satisfy every absolute gate:

- precision at least `0.95`;
- recall at least `0.90`;
- F1 at least `0.925`;
- false-positive rate on clean cases at most `0.05`;
- recall at least `0.85` in each framework;
- macro-averaged recall across the 24 patterns at least `0.85`, with recall at least `0.50` for every individual pattern;
- recall at least `0.90` for every preregistered severity stratum;
- unstable-case rate at most `0.10`;
- helpful-response rate at least `0.85` across all cases and at least `0.80` separately for Playwright, Cypress, positive, and clean strata;
- harmful-response rate at most `0.02` overall, with zero fabricated destructive or security-sensitive actions.

The primary paired lift comparison is `full` versus `no-skill` on the 120 unique cases. It must satisfy all of:

- case-correctness lift at least `0.10` (12 cases);
- the two-sided exact McNemar test rejects equal paired error rates at `p < 0.05` in favor of `full`;
- the case-stratified 95% bootstrap confidence interval lower bound for lift is greater than `0`;
- helpful-response-rate lift is at least `0.10`, with a case-stratified 95% bootstrap confidence interval lower bound greater than `0`;
- `full` is not more than `0.02` worse than `no-skill` in any framework or label stratum for either correctness or helpfulness.

`catalog-only` is reported using the same metrics and paired analyses, but it does not replace or relax the primary `full` versus `no-skill` gate. No threshold is rounded into a pass; exact rational counts are evaluated before display rounding. Missing, malformed, mutated, or non-independent evidence is an automatic `INCONCLUSIVE`, never a pass.

## Release evidence boundary

A local or public-corpus execution is development evidence only. A release verdict requires all of:

1. external sealed-corpus custody, with the custodian's corpus commitment signed before execution and the corpus revealed only inside the isolated runner;
2. a pre-run signed isolation attestation binding the protocol, evaluated skill, corpus commitment, runner image, model identity, and isolation policy before any model call;
3. a post-run signed result attestation binding the pre-run attestation plus every input, raw output, adjudication ledger, and scorer output.

Both attestations must verify against a preregistered Ed25519 public key using a trusted verifier whose SHA-256 digest is also frozen in the protocol; code supplied inside the evidence bundle is never executed as a verifier. Every bound artifact's SHA-256 digest is checked. The evaluated skill must come from a clean committed tree, not a dirty working copy. The custodian and benchmark operator must be independent of the skill authors. A wrapper name, local path, model string, or unsigned provenance record is not isolation proof. If signature verification, digest verification, custody independence, or any required report fails, the only permitted status is `INCONCLUSIVE`. The current bundle validator accepts only a verifier result explicitly marked `pre_run`; its Python test fixture still uses a fake verifier to exercise fail-closed integration. The separate Go reference verifier at [`scripts/evals/reviewer-release-attestation-v1/main.go`](../../scripts/evals/reviewer-release-attestation-v1/main.go) verifies real Ed25519 signatures over exact payload bytes and SHA-256 of each named regular, non-symlink bundle file. The signed corpus commitment identifies the bundle corpus, labels, pre-run adjudications, and custody ledger by path and SHA-256, plus the corpus ID. For `post_run`, the verifier also checks the referenced pre-run signature under the same key, its file hash, corpus identity, five shared artifact digests, and signed per-call input/output inventories against the 120 committed case IDs. It requires every case × three arms × three repetitions exactly once and rehashes every declared per-call file. Its tests use disposable keys and reject wrong keys, signature or artifact mutation, missing/extra bindings, traversal, symlinks, duplicate JSON keys, a mismatched pre/post chain, a missing call, and a changed raw file. This proves the declared files' presence and bytes, not that those files are authentic model output or that no model-visible event was omitted inside them. The reference verifier also does not establish signer independence, runner isolation, external custody, or human adjudication independence. The bundle validator checks pre-execution readiness only and explicitly rejects a `COMPLETE` protocol or any `PASS`/`FAIL` result; release-grade transcript reconciliation and provenance checks remain required before any verdict is possible.

The attestation envelope is strict JSON with exactly `payload_base64` and `signature_base64`. The signature is Ed25519 over the decoded UTF-8 payload bytes. The signed payload has `schema_version: 1`, `phase: "pre_run"` or `"post_run"`, `protocol_id: "reviewer-release-v1"`, a non-empty `corpus_id`, and a `bindings` object with exactly that phase's binding names in the protocol. Each binding is `{ "path": "bundle/relative/file", "sha256": "lowercase hex" }`; the path names a distinct regular file inside the bundle. The signed `protocol` binding must also match the SHA-256 of the actual protocol file the preflight validated; the preflight passes that digest to the verifier as `--protocol-sha256`. The pre-run envelope must be referenced by `bundle.json` as `isolation.pre_run_attestation`. The verifier defaults to `--phase pre_run`; `--phase post_run` verifies the signed chain but is not wired to a release verdict. For a local cryptographic self-test with Go 1.24 or newer, run `go test scripts/evals/reviewer-release-attestation-v1/main.go scripts/evals/reviewer-release-attestation-v1/witness_service.go scripts/evals/reviewer-release-attestation-v1/main_test.go scripts/evals/reviewer-release-attestation-v1/witness_service_test.go`. An independent release operator must build the verifier outside the bundle, independently pin that binary's SHA-256 and the custodian's public key in the protocol before execution, and audit the signed contents. The optional `--serve-witness` mode also requires an operator-owned raw Ed25519 private key and new private journal outside the bundle, plus `--socket-gid` for a dedicated runner-access group. The socket parent must be operator-owned, group-traversable, and not group-writable; the created socket is group-connectable (`0660`). This permits a separate runner user to connect without granting access to the private key or journal, but actual identity separation still requires operator evidence. This repository supplies neither a key nor an independently operating signer; self-issued receipts are not release evidence.

The bound `corpus_commitment` file is strict JSON with exactly `schema_version: 1`, `protocol_id`, `corpus_id`, and `corpus`, `labels`, `adjudications`, and `custody` references. Each reference is `{ "path", "sha256" }` and must equal its `bundle.json` reference and the actual file bytes. This freezes the reference oracle and its pre-run adjudication records alongside the corpus; timestamps and human independence still need external evidence. Each bound `all_inputs` or `raw_outputs` file is strict JSON with exactly `schema_version: 1`, `protocol_id`, `corpus_id`, and `calls`. Each of its 1,080 calls has exactly `case_id`, `arm`, `repetition`, and `artifacts`. Input artifact roles are `prompt`, `staged_case_manifest`, `staged_skill_manifest`, and `runner_config`; output roles are `codex_jsonl`, `stderr`, `final_response`, `mcp_journal`, and `transcript_report`. Each role is a `{ "path", "sha256" }` regular-file reference. The two inventories must have identical complete call-key sets over the signed corpus. This is a byte inventory only: an isolated executor must still establish call provenance, and a separate verifier must reconcile each response manifest hash, tool transcript, and raw final response before scoring.

The offline [`verify-reviewer-release-calls-v1.py`](../../scripts/evals/verify-reviewer-release-calls-v1.py) reconciles the signed `response_manifest`, input/output inventories, raw Codex JSONL, MCP journal, final response, and per-call transcript report for all 1,080 call keys. It requires all three signed call arrays to follow the frozen case/repetition/arm schedule, then matches each staged case manifest and MCP session's source root and file hashes to the signed corpus case. It requires a case-file read in every arm, a bundled-scanner call in `full`, and a unique Codex thread ID per call. Its caller must first verify the Ed25519 chain and supply the signed corpus ID and 120 case definitions. Ordered arrays prove only that the submitted records are arranged as declared: an independent, append-only executor log or equivalent attestation is still needed to prove actual execution order and rule out post-hoc reordering. ## Signed execution receipts

The post-run attestation now binds an `execution_journal` in addition to the input/output inventories. This UTF-8 JSONL file has exactly 2,160 receipts: `begin`, then `end`, for every call in the frozen case/repetition/arm order. Each line is an envelope with exactly `payload_base64` and `signature_base64`; Ed25519 signs the decoded JSON payload bytes under the preregistered key. Each strict payload has exactly `schema_version: 1`, `protocol_id`, `corpus_id`, `event_index`, `previous_sha256`, `stage`, `case_id`, `arm`, `repetition`, and `artifacts`. The first previous hash is 64 zeroes; each later value is the SHA-256 of the preceding payload bytes. `begin` binds the four signed input artifact references, and `end` binds the five signed output references. The Go verifier checks signatures, complete order, call identities, and exact artifact references. A missing `end` after a timeout or interruption makes the run `INCONCLUSIVE`, never eligible for a replacement call.

The independent operator must also establish that the witness key was inaccessible to the model runner, that `begin` and `end` were signed online at their stated boundaries, and that no attempt ran outside this journal. The offline verifier cannot establish these operational facts: a journal fully re-signed after execution would satisfy its byte checks. Until independent online-witness and runner-isolation evidence exists, signed receipts are a necessary consistency check, not authoritative proof of execution timing or skill lift. The Go tests use disposable signing keys only; this repository does not supply a release signer.

The candidate [`verify-reviewer-release-attested-calls-v1.py`](../../scripts/evals/verify-reviewer-release-attested-calls-v1.py) bridge requires a protocol SHA-256 independently pinned outside the bundle, plus a pinned operator-owned verifier. It checks the verifier's exact `post_run` result and attestation digest, rechecks every committed source file and pre-run oracle/custody contract, then passes only signed inventory references and sanitized committed cases to the raw-transcript reconciler. It also resolves the signed post-run adjudication ledger, recomputes the finding-level matrix score, and rejects a signed `scorer_output` that differs from the calculation. The candidate 1,080-call executor requires the same external protocol digest before bundle admission. A digest derived only from the supplied protocol file would let a changed protocol choose its own key and verifier pin. The bridge returns `SIGNED_BYTES_RECONCILED` with `score_reconciled: true` and `release_eligible: false`; score consistency alone does not establish independent judges or execution. Its local Python test fakes the Go verifier and score result to exercise wiring and mismatch refusal; the Go verifier, ledger resolver, and matrix scorer have separate contract tests. None is an independently operated release run.
