# Semantic candidate discovery — exploratory successor design

Status: **DRAFT / PILOT ONLY**. This is not a frozen v5 protocol, an admission ledger or evaluation evidence. V3 and v4 remain unchanged and v4's execution block remains active.

## Selection and independence

Retain 24-pattern whole-case adjudication and the intended 24–48-case benchmark. Add a discovery lane for the eight principal IDs the scanner cannot emit. Discovery proposes lookalikes with source anchors, not findings or clean labels. The two fresh adjudicators receive complete source files and the frozen pattern reference, never discovery output, scanner hits, principal labels or another verdict. The discovery model may share an adjudicator's family/identifier, but its session and output are isolated; shared model bias remains a limitation, not independent-human evidence.

Use repository-rank/framework/spec-path order before observing outcomes. Every reached case records a discovery result for every semantic ID: `candidate`, `absent`, or `insufficient-context`. A candidate requires an exact source anchor and cited contextual evidence explaining the apparent resemblance and why it merits review. Missing configuration, app handlers, render guards or environment evidence must not be treated as clean or invented. A candidate is selected in spec order, then taxonomy order, then path/line order. One full-file boundary contributes at most one case. Scanner and semantic proposals for the same boundary must be grouped, not counted twice. A successor must freeze the combined principal-assignment rule before its counted collection begins; this pilot tests only the semantic lane.

## Eight discovery contracts

| ID | Candidate shape | Required contextual evidence |
| --- | --- | --- |
| #1 | A title whose promised result is proved indirectly rather than by a literal assertion on its nouns | Map each explicit promise to the actual assertion/helper/request evidence; do not invent promises |
| #2 | A state-changing action with a non-obvious postcondition, or a helper action subordinate to another asserted result | Trace the promised final state, helper assertions and valid alternative proof; distinguish user outcomes from setup/cleanup |
| #12 | Navigation that appears unauthenticated in the spec but has supplied auth or cannot silently pass on the wrong surface | Configuration and setup/fixture evidence, plus protected-route and wrong-surface evidence when applicable |
| #13 | Direct-looking interactions that appear to bypass an existing POM | The POM, its ownership boundary and the spec interactions; no POM evidence means no invented inconsistency |
| #20 | A mutation with a controlled backend boundary despite no inline route stub | Actual write evidence and a supplied stub, rollback, disposable tenant/database or ephemeral-backend contract |
| #21 | A session-file reference with automated regeneration or fallback | Consumer and producer paths plus setup/dependency order; a filename alone is insufficient |
| #22 | A write-looking UI test with request proof, proven non-optimistic behavior or a proven client-only operation | Handler/fixture evidence establishing optimism or its absence, and request-proof ordering where relevant |
| #23 | A fixture whose renderability depends on conditional component behavior | The component/container guards, fixture values and view state; type correctness alone is insufficient |

Discovery never rewrites a source, manufactures a guard line or changes a pattern's severity. Each proposed principal guard must subsequently be checked for contextual validity before corpus admission. Both blind whole-case passes must be complete and clean; a finding or insufficient context prevents admission. Whether the two passes also need a separate, post-blind check of semantic principal attribution is an unresolved successor-design issue: clean adjudication alone does not validate that attribution.

## Bounded pilot

Use the existing v4 extraction snapshot without new network collection. Inspect its stable case order and select the first three spec closures whose root spec directly imports `test` from `@playwright/test`. This narrow intake deliberately omits indirect fixture imports and Cypress; it is a pilot scope, not a general framework detector. Record every skipped prefix row and the complete selected boundary. Verify every staged file against its extraction hash. Pilot repositories and cases must be excluded from any later counted corpus to avoid development contamination.

Run one fresh tool-free Claude Fable discovery call per selected spec, serially, with a 300-second timeout and no automatic retries. The first candidate in the ordered prefix receives two fresh, mutually blinded Opus/Fable whole-case passes. Maximum: three discovery calls plus two adjudication calls. If a call fails, times out, mutates its input or returns malformed output, stop and retain an incomplete record; do not advance to a more convenient candidate. Preserve partial responses only after credential redaction. The runner may resume already validated successful calls, but never silently rerun an unsuccessful reservation.

The report distinguishes transport completion, schema/citation validity, presence of semantic proposals, blind verdicts and provisional clean agreement. Even a successful five-call pilot proves only that this small selection-to-adjudication path works. It does not prove all eight patterns have adequate yield, all 24 slots are fillable, closure completeness, oracle correctness, or specificity lift. No new protocol freeze or large run is authorized by a plumbing-only success.

### Disclosed transport-parser revision

The first live discovery invocation exited successfully after approximately 129 seconds but wrapped its JSON in explanatory prose. The original strict parser stopped and recorded `StrictJsonError`. A parser-only revision accepts exactly one `json` fence, rejects additional fences or structured data outside it, and applies the unchanged strict schema and source-citation checks to that object. The original response and incomplete call record remain unchanged; a separate recovery artifact binds their hashes and records zero additional model calls. An explicit `--recover-framing` invocation records the old input-manifest hash and revised parser identity. Source bytes, selection, model identities and prompt bytes remain unchanged. This is a disclosed exploratory parser repair, not a successful original invocation or an undeclared rerun.

The first blind response exposed a second validator defect: it reported family ID `#4` at P1, consistent with reference-defined subtype `#4i`, but the reused validator expected a single canonical severity for a principal ID that has multiple subtype severities. The pilot-only validator now accepts exact reportable subtype IDs or principal-family IDs at their reference-defined severities, plus the reference's explicit #23 P0/P2 variants. It still rejects invented IDs, wrong subtype severity, invalid citations and finding/clean contradictions. `--recover-taxonomy` records a separate, hash-linked revision and validates the saved response without changing any finding, severity, verdict, source or prompt. The frozen protocols and their adjudication validator are not silently amended. A successor must settle its exact finding-ID vocabulary before freeze.

## Outstanding readiness gates

Before freezing a successor: validate semantic principal attribution independently of whole-case cleanliness; define reproducible contextual expansion without result-guided file trimming; freeze combined scanner/semantic grouping and principal order; demonstrate plausible clean-lookalike yield for every required slot, including scanner patterns such as #7 that intentionally have no legitimate committed use; and revalidate repository caps, lineage deduplication, framework provenance, freshness, blinding and evaluation input registration. A 24-pattern review surface must not be confused with guaranteed clean-lookalike availability for all 24 patterns.

The combined allocation also needs a starvation check: always assigning the first taxonomy ID can assign most multi-pattern cases to #1 and leave later slots unreachable in practice. Do not repair that after outcomes by relabeling admitted cases. Specify and test an open-quota assignment rule with immutable proposal sets and case digests before any counted collection.

## Implemented exploratory rules (2026-09-22)

[`specificity-successor-rules.py`](../../scripts/evals/specificity-successor-rules.py) is a separate preparation tool; neither frozen collector nor the completed pilot is changed. It expands literal `testMatch`, `globalSetup` and `globalTeardown` references, considers literal `testDir` directories, and includes each target's existing import closure. It never executes configuration or setup code. Dynamic expressions, arrays, regular expressions, glob paths, missing targets and unresolved imports are retained as unresolved evidence. This limited textual discovery is not a JavaScript parser or a complete project/dependency resolver; `context_completeness_proven` stays false even when no issue is detected. Runtime commands in added files are explicitly marked unexpanded. Storage-state JSON is not collected.

The preparation command requires a fresh external output directory. It reuses the pinned extraction tree, checks existing source hashes and Git blob identities, optionally fetches missing public blobs without credentials, and records source and implementation hashes. Existing artifacts cannot be overwritten. Fetches are limited to 32 unique blobs, with a four-MiB per-source acceptance limit (not a network response-size limit).

```bash
python3 scripts/evals/specificity-successor-rules.py \
  --source /path/to/v4-artifacts --output /path/to/new-context-artifacts --allow-fetch
python3 scripts/ci/test-specificity-successor-rules.py
```

The allocation function accepts only ordered proposal rows (`case_sha256`, `lane`, `patterns`), a unique taxonomy order, and positive attempt quotas. Scanner and semantic proposals for one source-boundary digest merge before allocation. Each boundary gets at most one principal: among its open patterns, choose the least previously assigned, breaking ties by taxonomy order. Quotas count **attempts**, not admitted clean cases. A rejected case retains its slot and principal; filling clean-case deficits requires a separately registered later batch, not retrospective reassignment. This avoids always choosing #1 when several proposed IDs are available, but cannot manufacture missing proposals or guarantee a feasible corpus. Input hashes bind the proposal sets, order and quotas; verdict-bearing inputs are rejected. The function is tested offline and is not wired into counted collection.

The allocation contract does not validate semantic attribution. A future admission stage must separately establish that the assigned pattern is a genuine contextual lookalike and that both blind whole-case passes are clean. Repository/lineage caps and multi-batch stopping rules still need integration before freeze.

An optional `--seed-cwd <repository-relative-directory>` now supplies a recorded cwd hypothesis for literal `execSync('node relative/path ...')` entrypoints. The tool reads a uniquely resolved entrypoint and its import closure as inert source, retains runtime uncertainty, and never executes a seed command or reads environment files. This is bounded contextual evidence, not a general shell parser or proof of database isolation. The follow-up preparation used `--seed-cwd e2e`, adding `tools/scripts/seed/seed-demo-user.js` and `tools/scripts/seed/user-data.js` alongside the setup file. Changed boundaries require fresh model calls; old verdicts cannot be carried over.

[`pilot-specificity-context-followup.py`](../../scripts/evals/pilot-specificity-context-followup.py) accepts one to three prepared boundaries and a fresh external output directory. It verifies source digests, records its five-call maximum before execution, applies the offline allocator after discovery, and gives both blind passes identical source/limitation prompts without discovery results. It cannot emit an evaluation corpus. The broader [sampling decision](successor-sampling-decision.md) keeps this challenge allocation separate from the proposed primary clean cohort.

The optional `--runner codex --model gpt-5.6-sol` development path adds one short transport check (six calls maximum), then uses the specified model for all five discovery/review calls. It records `independent_adjudication: false`; fresh sessions prevent verdict leakage, not same-model bias. The existing Claude defaults and frozen protocols are unchanged. Codex uses an opt-in JSON-event transport that requires one completed turn, a final agent message and no tool items; combined capture limits and isolation remain unchanged. See the [official non-interactive output documentation](https://developers.openai.com/codex/noninteractive/).

The tested CLI rejects a single input above 1,048,576 characters. Development discovery inputs over that limit now fail before any model call. Oversized complete boundaries are unprocessable with this CLI path, not clean or negative examples. An explicitly separate smaller context snapshot may be explored only with its missing-context limitations preserved and without transferring old verdicts or claiming full-boundary validation.

The opt-in `--discovery-contract v2` clarifies that a guarded resemblance can be a false-positive-test candidate even when no defect is present. The separate three-fixture #21 calibration records expected labels outside model prompts; passing it is only a development preflight, not a general recall gate. [`prepare-specificity-fresh-pilot.py`](../../scripts/evals/prepare-specificity-fresh-pilot.py) then limits intake to ten eligible inventory-prefix repositories, twenty e2e-named specs per repository and three prepared cases. It checks ancestor manifest ownership and pinned source hashes without executing source. Prior public API cache responses and pinned raw blobs are optional quota-saving inputs, with their hashes recorded. `--allow-prepared-prefix` explicitly permits reviewing staged cases from an incomplete intake; without it, incomplete intake is rejected. This opt-in never marks the intake complete or authorizes counted evaluation. See the [observed calibration and intake results](semantic-pilot-results.md#discovery-calibration-and-fresh-development-intake).
