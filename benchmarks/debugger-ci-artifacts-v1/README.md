# Debugger CI-artifact acquisition v1

Status: **100 real CI failure events acquired; one causal case linked to a maintainer fix; one two-arm pipeline smoke completed; no causal accuracy or skill-lift result.** This is a public development sample, collected on 2026-10-09 with read-only GitHub Actions queries. The raw downloads remain in a local cache, outside this repository. Nothing was pushed or submitted upstream.

The question was whether collecting about 100 CI artifacts would give a more realistic debugger benchmark than the previous two constructed preserved-outcome cases or the report-style, zero-tool real-fix prompts. The answer is **yes for finding acquisition and reader constraints, but not yet for measuring diagnosis accuracy**: 100 run/test events collapse to only 26 distinct repository/test IDs, and just one event has a maintainer-linked causal adjudication.

## Acquisition and counting

- Queried the 100 most recent failed runs each from OpenMetadata's Playwright workflow and Superset's E2E workflow. The OpenMetadata download was deliberately stopped after 25 processed runs when repeated failures dominated. Superset's 100 runs were processed. A recent Grafana E2E run supplied a Playwright blob shard. Other pilot sources were not counted: an OpenSearch Cypress run had 40 JUnit XML files but zero test failures; Directus's recent failed E2E runs had no artifacts.
- Only small `playwright-results-json-*` OpenMetadata artifacts and bounded `playwright-artifact-*` Superset artifacts were selected; container images, binaries, and videos were excluded. The collector had a 1 GB compressed-download budget and the disk remained above the local 4 GiB stop floor. The Grafana shard was inspected without executing repository code.
- The JSON reports contained 119 `unexpected` test records. The Grafana blob contained three tests whose final attempt failed or timed out. Deduplicating by repository, CI run, and test ID removed 22 duplicate report records, yielding exactly **100 events**: Superset 74, OpenMetadata 23, Grafana 3. These represent **26 distinct test IDs** and **45 distinct test/error-hash pairs**, not 100 independent root causes. The case-by-case provenance and content hashes are in [manifest.json](manifest.json).
- Reports can contain untrusted text and secrets. This repository keeps only hashes, IDs, URLs, and counts; it does not publish the raw reports or error messages. The original local pilot used `gh run download`; the checked-in collector was then changed to fetch bounded artifact ZIP bytes through the read-only API and extract only validated `results.json` members. Neither path tests the debugger's hardened downloader. Reproducing the raw input depends on GitHub artifact retention and access.

## Product-reader probe

The bundled Playwright reader was invoked on all 134 distinct downloaded JSON reports through its system-interpreter launcher, without printing raw output. It accepted **124** and safely rejected **10** with `credential redaction left residual sensitive output`. Among the 100 selected events, **85** belong to accepted JSON reports, **12** to rejected JSON reports, and **3** to Grafana's blob shard, which requires the documented merge path before this JSON reader can score them. The per-report disposition is [reader-probe.json](reader-probe.json). A rejection is a safety-preserving result, not evidence of a diagnosis error; loosening the credential gate merely to raise coverage would be unjustified.

## Source-and-trace validation

The 85 reader-accepted events cover only **11 distinct repository/test IDs**; the other 15 distinct IDs have no accepted selected JSON report or are in Grafana's unmerged blob. The private candidate selection used the bundled reader, matched its test identity to the manifest hash, and retained one accepted report per distinct test. It did not run upstream project code or assign causal truth. The reproducible selector is [`prepare-debugger-ci-validation-v1.py`](../../scripts/evals/prepare-debugger-ci-validation-v1.py); its sanitized output stays outside this public repository.

The most common Superset mobile test accounts for **55 events on 55 different head commits**, all with the same test/error hash pair. Its latest accepted report failed all three attempts because neither chart-container locator appeared within 20 seconds. The three corresponding trace attempts had no projected failed network request or browser error. A common error hash does **not** establish a common cause across different commit graphs.

One earlier mobile event **is source-adjudicated**. In the September 28 `master` run, the bundled JSON reader showed three failed chart-visibility attempts, and a bundled-media snapshot showed an empty `xref_dash_...` dashboard with the no-charts state. At that exact head, `openFirstDashboard` clicked the first card and the failed test called it. Superset [PR #44856](https://github.com/apache/superset/pull/44856) explicitly identifies an empty duplicate dashboard left by a cross-referenced-dashboard save, changes the Save modal to select the exact existing dashboard, and changes the mobile test to open a known sample dashboard. The PR reports targeted local mobile tests passing and its Playwright checks were green. This supports a test-isolation/data-selection diagnosis for **that run** (F7, test defect); it does not prove an independently reproduced post-fix outcome here. Importantly, the latest sampled October 7 PR head still contains `openFirstDashboard` despite the fix having merged to `master`: a later timestamp is not evidence that a branch included the fix. The case and its evidence hashes are in [adjudication-v1.json](adjudication-v1.json).

A later read-only source/CI check strengthened the failure-time linkage without using that PR as model input: the exact run-head cross-referenced-dashboard spec creates `xref_dash_1`, its helper names dashboards from that prefix and tracks the created ID for cleanup, and its save path selects by title through a partial-match-capable dropdown. The same CI job's log shows that individual test passing at 18:31:31 UTC, before its mobile step failed. These facts identify a preceding `xref` producer in failure-time evidence, but the retained material does **not** directly show the duplicate-creation request or response. [source-observability-v1.json](source-observability-v1.json) records this distinction. The frozen one-case pilot remains unchanged; re-prompting it after seeing both answers would be a retrospective development iteration, not an independent skill-effect test.

Seven different Superset drill-to-detail tests failed in one CI run, one report, and one artifact. For each initial-attempt trace, the bundled reader projected a `POST /api/v1/chart/data` response of HTTP 500 before the failed canvas-visibility assertion. The historical test source at that run's head indeed waits for `canvas` in a chart after loading the dashboard. This is strong evidence of a **shared chart-data/backend failure upstream of the missing canvas**, rather than seven independently demonstrated selector defects. The API's underlying reason for returning 500 and any maintainer fix remain unverified. [validation-v1.json](validation-v1.json) binds the seven validated trace ZIP hashes, report, run, and bounded observation.

The remaining accepted OpenMetadata candidates show a status race (`Running` expected, `Success` observed) or setup timeouts, but no source-backed corrective change was established. Their causal labels remain unadjudicated. The drill-to-detail group likewise has a verified shared 500 symptom but no established backend cause or linked fix. Thus five candidate groups yield **one maintainer-fix-linked causal case and four unadjudicated groups**. The subsequent one-case pilot below does not support a skill-lift estimate.

We also checked an older maintainer-linked OpenMetadata candidate: [PR #32759](https://github.com/open-metadata/OpenMetadata/pull/32759) names failed run `34023457610` and explains a stale glossary-chip selector. The run's Actions API currently lists zero retained artifacts, so this cannot be promoted to an artifact-backed model case from the available evidence. A PR narrative alone is not a substitute for the model input.

## One-case prompt-complete pilot

The [pilot protocol](pilot-v1-protocol.json) froze the September 28 mobile report, screenshot, historical test source, model, two arms, and one call per arm before execution. The model received the bundled-reader's sanitized report projection, the exact run-head test source, and a validated screenshot. Only the `skill` arm also received the current debugger skill and its relevant reference text. Both arms had model-callable shell, file, and web tools disabled; the upstream project was not executed. The maintainer PR and [truth](pilot-v1-truth.json) were withheld from both prompts. A model-free readiness record bound the prompt and input hashes; the model calls refused drift from that record. Raw answers and runner details stay in the private cache, bound by hash in [pilot-v1-result.json](pilot-v1-result.json).

Both Codex calls completed with schema-valid outputs. Both identified that the test selected an empty first dashboard and then asserted a chart existed; both called it a test defect and explicitly said the origin of the empty dashboard was unknown. Neither could infer the maintainer-linked **cross-test leak** from the supplied failure-time input. That is a valid uncertainty, not a diagnostic miss. Consequently the pilot passed its input-isolation, image, reader, and structured-output smoke but **failed the prerequisite for full causal scoring**: the ground-truth distinction was not observable to the model. The tool-disabled, prompt-complete format also does not measure the full debugger skill workflow. Do not score this one case as skill lift or general root-cause accuracy, and do not change its frozen input after seeing the answers.

## Interpretation and next gate

This run establishes a concrete local corpus and exposes its major limits: repeated CI failures make raw-event count a poor proxy for independent cases; the reader cannot presently consume every selected JSON report; and even a verified proximal failure does not reveal the final product or test fix. **Two prompt-complete model calls ran, but no upstream-code execution or valid causal-accuracy scoring ran**, so the current debugger's root-cause accuracy and the post-v3 wording change remain unmeasured here.

The next valid comparison needs not only a maintainer-linked label but failure-time evidence that exposes the distinguishing mechanism without leaking the fix PR. Do not reuse the frozen mobile pilot as a holdout. Select new, independent cases whose original artifacts and run-head source support a prospective answerable question; keep proximal symptoms separate from unverified underlying causes. Freeze a diversified subset and its truth before any larger comparison. Count independent failure clusters, not repeated runs, for confidence intervals. Keep reader rejection and blob-merge coverage as separate operational metrics.

A bounded follow-up search found a promising **unverified** new case: OpenMetadata [PR #34929](https://github.com/open-metadata/OpenMetadata/pull/34929) names a pre-fix merge-queue run where two drag tests passed only on retry. The run-head source measures a drop coordinate before `hover()`, and the PR attributes the failure to hover scrolling the page and invalidating that coordinate. The run retains a blob shard and an HTML report, but neither has been read through the bundled reader, so the original failed attempt, trace availability, and model-visible observability are **not established**. [candidate-screen-v2.json](candidate-screen-v2.json) records the acquisition gate and rejected alternatives. No second model comparison was run.

## Candidate gate result: OpenMetadata PR #34929 (2026-10-10)

The bundled downloader fetched run `37746994563`'s `playwright-report-37746994563-1` artifact (HTML report, 11 trace ZIPs, no `results.json`) after two group-writable directories on the local `gh` path (`/opt/homebrew/bin`, `/opt/homebrew/Cellar`) were tightened to `755`; the downloader's refusal there is its intended safety behavior. The bundled trace reader accepted every ZIP. Its projections contain only 404 console errors and a few network records; **no failed-action, drag, hover, or Persona-widget evidence appears**, so the original failed attempt's scroll/coordinate mechanism is **not observable** from reader-validated, PR-free input. Per this file's own gate the case is **not promoted**: the PR narrative alone cannot serve as truth for a model comparison. The blob shard (`playwright-blob-chromium-03`) was not merged or read, so a different shard could still hold the failed attempt.

**Follow-up: blob shard read.** The HTML report's traces did not hold the failed attempts, but the retained blob shard `playwright-blob-chromium-03` (outer ZIP: one stored member, written to a scratch `blob-report/` after a name/size check; Playwright 1.57.0 blob v2) merged with the repository-independent local Playwright 1.62.0 `merge-reports --reporter=json`, which executes no upstream code, and passed the bundled `report` reader. It shows two `flaky` tests in `PersonaOverviewCardWidgets.spec.ts`, each with a **failed first attempt and a passing retry**: the drop target's `data-testid=left-panel-drop-target` never got `panel` (received empty, 15 s timeout, line 239), and a grid placement read `start: 0` instead of `3` (line 431). So the failure-time input exposes the **symptom** (the drop did not land where measured), not the scroll-after-hover mechanism; the mechanism needs the run-head source, which measures the drop point before `hover()`. This is one cause shared by two events, i.e. one independent case. It is not a basis for an accuracy result, and no model call was made. A fair test needs several such cases with PR-free, reader-validated evidence; collect them before freezing any protocol. The raw reports stay in the local scratch cache.

**Follow-up: second screening (2026-10-10).** Of 13 merged fix PRs from three repositories (OpenMetadata, Superset, Grafana) since 2026-09-20 that name a CI run, only OpenMetadata's merge-queue runs still retain blob shards (the others have zero unexpired artifacts, or the run is a successful release-branch backport). Blob shards were fetched through the read-only API (one stored member, name and size checked), merged with the local Playwright `merge-reports --reporter=json`, and read through the bundled `report` reader; no upstream code ran and no model call was made. Two new candidates pass the observability gate in different ways:

- **PR #35016, run 37882115854** (`IngestionLogStreamLive.spec.ts`): attempt 1 fails because `log-viewer-live-indicator` is not visible; attempt 2 fails because the agent card already reads `Success` where `Running` was expected. The artifact shows the symptom "the ingestion run finished before the assertion looked"; why it finished early (the external Kafka's topic count per the PR) is not in the report.
- **PR #34725, run 37419482152** (`GlossaryAdvancedOperations.spec.ts:907`): the first attempt times out in `storageStateRecovery.ts` waiting for `**/signin` while the navigation log shows normal glossary pages, then the retry passes. The reported error is a misleading session-recovery race; the actual cause (a click swallowed during re-render, with the Owners button focused and no popover) is **not** in the JSON report and would need the failed attempt's DOM snapshot. It is a good probe of whether a diagnoser avoids asserting an auth/session cause the artifact does not show.

Counting the Persona drag case and the Superset mobile case, four causally linked independent cases now exist; a fair comparison still needs more, and the other candidates' truths must not be used as model input. Raw reports stay in the local scratch cache.

**Follow-up: OpenMetadata pool exhausted (2026-10-10).** Scanning 100 merged OpenMetadata flake PRs since 2026-08-01 found 40 PR/run links; only three runs (#34811, #34725, #35016, all from 2026-10-06 to 2026-10-09) still hold unexpired blob shards, and the older runs return 404. Retention is therefore about two weeks, so the usable pool is whatever merged in that window. #34811's 25 merged shards contain no DataContracts failure, so its failed attempt is not observable and it is not promoted. A broader GitHub search for other repositories' recent flaky-Playwright PRs returned mostly small or generated repositories without usable run links, which were not pursued. Net: four causally linked independent cases, no more obtainable now. Reaching a larger sample would need snapshotting qualifying runs while their artifacts are retained; a collector for that was built, judged unnecessary while the shipped skill is unchanged, and removed. No protocol should be frozen on four cases.
