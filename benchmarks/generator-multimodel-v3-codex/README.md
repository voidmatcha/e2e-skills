# Codex successor of the multi-model generator benchmark (preregistration)

Status: **PREREGISTERED, NOT RUN** when this file was written. Results, if any, are appended below the line marked `Results` and never change anything above it. Pre-freeze changes after an independent review are listed in [CHANGES.md](CHANGES.md). Nothing in this directory has been frozen yet: `freeze.json` does not exist, and `freeze` is the owner's decision after reading this file.

[generator-multimodel-v1](../generator-multimodel-v1/README.md) compared the first-party Playwright generator (A), A plus one `e2e-reviewer` pass (B) and this repository's `playwright-test-generator` 2.0.1 (C) across models. On Claude models arm A genuinely called the official MCP generator tools (claude-sonnet-5-5: `generator_setup_page` and `generator_write_test` in 12 of 12 A cells). On Codex models it mostly did not: in the gpt-5.5 pilot 6 of 12 A cells had a child agent report that the generator tools were not exposed (the other 6 are unknown), gpt-6-sol delivered 3 of 12 A cells, gpt-6-astra 0 of 12 in every arm. **The v1 Codex results therefore stay "harness-limited descriptive": they are not corrected, replaced or read as quality differences by this protocol.** This protocol asks the narrower question again for the Codex models only: **among cells classified as generator MCP use (observed calls or disclosed self-report fallback), how do A, B and C compare, and do the per-model labels agree across Codex models?** A negative, mixed or not-evaluable outcome is acceptable. There is no PASS/FAIL rule and no confidence interval in any per-model label or in the cross-model rule; the pre-registered pooled analysis (below) prints a descriptive p-value and interval that draw no verdict.

## Live check after freeze, before the first preflight

One cheap call that must pass before the first entry call, run **after** `freeze` (every campaign live command needs `freeze.json` and the harness-check result is bound to its digest; the separate non-data `smoke` command does not require a freeze). If it does not pass and code has to change, preserve the frozen files, create another authorized successor and rerun its check; the result of an earlier freeze is never reused. It is needed because the rollout parser and the persistence mount are built against rollouts read on the host (Codex CLI 0.157 to 0.159), not against the container's build:

```bash
python3 scripts/evals/run-generator-multimodel-v3-codex.py harness-check --allow-live [--model gpt-6-sol]   # exit 0 pass, 5 not a pass
```

`preflight` runs this check first and exits 5 without entry calls unless it passes; `drive` refuses without a passing check bound to the freeze. The diagnostic uses the same session-wide `playwright-test` configuration as arm A: the exact 19 generator/browser tools, `danger-full-access` shell sandbox, `approval_policy="never"` and `mcp_servers.playwright-test.default_tools_approval_mode="approve"`. ## Cost endpoints (pre-declared, descriptive)

A proven never-launched B reviewer call has complete zero usage and zero reviewer elapsed time, while its pipeline retains the source A tokens and elapsed time. Only the runner's explicit skip record establishes this; missing evidence from a launched or ambiguous call remains incomplete.

Cost is read next to quality, never alone. Co-primary: **quality per 100k tokens** (refactor survivors per 100k processed tokens, where processed = uncached input + output, parent and child agents together, cached input reported separately and added in a sensitivity ratio) and pipeline seconds (mean per cell, and per survivor). Arm B's pipeline is its source arm A cell plus the reviewer call. Every call attempt is included once, including infrastructure retries; a missing per-attempt token record makes the cell incomplete. The ratio is a ratio of sums over the cells with a complete token record (the others are counted but excluded). Codex parent tokens come from its own persisted root rollout (the stream is retained as a cross-check, or used as fallback), and child tokens come from persisted child rollouts; Claude tokens and cost come from `modelUsage` (subagents are inside it). Printed per model, view and arm in the summary (`cost_endpoints` in `results.json`).

## Pooled analysis (pre-registered, descriptive)

Written before any successor data is scored as a complement to the per-model sign rule. Unit: model by task (per task, the mean of X cells minus the mean of Y cells in the view); estimate: the unweighted mean over models of each model's unweighted mean over tasks; test: an exact enumeration of sign flips over the models' effects (smallest attainable p = 2/2^N, 0.03125 at N = 6, never below 0.125 at N <= 4, printed beside every p); calibrated p-values require joint coordinate-wise sign invariance conditional on effect magnitudes, which marginal symmetry alone does not establish. Shared task or lineage shocks can violate that assumption, so the p-values are not calibrated under such correlated effects. Interval: a crossed task-and-model cluster bootstrap (10000 replicates, seed 20261016, percentile 95%, known to under-cover with 4 to 6 models); plus per-model effects, lineage means, the per-task profile and leave-one-model-out estimates. Views: primary, itt and as_treated for the primary metric (refactor survival); clean-3/3 and effective fault kill in the primary view. **Approved 2026-10-15:** model and task clusters, the unweighted mean over models, exact model sign-flip, two-way cluster bootstrap, ITT and as-treated views are part of the pre-registered analysis. **Every pooled result is labelled "development evidence" and never replaces a per-model label or draws a verdict.** `pooled_analysis.owner_approval.inference = true` and the approval date are bound by `protocol.json` at freeze. `pooling_with_v1_claude_family = false` remains: no cross-family pooling is approved or implemented. The pool is the same eligible models as the cross-model rule, Codex v2 only; it never combines families. A Claude successor protocol must carry this section unchanged.

## Secondary refactor classes (specified, not built)

Two further refactor classes would show whether specs survive more than the id/class rename, as **secondary** metrics beside the unchanged primary: R-TEXT (a visible-text or label change that keeps DOM structure, ids, classes and roles) and R-STRUCT (a DOM-structure change that keeps roles and accessible names and every id and class). They need per-case edit lists validated by ARIA snapshots before and after, which needs a browser and local servers; this offline-only round did not build them, because unvalidated edit lists must not enter a freeze. The exact specification (edit form, acceptance checks, build procedure, metric names `refactor_text_score` and `refactor_struct_score`) is in `protocol.json` (`secondary_refactor_classes`); they never enter a per-model label or the cross-model rule.

## Roster and entry rule

Roster (the v1 Codex models whose catalog entry says v2): gpt-6-sol, gpt-6-astra, gpt-6.1-sol, gpt-6-luna (lineage gpt-6) and gpt-5.6-sol, gpt-5.6-terra (lineage gpt-5.6). Not included: gpt-5.6-luna (catalog v1, so the new arm A line would state something false for it; its v1 rows stand; excluded under the approved six-model roster), gpt-5.5 (unavailable: HTTP 400 "not supported when using Codex with a ChatGPT account", owner-verified 2026-10-14 23:50 KST; historical pilot reference only, no plan depends on it), the moving alias and the two hidden models, as in v1.

**Entry rule, decided before any scored cell.** For every roster model, in order, one call at a time: up to 2 arm A calls on the unscheduled task `v2-01`. The model is admitted at the first real attempt classified `official-tool` **with hard evidence** (a completed `generator_*` or `browser_*` call, in the parent stream or any rollout, or `.playwright-mcp/` snapshot files; an affirming message alone does not admit, because the decision is final). It is excluded only after 2 real attempts none of which admits, and the classes of both are recorded. Only real attempts count: an aborted call (infrastructure outcome) is never an attempt, and neither is a call whose primary evidence is missing or incomplete without hard admission evidence (including message-only success narration). Within one `preflight` invocation the first aborted call is rerun once; a second aborted call, or any usage or rate limit, stops the invocation at once and leaves the model **undecided** (no decision file, exit code 4, attempts kept in `_entry/<model>.pending.json`); the owner reruns `preflight` when the infrastructure is healthy. An outage therefore never excludes a model. `drive` refuses to start unless every roster model has an admitted or excluded decision bound to the freeze; those decisions are final. Preflight calls are never data.

**Go/no-go after the preflights.** The cross-model rule needs at least 4 evaluable models over both lineages, so `drive` proceeds only if at least 4 models spanning both lineages were admitted. Otherwise it refuses, and the owner may pass `--descriptive-only` to run the admitted models for per-model descriptive results with no cross-model verdict.

## Arm A fidelity (the point of this protocol)

Per arm A cell, from the parent JSON stream and the workspace:

- `official-tool`: positive observed or self-reported fallback evidence of generator MCP use (delivered or not). **Primary signal (observed):** a completed call to a generator tool (`generator_*` or `browser_*`) on the `playwright-test` server in the parent stream or in any rollout of the cell, child agents included. Completed `test_*` (`test_list`, `test_run`, `test_debug`) and `planner_*` calls on the same server are recorded as information (`other_playwright_test_calls`) and are not evidence that the generator ran. Malformed rollout lines, unlinked children and extra roots also make a record incomplete for fidelity and cost. The rollouts are the complete record only when there are no `observation_gaps`: the parent's rollout is identified, every unique spawned thread ID in the parent stream and all descendants has a persisted rollout with the expected parent relationship, and the persistence census (skipped or errored files) is clean. With a complete record, no generator call means none was made, and the secondary evidence cannot make the cell positive (a disagreement is recorded as `signal_conflict`). Unknown spawn identities and duplicate thread rollouts are gaps. Fallback MCP completion requires a matching structured success result; explicit errors fail and ambiguous output is unverified. If rollouts exist with gaps and no hard signal is positive, the cell is `observation_incomplete`: the entry rule treats it like an infrastructure outcome (not an attempt, model left undecided), because a lost rollout could hide a call and the entry decision is final. **Secondary evidence, used when the record is not complete (no rollouts, as in stored v1 cells, or observation gaps):** files under `.playwright-mcp/` among the out-of-scope writes (hard), then an agent message with a sentence affirming the tools worked, carrying no negation and no plan or intent wording, in a message with no denial (message-only). Hard call evidence observes generator MCP use. Message-only fallback reports use and can be false positive; the scored class therefore does not guarantee observed use or spec authorship. Admission requires hard evidence.
- `manual-follow`: delivered, no positive evidence, and a message denies the tools. `unverified`: delivered, neither (with rollouts present: an observed absence of any call). `blocked`: nothing delivered, no positive evidence. `aborted`: infrastructure outcome.

**The `// spec:` and `// seed:` headers are not evidence.** `generator_write_test` writes the model's `code` argument verbatim (playwright 1.62.0 `lib/mcp/test/generatorTools.js`); the headers come from the agent definition's example, so a model following the definition by hand writes them too. Checked on the stored gpt-5.5 pilot cells: 5 of the 6 cells whose child said the tools were not exposed carry both headers (11 of 12 A cells carry them). v1's `official_signature` column and its comment ("first-party generator_write_test output carries ...") overstate fidelity; the v1 files are not edited and the column is kept here only as a labelled non-discriminating proxy.

**Arm A configuration correction (approved 2026-10-15) preserves the official generator's 19-tool MCP allowlist.** The generic generating child inherits the session configuration because the v2 spawn tool cannot select the custom role. Shell execution uses `danger-full-access` inside the isolation container. Session-wide `playwright-test` calls are explicitly pre-approved with `default_tools_approval_mode="approve"`; `approval_policy="never"` remains explicit. Specs must still be written through `generator_write_test`, and planner/healer tools remain excluded. Offline argv and parser probes establish requested configuration, not live acceptance or inheritance.

**Successor invalidation.** This unfrozen v3 protocol supersedes [frozen Codex v2](../generator-multimodel-v2-codex/README.md). The v2 freeze and all bound bytes remain intact. Its read-only shell and missing explicit MCP approval cannot establish admission under the corrected configuration. Every previous admission and harness pass is invalid for v3; no prior A, B or C result is carried forward. A new freeze and fresh harness check/preflight are required before any v3 data call. This offline repair inspected no unfinished campaign results and creates no freeze or live result.

The classifier, run read-only over stored cells: gpt-5.5 pilot A cells 6 `manual-follow` (all six "not exposed" cells) and 6 `unverified` (absence of a denial is not evidence of use); gpt-6-sol A cells 3 `official-tool` (parent: "the agent confirmed the approved Playwright generator tools are working", one with 33 `.playwright-mcp/` files) and 9 `blocked`; gpt-6-astra 12 `blocked`; the compat-diag astra run `official-tool` (20 `.playwright-mcp/` files, "browser setup succeeded"). One compat-diag sol run classifies `unverified` although its summary describes the generator's browser session (the parent deleted the snapshot files first): the primary view is conservative and can drop genuine cells. The first regular expressions were written after reading only those transcripts. A review found that they accepted negations ("was not working", "isn't available", "never called") and plan narration ("ask it to write via `generator_write_test`") as affirmation; the revised patterns judge sentence by sentence with negation and intent guards, no longer accept "via/through <tool>", and the test suite carries those sentences as negative controls. They are still tuned on a small stored sample and not validated on unseen transcripts.

Five views are computed for every model. **primary** (the decision view): arm A cells of class `official-tool`, arm B cells whose source A cell is `official-tool`, all arm C cells, aborted cells removed. **itt** (sensitivity): all 72 cells as run. **upper** (sensitivity): primary but `unverified` A cells also count. **load_clean** (sensitivity): primary without cells started above load 40 (an arm B cell is removed together with a load-flagged source arm A cell). **as_treated** (sensitivity, defined in advance): arm A `official-tool`; arm B reviewing an `official-tool` cell and having read the reviewer skill and run the scanner; arm C cells that read SKILL.md and a reference file and ran the scanner (`treated_core`). Every per-model contrast is printed with a treatment-fidelity table (arm C's seven key steps, arm B's reviewer steps, arm A's rollout evidence). The primary view is a per-protocol analysis: it selects arm A and B cells on evidence that the tools ran, a post-randomization variable that may correlate with the outcome, while arm C is unselected. The verdict is the primary view; `summary` prints per contrast whether itt, upper or load_clean give a different cross-model verdict and reports such a discordance next to the primary one without letting it override.

## Decision rules (fixed before any scheduled call)

1. **Per model and contrast** (C vs A, B vs A, C vs B), v1's rule applied to a view's cells: evaluable only if both arms have at least 6 delivered spec files in the view and share at least 5 tasks; then `suggestive: X better` if X's per-task refactor survival is higher in at least 5 of the 6 tasks and its clean-3/3 rate, effective fault kill, scanner P0 and scanner P1/P2 are not worse (scanner totals compared per cell, equal to v1 when the arms have equal cell counts); otherwise `nothing`. Ties and 3-3 splits are `nothing`.
2. **Across models, Codex family only, primary view only.** N = complete models (72 scored cells, at most 3 aborted) for which the contrast is evaluable. N < 4: `not evaluable`; one lineage only: `not evaluable (single lineage)`; otherwise `consistent: X better in k of N models` only if at least max(2, ceil(N/3)) models carry `suggestive: X better`, none carries the opposite label and the agreeing models span both lineages; else `not consistent` with counts. No intermediate wording. For every feasible N (4 to 6) the threshold is just 2 agreeing models, a weak bar, so the positive verdict is worded as a count of agreeing models and not as a replication.
3. An incomplete model is shown descriptively and excluded from N. No p-values in the labels or the rule; the pooled analysis is separate, descriptive and draws no verdict.

**Why this N rule and this threshold (offline simulation, `power` subcommand, seed 20261016, 1500 replicates per cell).** The complete recorded table is regenerated for 4 repetitions and the actual fixed evaluability minimum of 6 official A cells on at least 5 tasks; the former `3 * repetitions` shortcut would incorrectly require 12 cells. A pilot-sized effect (A 0.5 to C 0.917) gives a positive per-model label about 59% of the time at perfect fidelity. Chosen-rule power at N = 4 / 5 / 6 is:

| Arm A fidelity | N = 4 | N = 5 | N = 6 |
|---|---:|---:|---:|
| 1.0 | 0.6727 | 0.7447 | 0.7933 |
| 0.75 | 0.5373 | 0.6093 | 0.6720 |
| 0.5 | 0.2073 | 0.2833 | 0.3260 |
| 0.25 | 0.0000 | 0.0033 | 0.0073 |

**The unchanged rule no longer meets the earlier 1% simulated false-agreement target:** maximum null agreement in either direction is 0.0447 (N = 6, shared-task null, fidelity 0.75; all null scenarios and fidelities, N = 4 to 8). Without the lineage requirement the maximum is 0.0753. The v1 ceil(2N/3) threshold gives power 0.5247 at N = 6 and perfect fidelity. With an N floor of 3, maximum null agreement is 0.0127 and perfect-fidelity power 0.4827. N = 3 and N = 8 are sensitivity scenarios, outside the six-model roster's evaluable range. No threshold was changed by this build: **the owner must decide before freeze whether to retain the descriptive rule with this disclosure or recalibrate its threshold.** Raising the agreement minimum to 3 also requires a new simulation. The simulation ignores guard conditions and post-randomization selection. Ignoring guards upper-bounds each individual-model directional label probability within the simulated model. Cross-model probabilities are simulation estimates, not upper bounds: a guard can remove an opposing label and create agreement. "Not consistent" remains no evidence of no effect.

The four Claude models of v1 and the Codex models of v3 are combined only descriptively: `summary --v1-dir <v1 output>` lists the v1 per-model labels beside the v3 labels (v1 Codex rows marked as the frozen v1 harness). ## Schedule, load, aborted cells, per-cell records

- One call at a time. Entry preflights for all roster models first; then one admitted model at a time in roster order; within a model the seeded v1 two-phase algorithm recomputed for 4 repetitions (48 A and C cells shuffled, then 24 B cells, so B always follows the A cell it reviews). A v2 driver holds a campaign lock file, refuses to start while a v1 or v2 driver process exists, and uses scoring and staging ports offset by 3000 from v1's (v1 uses 5300+ for scoring and 6300+/6700+ for staging, so v2 uses 8300+ and 9300+/9700+; there is no occupancy check, so make sure nothing else listens there).
- Load: a cell waits up to 1800 s while the 1-minute load is above 40, then starts regardless. `load_at_start` above 40 **flags** the cell; flagged cells are kept in the primary view and removed only in the `load_clean` sensitivity.
- Aborted cell: infrastructure error after the inherited in-call retry, usage or rate limit, Docker or container failure, disk floor, or arm A setup UNAVAILABLE (the v2 runner marks such a row `infrastructure_error`, which the inherited v1 loop does not, so that the retry and stop rules below apply to it). A timeout and an empty source for arm B are not aborts. Aborted cells are retried by later resumes at most twice, score 0 in `itt`, and leave every arm in the other views. More than 3 aborted cells make a model incomplete; three infrastructure-error cells in a row stop the campaign, and a usage or rate limit stops it at once.
- Per-cell record: rollout evidence, untruncated compliance, treatment steps, generation-config digests, token and pipeline records, selector status, fidelity class with evidence counts, setup status, spawn and wait census, aborted flag and attempt errors, `load_at_start`, `load_pause_s`, `load_flagged`, `load_at_finish`, `cell_started_utc`, `cell_finished_utc`, elapsed and setup seconds.

There are 24 calls per arm and model, 72 per admitted model and at most 432 scored calls across six models. Including at most 12 real entry calls and one initial harness check gives a baseline of 445 calls; infrastructure retries and repeated checks are additional. At the 1500 s generation/entry timeout and 420 s harness-check timeout, the serial nominal generation-timeout budget is 30 h per model, 180 h for all scored calls, or 185 h 7 min including baseline entry/check calls. This is not an elapsed-time forecast or a hard upper bound: setup, scoring, load waits and retries add time. Smoke diagnostics are separate (at most 18 calls across all six models).

## Smoke diagnostics before freeze (non-data; not run in this build)

`smoke --allow-live --output <external-directory> [--model <roster-id> ...]` does not require or create `freeze.json`. Choose models with repeatable `--model` (default: first roster model). It makes at most 2 arm-A calls and 1 arm-C call per model on the preflight task `v2-01`, without retries. It records availability, per-cell CODEX_HOME sessions persistence, MCP reachability, child-rollout parsing and parent/child token usage. It refuses output inside the repository, `~/.cache/e2e-skills-bench` or either resolved configured campaign root (including environment overrides), including symlink aliases, before calls or writes. Every output is **non-data**, cannot feed `analyze` or `summary`, and cannot satisfy freeze-bound harness checks or entry decisions. The generator calls use arm A's role restrictions; no smoke output is a scored or preflight campaign cell.

## Limitations

Six task clusters and four repetitions per arm and model; the same synthetic fixtures. The classifier needs positive evidence and under-counts genuine runs. Under multi_agent v2 the child's tool calls are not in the parent stream; the persisted child rollouts are the primary fidelity signal now, but the rollout schema was read from host Codex CLI 0.157 to 0.159 rollouts and the persistence mount has never run live, so until the live check passes fidelity is inferred, not observed. Arm A is a generic native agent following the generator definition with the server session-wide, not the role-scoped agent v1 asked for, and it preserves the 19-tool generator/browser allowlist while using the container as its isolation boundary and explicitly approving that server's tools; live acceptance and child inheritance remain unverified. The host catalog lists `multi_agent_reasoning_effort` xhigh for gpt-6.1-sol and gpt-6-astra while every cell runs at medium; whether a spawned child inherits that setting was not verified, so arm A's child may run at a different effort than arm C's parent for those two models. The compat flags also change arm B's command line. The generation-phase config (reuseExistingServer true) differs from the scoring config (false) by design; it changes what every arm's model observes when it runs its own tests, not the arms' relative treatment. The as_treated view and the fidelity tables select on post-randomisation behaviour (per-protocol); step detection is textual and reads the parent stream only (a command run by a spawned agent, for example a reviewer child running the scanner, is not seen); the scanner step counts an executed `scan.sh` (a bash/sh invocation or a direct run), the looser mention count is kept beside it. The headline metric is, empirically, a selector-hygiene indicator; the secondary refactor classes that would separate hygiene from robustness are not built. The cross-model rule remains descriptive and now exceeds the earlier 1% simulated false-agreement target; threshold recalibration remains an owner decision. A systematic harness difference between arms on these six fixtures looks like an effect to any cross-model rule. Models run on different days and loads; model ids are provenance. Before writing this protocol the authors read the stored cells of gpt-5.5 (pilots), gpt-6-sol, gpt-6-astra, claude-sonnet-5-5 and the compat-diag runs, and no other v1 model.

Smoke output refuses any `.git` file or directory ancestor, including sibling worktrees. Smoke stages a disposable Git repository before the adapter call; the adapter refuses a missing project-local repository before any model launch. Offline tests assert both boundaries.
