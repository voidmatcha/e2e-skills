# Thin-layer autoresearch loop v1

Status: **offline build; not frozen; no calls made; repaired after a first independent review (R1 to R9, see the repair log below); a second independent review (F1 to F10, see the second-review log below) is repaired offline; a fresh independent PASS is still required before freeze**. This protocol optimizes the thin rules layer ([THIN-RULES.md](../generator-thin-layer-v1/THIN-RULES.md)) on development tasks only. The machine-readable contract is [protocol.json](protocol.json); the runner is [run-generator-loop-thin-v1.py](../../scripts/evals/run-generator-loop-thin-v1.py), with [offline tests](../../scripts/ci/test-generator-loop-thin-v1.py). It makes no release, unseen-task, significance or cross-model claim.

It forks [generator-loop-v2](../generator-loop-v2/README.md), which stays unchanged as an archive (it was never frozen or run and optimized the heavy skill under arm C). The fork follows the Claude review stream `loop-v2-retarget` (findings L1 to L11). Evidence motivating the thin layer: refactor survival mostly measures avoiding id and class selectors, review passes dominate pipeline cost (the reviewer pass is about 58 to 59 percent of generation plus review dollars on Claude, from an independent finished-run analysis, not a measurement here), and the strongest model scored 1.00 on every arm at about five times the cost of the full skill.

## What is optimized

The edited object is exactly one file: a campaign copy of THIN-RULES.md (v0 is 1,883 bytes, 11 checklist lines, estimated 471 tokens). The frontmatter and the heading are frozen byte for byte. The body is only checklist lines of the form `- [ ] text`. Each iteration the researcher may add, delete, or reword exactly one line in place; a move or any two-line change is refused, and deleting a rule is a legal hypothesis. Machine-checked limits: ASCII only, at most 260 bytes per line, at most 2,400 bytes in total (thin-eval's own hard ceiling is 2,500), at most 12 lines, net growth at most 250 bytes per iteration. At the byte ceiling only non-growing edits are valid, and at the 12-line cap an added line is invalid (a reword or a delete stays possible): one saturation rule for both limits, stated to the researcher in its task and recorded when no candidate is found (second-review F10; v0 has 11 lines, so exactly one add can still fit).

The layer is mounted exactly as in thin-eval arm D: read-only at `/work/skill/thin-rules/SKILL.md` plus one prompt line. Candidate and incumbent differ only in the mounted bytes; the runner copies the slot's bytes, checks the copy before and after every attempt, and an offline test compares its `d_command` with the thin-eval source. The synthetic D and reference-A cells also carry the thin-eval generation-phase repairs (next section). v0 already encodes the id/class selector ban and the no-`toHaveClass` rule that earlier audits found on these development cells. Those two mechanisms are the baseline, never loop gains.

## Generation-phase repairs (F3 and F5)

The first review (R1) found that the loop's cells used the unrepaired v4 generation staging, so every generation-time test run reused a server that the child's browser exploration had already mutated. All three synthetic dev tasks are stateful (reset, delete and restore endpoints), and this is the failure that polluted 4 of 9 arm-A cells in the Codex v3 mid-run check. Pollution would have depressed D survival (a spurious HEADROOM), entered the redacted packet as failing cells the researcher is asked to fix, and added noise to a one-cell-resolution decision. The synthetic D and reference-A cells therefore use the same two repairs as thin-eval-v1:

- **F3 split ports.** The staged generation config and app read `GEN_EXPLORE_PORT`, which only the MCP server process receives (one extra `-c mcp_servers.playwright-test.env` entry). The parent's single test run starts a fresh application process (`reuseExistingServer` false) and can never attach to the explored one. Scoring is untouched.
- **F5 git excludes.** `node_modules` and `.playwright-mcp/` are listed in `.git/info/exclude` before the baseline commit, and the collector keeps the snapshot files out of the out-of-scope write check, recording them as `mcp_artifact_writes`.

The repair functions are copied line for line from the thin-eval runner and an offline test compares their syntax trees with the thin-eval source; only the name `integration` resolves, lazily, to this campaign's one machinery stack. The exploration port reaches the MCP server of synthetic cells only; the availability probe never gets it. `analyze` refuses any synthetic cell whose record does not show the split-port isolation. The Zeppelin dev cells use one shared external proxy with per-cell note namespaces and no per-session port, so F3 does not apply to them and they receive only F5. That leaves a residual hazard (the child's exploration writes notes in the cell's own namespace that the parent's test run may then see); it is disclosed here, recorded per cell as `server_isolation: shared-proxy-note-namespace`, and is an owner decision (keep the two Zeppelin tasks with the disclosure, or drop them until a Zeppelin-specific repair is proven live).

## Arms, tasks, sequencing

- **Loop arm D**: the official generator (arm A treatment, 19-tool allowlist, auto-approved MCP, danger-full-access) plus the layer. **Reference** `ref-A`: ten cells of the official generator without the layer at iteration 0, descriptive. **E** (D plus the scanner-only gate) is not looped; the final incumbent should be compared once against v0 in E in a separate preregistration. No reviewer arm, no scanner gate, no heavy skill.
- **Tasks** (owner decision 2026-10-15, pre-freeze): the default dev tasks are the synthetic dev split only, `v2-11`, `v3-08` and `v2-18`, two repetitions each (six cells per batch). The Zeppelin dev tasks `zep-sidebar` and `zep-note-rename` are dropped from the default list and kept as an **opt-in list** (`prepare --include-zeppelin`, ten cells per batch, the earlier numbers below) until a Zeppelin-specific repair of the shared-proxy hazard is proven live. **Hazard (disclosed):** Zeppelin cells use the shared external proxy, so the F3 stale-server hazard (the generation-time test run reuses a server that the child's browser exploration already mutated) is not repaired there; only F5 applies. All tasks are hard-asserted disjoint from the six thin-eval tasks, the Zeppelin evaluation pair and the sealed vault; the runner never enumerates other task directories and has no final-evaluation command. The pool handed to `prepare` must still be a staged copy holding exactly `tasks/zep-sidebar` and `tasks/zep-note-rename` (no `sealed-eval/`, `harness/`, `results/`) because the shared runtime stages it (its reference calibration runs only with the opt-in), but no Zeppelin cell is scheduled unless the opt-in is chosen. The mode is bound in the campaign config at freeze.
- **Sequencing**: the loop starts only after the Codex v3 campaign and thin-eval-v1 have finished. `prepare` refuses unless a thin-eval gate record for the chosen model says HEADROOM (D survival or fault kill below .95, layer read in at least 90 percent of D cells, the same rate every loop decision needs), the thin-eval freeze exists and binds the same v0 bytes, the gate record binds that freeze and the very results file the model selection read (their sha256 digests are recorded and compared), the model selection comes from the rule below, and the campaign root is under the home directory (container bind mounts). The machine-wide campaign lock is held for every whole batch, synthetic cells included, so nothing else runs on the host during a batch.
- **Model**: chosen by the outcome-blind rule `outcome-blind-ad-v1`: among Codex candidates with finished thin-eval evidence (at least 12 arm A and 12 arm D cells, results complete; any other model is skipped and listed with its reason, never ranked, so a partly run model cannot block selection and the chosen model can always pass the thin-eval gate), rank by the share of arm A and D cells with hard official-tool evidence, then delivery share, then the share of D cells with the layer-read indicator, then roster order. Only five process and delivery fields are read; quality, kill, selector, scanner, token, cost and time fields are never read (a test passes cells that fail on access to those fields). `gpt-6-sol` satisfied the superseded arm-C rule and is the lowest-invention proposal, but this offline build could not compute the new rule on the finished campaigns, so the choice is an owner decision recorded by `select-model`. Medium reasoning effort. A one-token availability probe runs inside the lock at the start of every generation batch and is retried once; two failures in a row write `BLOCKED.json` and end the loop. A rate or usage limit is transient: it is recorded as `RATE_LIMITED`, refuses the batch before any cell starts, and does not block the campaign (rerun after the limit resets). No model is ever substituted.

## Batches and decision

Iteration 0 runs `aa1` and `aa2` (D with v0, six cells each; ten with the Zeppelin opt-in) and `ref-A` (six cells; ten with the opt-in), in adjacent triples with shuffled slot order; an optional `aa3` (owner decides at prepare) adds a third A/A batch. **Headroom gate**: if the layer was read in fewer than 0.9 of the cells of any D-v0 batch (all 6 of 6 by default, since 5 of 6 is .83; 9 of 10 with the Zeppelin opt-in), the loop stops with LAYER_NOT_READ (every later decision needs the same rate in both batches of a pair, so screening cells would otherwise be spent on NOT_APPLIED pairs); otherwise, if any D-v0 cell is not official-tool it stops with LOW_FIDELITY (every later decision requires the official-tool process in both batches of a pair); otherwise, if D-v0 survival is at least .95 and kill over all cells is at least .95 across the aa batches, it stops with NO_HEADROOM. The same NO_HEADROOM stop applies, and is now recorded as `no-headroom.json`, when an iteration packet finds no failing cell.

Each iteration runs a **screening pair** (incumbent and candidate, six cells each by default and ten with the Zeppelin opt-in, adjacent interleaved slots). Only an ADOPT verdict triggers a **confirmation pair**: fresh incumbent and candidate cells with their own seed. Adoption needs ADOPT in both stages (ADOPT_QUALITY only if both are ADOPT_QUALITY, otherwise ADOPT_COST) and then the **pooled confirmation gate**: the screening and confirmation cells must be disjoint, no task may be lower for the candidate, and on the quality path the pooled net gain must be at least 3 cells (a quarter of the pooled mean by default, .15 with the opt-in). A screening ADOPT followed by a confirmation non-adopt, or by a pair that fails the pooled gate, is REJECT_ON_CONFIRMATION. The confirmation re-runs the same development tasks with fresh cells; it does not add tasks, so the pooled threshold is the stated compensation, not a cure for task-level overfit (second-review F4). An adopted candidate's two batches become the next incumbent's A/A history, filtered by exact layer sha256. Verdicts: ADOPT_QUALITY, ADOPT_COST, REJECT, NOT_APPLIED, NO_CANDIDATE, REJECT_ON_CONFIRMATION.

Primary metric: the unweighted task mean of delivered, clean-3/3 and refactor-pass cells; no deliverable or a timeout is zero. A candidate adopts for quality at survival delta at least +0.10 (a single net cell on the default tasks, since one cell moves the three-task mean by .17, which is why the task and pooled requirements below exist); otherwise for cost at survival not lower and a 15 percent drop in tokens (seconds at most +10 percent) or seconds (tokens at most +10 percent) with the verification-executed rate not lower (unknown blocks it). All of these must hold:

| Guard | Rule |
|---|---|
| Applicability | layer read in at least 0.9 of the cells (6 of 6 by default, 9 of 10 with the opt-in) of both batches, else NOT_APPLIED and no credit |
| Clean rate, kill (all cells, clean cells), scanner P0 and P1/P2 totals | A1 rule, profile below |
| Official-tool fidelity (requirement) | every cell of the candidate batch and of the incumbent batch it is compared with has fidelity class official-tool; any other class or none is a REJECT on both adoption paths, so a rule that makes the model bypass the official generator cannot be adopted on cost (F1) |
| No task regression (requirement) | the candidate's survival count is at least the incumbent's on every task, on both paths (F4) |
| Timeouts | none in the candidate batch (a wall-clock timeout marked by the adapter is scored zero; if its usage is unknown the cost is recorded as a lower bound and the batch stays analyzable, which can only make a candidate look more expensive against it) |
| Slow cells | at most one candidate cell with an attempt over 1,200 s |
| Layer size | at most 2,400 bytes and at most +250 bytes against the incumbent |
| Processed tokens | at most +10 percent against the same-pair incumbent and against the iteration-0 D mean |
| Cached-inclusive tokens | at most +10 percent against the same-pair incumbent and against the iteration-0 D mean |

The cumulative checks stop a chain of individually legal +10 percent steps from compounding to 1.1^n. Every decision also reports the exact one-sided task-stratified permutation p (descriptive, never a gate), the min/max/range of every metric over all incumbent-layer batches, whether the survival delta is within that width, per-task counts and layer bytes. One cell moves survival by .10, so only effects of roughly +.2 or more are detectable on ten cells, and on six cells one cell moves survival by .17, so the default is coarser still.

**Guard profiles.** `strict` is the audit's A1 rule: no tolerance on the five rate and count guards. `noise-tolerant` allows a one-cell clean-rate drop (.10), a .05 kill drop in either view, one extra scanner P0 and three extra P1/P2 findings (these tolerances are assumptions). **Owner decision 2026-10-15 (pre-freeze): `strict`.** A low false-adopt rate is preferred to missing a real improvement, because a false adoption stacked on a tiny rules file is the main risk; `prepare` defaults to `strict`. `noise-tolerant` stays registered but is not the chosen profile and would need a new owner decision before freeze. No pre-freeze variance measurement is part of this design (the A/A batches run after freeze).

## Stop rules and budget

The loop ends at the first of: BLOCKED (two failed availability probes or a void batch); NO_HEADROOM; LAYER_NOT_READ; LOW_FIDELITY (a D-v0 batch with a cell that is not official-tool); six iterations; two consecutive non-adoptions (REJECT, NOT_APPLIED, NO_CANDIDATE and REJECT_ON_CONFIRMATION all count); a layer at its ceiling with no valid shrinking candidate; the generation budget of 162 cells by default (18 baseline plus 6 times 24, or 168 with `aa3`; 270 and 280 with the Zeppelin opt-in: 30 baseline plus 6 times 40); or 12 researcher draws. The budget is checked before every batch. "No adopted change, keep v0" is a valid recorded outcome.

**Void batches and retry (second-review F3).** Void cells count toward the budget: a void stage is charged the cells it started (recorded in `VOID.json`; its whole schedule when unknown), an archived void stays charged, and a process killed mid-stage is charged its whole schedule. An infrastructure failure reported by the adapter writes a void marked retryable; input drift, a changed candidate, a namespace violation and score voids are terminal. `retry-void --campaign C --iteration N [--stage S]` archives a retryable, never completed, scored or analyzed void under `iterations/NN/void/`, writes a ledger entry under `retries/`, and lets the same deterministic schedule run again. At most one retry per stage and two per campaign, a retry must still fit the remaining budget, the partial records must be unchanged since the void (their digests are recorded in the marker), and no cell content is read. The voided cells never enter a decision, a packet or a noise estimate, and the schedule is not reseeded, so a retry cannot be used to resample a disliked outcome. A hand-written `VOID.json` is outside what offline code can prevent. With the Zeppelin opt-in a retry reuses the cell serials and so the note namespaces (unexercised live).

The noise levels are assumptions, not measurements. **Low power, stated plainly (F6):** at a true +.2 the chosen `strict` profile adopts with P(iteration adopts) = 0.0015 and P(loop adopts at least once) = 0.0030 (the review's roughly 0.004 was the earlier figure, before the added gates); `noise-tolerant` adopts in about 1.5 percent of iterations and 2.9 percent of loops. Under the assumed noise the chance of any adoption in a whole loop at a true +.2 is about 0.3 percent for `strict` (the chosen profile) and about 2.9 percent for `noise-tolerant` on the default tasks, so the realistic outcome is "keep v0". The strict choice accepts that: a false adoption stacked on a tiny rules file is judged worse than a missed improvement. The simulation is a prior, not a forecast.

## Researcher, redaction and review

The researcher is a pluggable command; the default is a Claude subagent invoked by the owner in the staged workspace (`researcher-stage`, then `researcher-ingest`), and `researcher-run` can plug in another command. It refuses Codex, restricts the environment and records the researcher identity (family, model, session id) and its usage when known (otherwise "unknown", never zero). Workspace: `TASK.md`, `incumbent/THIN-RULES.md`, `packet.json` and, if enabled, read-only copies of the three public product reference files. Its workspace is a fresh private temporary directory outside the campaign tree (recorded in `staged.json`), so no relative path from it reaches the forbidden-token file, the private packet records, raw artifacts or scores, and the exact bytes it wrote are preserved in the draw as `researcher-out`. The isolation is by location and instruction only: the environment keeps `HOME`, there is no filesystem sandbox, and the transcript scan listed under the live checks (outbound fetches and file access) remains required. The workspace holds no repository, campaign, task truth, forbidden-token file, call IDs or case names. At most two draws per iteration are allowed and both are preserved; two spent draws without an accepted candidate is NO_CANDIDATE, which counts as a non-adoption.

The packet is deterministic and literal-free: task labels T1 to T3 (T1 to T5 with the Zeppelin opt-in), opaque cell references, outcome flags, closed-vocabulary error classes (for example `strict_mode_violation`, `locator_wait_timeout`, `assertion_mismatch`), the thin-metrics static hygiene counters, and a skeleton of at most three failing specs in which every literal becomes a kind tag and every unknown identifier is dropped. A cell is failing if it was not delivered, timed out, was not clean 3/3, failed the refactor, has kill rate below .8, or did not use the official generator surface (fidelity class other than official-tool).

**Skeleton redaction limits (F8).** The skeleton is not a privacy boundary. It drops comments, replaces every literal by a kind tag (css-id, css-class, css-attribute, text; a template literal and a regular expression get their own markers) and drops every identifier except Playwright API names and words of up to four letters, which stay verbatim. What survives: the order and shape of the user steps, the locator strategy, numbers (counts, timeouts), whether a literal was an id, a class or text, and short application words (a four-letter noun is kept). It is cut at 2,500 characters. The derived forbidden-token screen catches echoes of the raw evidence, not a paraphrase of the structure. The packet therefore leaks the outline of the failing tests by design, because that outline is the evidence the researcher needs; only literals and long identifiers are removed.

Candidate wording is screened against tokens **derived from the raw packet evidence** (spec literals, application identifiers, error text and plan behaviors), minus a generic vocabulary built from words that occur at least three times in the public product reference files plus the incumbent's own words; a fixed ban on grader vocabulary (refactor, restyle, rename, markup, grader, scorer, mutant, held-out, benchmark, eval, and since the second review oracle, rubric, score, grade, hidden test, reference solution, fault, injected, kill rate, survival, calibration) always applies, and the screen looks through separators and punctuation inside a word ("side-bar", "re_name"), spaced-out letters and squashed spellings (F7). Violations are reported by category, never by token. This is a screen, not a proof: a paraphrase, or a task-specific instruction smuggled in general words, is not detectable offline.

**Static inner stage (F5, F7).** Before any live cell, an offline, deterministic, pre-registered stage screens the added line at researcher ingest and again at candidate validation: a minimum length of 40 bytes, a directive verb, no hedging, no near-duplicate (token Jaccard 0.7) of another rule, no endorsement of a pattern the e2e-reviewer scanner flags (a flagged pattern may be named only to forbid it, or under "only with", "unless" or a JUSTIFIED marker), no polarity contradiction of an existing rule on the same API name, and no risky action: an install or download, network access, credential or secret use, a write outside the generated tests or a destructive command, or skipping or bypassing the official generator and its tools. The scanner itself is not run on reference specs under the candidate text because it reads specs, not rule text, so that run would not depend on the candidate. The stage is a fixed-pattern filter that spares live cells on obviously malformed or risky candidates; the independent wording review and the official-tool requirement remain the real protection. The three phrases that passed the old fixed list are refused by the derived screen. A candidate also needs a recorded independent Claude-family wording review (different session from the researcher, different model from the generator, exact prompt and output files whose digests are checked; the prompt is recomputed) and a passing `scripts/ci/review.sh` run on a disposable checkout with the candidate overlaid (a weak check by construction: `review.sh` does not inspect the layer text, so it mainly confirms the repository stays healthy; the grammar, the derived screen and the wording review carry the real load).

## Alignment with thin-eval arm D

What matches thin-eval arm D: the D prompt line is byte-identical (`prepare` refuses otherwise, and a test compares them), the layer is a read-only nested mount at the same path, and the tool surface is the shared official-generator surface (19-tool allowlist, auto-approved MCP). What does not, with the cheap items fixed and the rest disclosed (F9; also `thin_eval_alignment` in `protocol.json`):

The fidelity classifier is the shared one, so its evidence limits apply (a parent-stream indicator for the layer path; a child-only read can be missed). The loop's cells are not thin-eval-comparable and must stay out of any thin-eval comparability claim.

## Machinery, freeze set and integrity

One machinery stack: `run-generator-oss-eval-v1.py` and the Codex v4 modules it imports. Synthetic and Zeppelin cells are generated, scored and costed through the same module instances (an offline test proves one engine, evidence and compat instance, and that the generation and scoring guards act on that engine). The v2 core, the v3 runner and the thin integration stack are not imported; `generator_thin_metrics_v1.py` supplies static counters only. The freeze set is computed, not hand-listed: the static closure of imports and path strings from the runner and the modules it loads, united with every repository script reachable through the loaded module graph; a test injects an unbound module and shows it is detected. Freeze also binds the protocol, README, tests, v0 and the baseline copy, the library files, the model selection, the thin-eval gate, plans, schedules and DEV task bytes. All outputs are exclusive and append-only; an interrupted or infrastructure-invalid batch is VOID and cannot decide. No freeze, calibration or live command works until `independent-review.json` records a PASS by a reviewer other than the builder for the exact runner, protocol, README and tests (finding L1). The record is JSON: `verdict` "PASS"; `open_material_findings` 0; `reviewer` and `builder`, each `{id, model}` with different ids and different models; and `reviewed_sha256`, an object of the sha256 digests `{runner, protocol, readme, tests}` of the exact files reviewed (any later byte change stales it). Because this repair changed those bytes, the earlier review does not carry over.

## Verification limits and required live checks

This build is offline only. Tests with inert generators and scorers verify arithmetic, boundaries, bindings, orchestration and file contracts. They cannot establish model availability, that the model reads the layer or passes it to the child, token accounting in a new CLI build, browser correctness, or the Zeppelin D path (the thin-eval Zeppelin amendment is specification only; this runner calls the OSS generate function with arm A staging plus the layer mount and the D line, which has not been run). The synthetic dev tasks use one-paragraph truth-derived plans (a single "Behavior 1" built by the shared plan function), not curated multi-behavior plans like the thin-eval and v3 synthetic tasks, so the generator's scenario structure and the plan-derived vocabulary differ from thin-eval's D cells; the loop's cells are not thin-eval-comparable and must stay out of any thin-eval comparability claim. Mutant attribution, when a kill lacks a valid-detection label, is an offline `adjudicate` step: give the adjudicator only call IDs and the saved failure texts (never slot names, layer hashes or the schedule), keep the slot-to-call mapping with the coordinator who files the annotations (the file is keyed by slot, call ID and defect because the runner applies it), and publish only complete attributions. Before a live loop, verify separately: the availability probe; read-only mount enforcement and the layer-read indicator in transcripts; child instruction receipt; D versus A argv and prompt parity on the real adapter; token and cached-token accounting including children; a Zeppelin D cell with namespace cleanup; a no-op researcher smoke and outbound-fetch scan of researcher and generator transcripts; the inherited Git staging isolation; host idleness during batches; the split-port exploration port actually reaching the MCP server and the application restarting for the parent's test run on a real synthetic D cell; the F5 wrapper around the external Zeppelin loop's `commit_baseline` (it pre-creates `.git/info` before the loop's own `git init`, which plain git tolerates, but the external function is not in this repository); the rate-limit patterns against the real CLI's error text.

Three reused synthetic development tasks by default (five with the Zeppelin opt-in, whose two tasks come from one upstream change), one model and adaptive repeated decisions cannot establish generalization. An adopted layer needs a separately preregistered final validation on tasks no campaign has used and at least one other model, comparing D with v0, D with the final layer and optionally E, A and the unchanged v0; this build neither prepares nor authorizes it.
