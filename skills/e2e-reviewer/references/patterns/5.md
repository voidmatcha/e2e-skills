#### 5. Bypass Patterns `[grep-detectable]` (5a P0, 5b P1)

Two sub-patterns that suppress what the framework would normally catch — making tests pass when they should fail. Listed under P0 because 5a is a silent-pass bug; 5b is a P1 actionability issue documented in the same section for proximity.

**5a. Conditional assertion bypass** — a load-bearing assertion for the scenario's promised outcome is gated behind a runtime condition. If the branch is false, that outcome is never verified and no independent unconditional meaningful postcondition or failure-producing action can fail the test.

```typescript
// BAD — if spinner never appears, assertion never runs
if (await spinner.isVisible()) {
  await expect(spinner).toBeHidden({ timeout: 5000 });
}
```

**Rule:** Flag P0 only when the conditional assertion is load-bearing for the title/action's promised outcome and the false branch has no independent unconditional meaningful postcondition or failure-producing action. Do not flag a conditional diagnostic or optional-state assertion when the scenario still has an unconditional assertion or action that meaningfully proves or enforces the promised outcome. A pre-action state check, or an absence assertion a missing value also satisfies, is not that proof. Move environment- or feature-flag gates for a required outcome to `beforeEach` / declaration-level `test.skip()` so unsupported runs are skipped explicitly rather than passing silently.

A fallback assertion against a generic or merely similar UI element does not prove the promised outcome when the primary confirmation is absent. By contrast, conditionally dismissing an optional blocker before an unconditional promised-outcome assertion is an action-only branch, not this bypass. Judge both from code-visible behavior; do not infer that a runtime blocker actually appears. The scanner emits a #5a candidate only for a gate with an assertion on exactly one path: an `if` whose branches provably hold no assertion, because every call in them acts on a proven Page or Locator or writes to the console (for example `if (await banner.isVisible()) await dismiss.click()`), and an `if`/`else` that asserts on both paths are not candidates. A branch that calls any other helper keeps the candidate, because the helper may assert. It also skips gates fixed by the test's own literal data when evaluation shows the branch runs, and a branch that asserts the very value its condition tests. A gate in a module-level helper whose condition reads only the helper's own parameters is reported at each test call that passes a runtime value for them, not in the helper.

The scanner reports one #5a shape as a mechanically confirmed P0 instead of a candidate, so `--fail-on p0` fails on it: an `if` with no `else`, written directly in the body of a proven Playwright `test(...)` or `it(...)` callback, whose then-branch holds every assertion of that test as a direct `expect(...)` call to an import named `expect` that is proven to be Playwright's, and whose condition, or the one same-function `const`/`let` it reads, makes a non-waiting `isVisible`, `isEnabled`, `isChecked`, `isDisabled`, `isEditable`, `isHidden` or `count` read on a proven Page or Locator (a `.catch(() => false)` wrapper is allowed). Every other call in that test must act on a proven Page or Locator or write to the console. Whatever the scanner cannot prove keeps the candidate for review: a helper or page-object call anywhere in the test, which may assert; an assertion inside a nested function, including `test.step`, `expect.soft` or `expect.poll` callbacks; an aliased or wrapped `expect`; a receiver with unresolved provenance, such as a custom fixture object; and an `else` branch.

The scanner lists a #5a candidate as `[P2?][REVIEW-HINT]` instead of `[P0?]` when its condition reads only run configuration: `process.env.*`, `process.platform`, the `browserName`, `isMobile` or `viewport` fixtures, `testInfo.project.*` or `test.info().project.*`, `viewportSize()`, an imported `isCI`, a parameter named `browserName`, `isMobile`, `isCI` or `projectName`, or a never-written `const` holding one of these, combined only with literals, operators and pure string or array helpers. Such a gate is decided by configuration, not by product state, so it cannot hide a product break inside one configuration; whether CI runs the configuration that executes the assertion is the review question. A gate on the `browserName`/`isMobile` fixtures or `testInfo.project.name` that is true in some project of every static Playwright config running the file is still dropped outright. A condition that also reads product state, or a local value merely named `isMobile`, keeps the P0 candidate.

**#5a with unresolved source (semantic review):** these limits block only the mechanical confirmation. Missing or unresolved source justifies NEEDS-CONTEXT only when that source could change the verdict. `count() >= 0` is always true for any receiver, and an `if` that gates the only assertion on the element's own count/visibility bypasses for any receiver type, so confirm those.

**#5a gates are judged one by one:** a project, environment or feature allowance (`testInfo.project.name`, a flag) explains only a gate whose condition reads that allowance. It never dismisses a gate on the observed value itself, such as `if (keyAfter) expect(keyAfter).toBe(expected)`. When that value gate holds the only post-action assertion a missing or wrong value can fail, confirm it; a pre-action check or an absence assertion elsewhere in the test does not cover it.

**5b. Force true bypass** — `{ force: true }` skips actionability checks (visibility, enabled state, pointer-events), hiding real UX problems that real users would encounter.

**Rule:** Each `{ force: true }` (including quoted keys and whitespace before the colon) on a Playwright/Cypress action must have `// JUSTIFIED:` on the line above explaining why the element is not normally actionable. Unrelated APIs such as `fs.rm(..., { force: true })` or `apiClient.request({ force: true })` are not findings. Without a comment, flag P1 and anchor the finding at the line containing the action option.
