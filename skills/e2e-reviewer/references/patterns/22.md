#### 22. Optimistic UI Without Call Proof `[LLM-only]`

**Symptom:** A test whose stated contract includes a backend write or persisted result clicks a write control and asserts only UI state that supplied implementation evidence shows is updated *optimistically*, before or regardless of the network call. The assertion can pass even if the promised write never occurs.

**Why it matters:** This is a false positive specific to write interactions: the visible behavior under test is produced client-side, so the test proves the click handler ran, not that the write reached the backend contract. A regression that drops the API call (refactor, early return, swallowed promise) ships green.

```typescript
// BAD — aria-pressed flips optimistically; passes with the POST deleted
await likeToggle.click();
await expect(likeToggle).toHaveAttribute('aria-pressed', 'true');

// GOOD — request proof + UI state
const call = page.waitForRequest(r =>
  r.method() === 'POST' && r.url().includes('/user/sentence/like'));
await likeToggle.click();
await call;
await expect(likeToggle).toHaveAttribute('aria-pressed', 'true');
```

**Rule:** Flag P1 only when the test or supplied acceptance contract promises a backend call or persisted result, repository evidence proves the asserted UI state is optimistic or survives deleting the write call (set after an awaited write without using its result), and no assertion proves the promised backend effect. Match the proof to the promise: a request/response observation, route-handler hit, or mocked-request capture can prove a promised call, but a promised persisted result needs equivalent persistence evidence from a server-backed reload/re-fetch assertion or independent persisted-state observation against a disposable backend. A stubbed or merely captured request does not prove persistence. Set up a request observer before the click when that is the chosen proof so a fast response cannot race it. Do not require a request assertion from every write-shaped interaction: a test scoped to client-visible UI state may intentionally prove only that state, and request details may be covered by a separate test.

**Detection (LLM):** First identify the outcome the test promises. Keep requirement evidence separate from implementation and environment evidence: cite the test title or supplied acceptance clause that promises a backend call or persisted result, then cite the optimistic update in the component, handler, helper, or fixture. A POST in application source or a comment describing persistent/shared infrastructure does not establish that promised outcome. Only when the promise exists, confirm that the asserted UI state updates optimistically before or regardless of the request, or would still appear if the write call were deleted. Flag when that optimistic state is the only proof and the spec lacks evidence for the specific promise: call evidence for a call, persisted-state evidence for persistence. Recommend a fix with the same distinction; do not offer a route stub or request capture alone as a persistence fix. Do not infer a backend contract or optimistic behavior from a write-shaped action name alone. Tests of pure client-side state and UI-only interaction tests that do not claim persistence are not hits.

**Write-evidence question (mandatory #22 discovery):** For every like/save/submit/delete click or form submit followed only by client-visible assertions (text, toast, count, or `aria-pressed`), inspect the handler and helpers even when the title does not mention a request. Ask: "What proves this write beyond the optimistic UI?" Then apply the **removed-call check** to every assertion offered as write evidence: would it still pass if the write call were deleted from the code path (not made to fail)? UI state set after `await <write>()` without using its result is not write evidence: with the call deleted nothing is awaited and the state appears at once. Trace evidence for the same action: an awaited matching request/response, an asserted mocked request or route-handler hit, server-backed reload/re-fetch or API state assertion, or a failure-path assertion tied to the rejected write. Mere route setup, an unrelated request, or reload without an outcome assertion is not proof. The evidence must be in the same test or its hooks/fixtures; a sibling test that covers the call may be cited but does not clear this one. If such evidence exists, do not raise this question as a missing-call gap; do not demand persistence unless the contract promises it. Skip explicitly UI-only/client-only contracts. If source proves optimism, or the asserted state survives the removed-call check, but the backend promise is unspecified, record `NEEDS-CONTEXT` with the action's `file:line` and this question in `Limitations/exclusions`, not as a confirmed finding or count. If source or helpers are unavailable, identify that missing evidence there. Apply #22 P1 only after its contract is confirmed; never infer a write or optimism from the button label alone. Failure-path coverage proves only the exercised failure, not successful persistence.

**Primary line:** Anchor #22 to the write-control action. The following UI-only assertion explains why the test is insufficient but is not the causal line.
