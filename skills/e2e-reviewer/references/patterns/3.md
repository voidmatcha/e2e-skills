#### 3. Error Swallowing `[grep-detectable + LLM]`

**Symptom (POM — grep):** empty/fallback Promise catch callbacks such as `.catch(() => {})`, optional-call `.catch?.(() => {})`, `.catch(function () {})`, or `.catch(() => false)` on awaited operations — caller never sees the failure. Async, named, and parameterized function-expression callbacks carry the same semantics and must not bypass review.

**Symptom (spec — LLM):** `try/catch` wrapping assertions — test passes on error instead of failing.

```typescript
// BAD POM — caller thinks execution succeeded
await loadingSpinner.waitFor({ state: 'detached', timeout: 5000 }).catch(() => {});

// BAD spec — silent pass on assertion failure
try { await expect(header).toBeVisible(); }
catch { console.log('skipped'); }
```

**Rule (POM):** Remove `.catch(() => {})` / `.catch(() => false)` from wait/assertion methods. If the operation can legitimately fail, the caller should decide how to handle it. Only keep catch for UI stabilization like `input.click({ force: true }).catch(() => textarea.focus())`.

**Rule (spec):** Never wrap assertions in `try/catch`. Use `test.skip()` in `beforeEach` if the test can't run. A real assertion on a swallowed catch path is P0 unless the identical check is re-asserted unswallowed later, control flow makes the test fail regardless, or the documented JUSTIFIED/intent path applies; a later assertion on a different fact does not excuse it. For swallowed non-assertion operations, judge the exemption by consequence, not by where the code sits: `try/catch` is **exempt only when the swallowed failure cannot change what the test proves** — best-effort teardown, cache cleanup, an optional element nothing asserts on. By the same measure **a swallowed wait, gate, or status check that a later assertion depends on is in scope**, even though it is not itself an assertion, because suppressing it lets the test reach that assertion in a state it never verified.

**Scanner tiering:** the rule above is the review contract; the deterministic scanner emits empty catches as `[LLM-TRIAGE]`, including attached catches on hard asynchronous assertions. Custom or shadowed receivers and recorded soft failures need contextual review because the candidate may not be a real catchable assertion. A synchronous matcher followed by an attached Promise `.catch()` throws before that `.catch()` can attach, but a synchronous assertion inside a surrounding `try/catch` is swallowed. A real swallowed assertion is P0 unless the identical check is re-asserted unswallowed later, control flow makes the test fail regardless, or the documented JUSTIFIED/intent path applies; a later assertion on a different fact does not excuse it. For swallowed non-assertion operations — action, navigation, query, readiness, status, and cleanup catches — Phase 2 must establish that a later assertion depends on the operation without independent meaningful verification before confirming P0; otherwise they remain candidates, not counted defects. The scanner emits no candidate where no later assertion can depend on the swallowed operation: a non-assertion `.catch()` inside the `finally` of a Playwright test's last statement, or in an `afterEach`/`afterAll` hook, with no `expect` after it in that callback; and a `locator.waitFor()` whose `.catch()` is followed in the same block by an awaited web-first assertion on the same locator that proves the waited state. The scanner also emits a `try/catch` as `[LLM-TRIAGE]` when the catch's own try body, paired by brace balance, holds a web-first matcher, a readiness or network wait, a poll, an `expect`, a Cypress `wait`/`get`/`contains`, a Page Object helper named for a check (`verifyX`, `ensureX`, `xVisible`), or a `throw`, unless it proves all-path propagation or a named application-error allowlist; assertion candidates follow the assertion rule and non-assertion candidates follow the dependency rule. An inverse guard that swallows the framework's timeout or assertion failure remains a Phase 2 candidate. A guard `throw` inside the try body also qualifies, so a try that only validates input can be a candidate. The hit line is the `catch` line, so a `// JUSTIFIED:` marker for it goes on a comment line directly above the `catch` line; anchor a confirmed finding at the protected assertion or non-assertion operation. Pairing runs on lexed source (comments, string and template contents, and regex literals removed), so a brace inside a literal or a `throw` in a comment does not change the verdict; it looks back at most 400 lines from the catch, and a try that starts further up leaves the catch to the bounded sweep. Quotes in simple same-line JSX text bounded by matching ordinary opening and closing tags, such as `<p>Don't panic</p>`, are inert. Quotes in multiline JSX text, fragments, or text following a nested child can still unbalance this deliberately bounded lexer and leave a catch unpaired; the bounded sweep covers those cases.

**#3 review hint:** the scanner lists `await x.act().catch(() => undefined);` as `[P2?][REVIEW-HINT]`, not as a P0 candidate, when the result is discarded (an expression statement, optionally awaited or `void`), the handler takes no parameter, and the receiver is a direct method call that is not a wait or navigation, a state check (`isVisible` and the other boolean reads), `count()`, a matcher, `toPass`, `poll`, `test.step`, a Promise combinator, `then`/`finally`, an assertion-named helper (`expect*`, `assert*`, `verify*`, `check*`, `ensure*`, `should*`, `validate*`, `wait*`) or a call that takes a callback. Nothing reads the fallback, so the only open question is whether a later step depends on the swallowed call. An empty block body (`() => {}`), a stored or returned result and every other fallback keep the P0 candidate.

**Effective timeout (Playwright swallowed wait or action) — refute first:** a `.catch` or `try/catch` around a Playwright wait or action can swallow a `TimeoutError` only when that call has a finite timeout. Establish it before any silent-pass verdict: (1) an explicit `{ timeout: N }` option with N > 0; (2) config `use.actionTimeout` > 0 for actions and `waitFor`, `waitForSelector`, `waitForResponse`, `waitForRequest`, `waitForEvent`, `waitForFunction`, or `use.navigationTimeout` > 0 for `goto`, `reload`, `waitForURL`, `waitForLoadState`, `waitForNavigation` (`actionTimeout` does not bound navigation); (3) `page.setDefaultTimeout` / `context.setDefaultTimeout` or `setDefaultNavigationTimeout` in scope, or `test.use({ actionTimeout })`; (4) for an expect-based wait, `expect.timeout` or its 5000 ms default. Playwright Test defaults `actionTimeout` and `navigationTimeout` to 0 (no limit). Read the config the runner actually uses (a `--config` script, a `projects[].use` override), not only `playwright.config.*`. With no finite timeout, a target that never arrives keeps waiting until the test timeout fails the test, and a test timeout cannot be caught, so the catch fires only on non-timeout errors (closed page, detached frame, strict-mode violation). Then the silent-pass claim is **FALSE-POSITIVE**: report it as a diagnostics issue at most (the test hangs to its timeout instead of failing fast), never as a #3 P0. `goto`, `reload` and `waitForFunction` are the exceptions: they reject at once on a network error or a throwing page predicate, so judge that non-timeout failure on its own. If the effective timeout depends on an environment variable or a config you cannot see, the verdict is NEEDS-CONTEXT, not CONFIRMED. Cypress commands are different: they time out at `defaultCommandTimeout` (4000 ms) unless configured, so this rule does not apply to Cypress. The scanner applies the provable part: with no explicit option and a single static Playwright config that sets no matching timeout, a no-timeout swallowed wait becomes a P2 candidate whose hint starts `no finite timeout: cannot swallow a timeout`; a finite or unknown timeout keeps the P0 candidate and its hint names the timeout source or why it is unknown.

**Three-way catch classification:** (1) A top-level unconditional `throw` is exempt only when it is reachable on every catch path. Logging or cleanup before it is fine; an earlier `return`, `break`, or `continue` breaks all-path propagation. (2) Otherwise, a conditional guard is exempt only when every `throw` is guarded by a negated identity test that allowlists one named application error and rethrows every other error. (3) Otherwise keep `[P0?][LLM-TRIAGE]`. This includes guards that swallow the framework's ordinary failure: `TimeoutError`, `AssertionError`, any identifier ending in `TimeoutError`, and those same names in `error.name` or `error.constructor.name` `===` / `!==` checks. Thus `!(e instanceof TimeoutError)` and `e.name !== 'TimeoutError'` stay candidates, while `!(e instanceof PaymentError)` is exempt. The scanner never confirms a candidate as P0; Phase 2 makes that decision. Prefer triage for other genuinely undecidable propagation shapes.

**Where to look:** a swallow counts wherever it executes, so check **any file the spec reaches — an imported helper or support module, a custom command, or a callback body such as `.then(...)`** — not only the spec body and POM classes. A swallow one import away is the same defect and is easier to miss; when a spec's assertions look adequate, follow the helpers it calls before concluding the file is clean.

```typescript
// BAD helper — the readiness gate is swallowed, so the spec's assertion runs
// against whatever the client optimistically rendered
try { await page.getByTestId('saved-badge').waitFor({ state: 'visible', timeout: 5000 }); }
catch (error) { console.warn('save not confirmed', error); }
```

```javascript
// BAD Cypress — the status assertion is swallowed inside the .then() callback
cy.wait('@ship').then((interception) => {
  try { expect(interception.response.statusCode).to.eq(201); }
  catch (error) { Cypress.log({ name: 'ship', message: 'skipped' }); }
});
```
